## 1. 문제 정의

### 1-1. 웹뷰를 쓰는 이유가 지금 작동하지 않는다

하이브리드(Flutter 셸 + 웹뷰 Vue) 구조를 택한 목적은
**"네이티브 수정이 아닌 변경은 서버 배포만으로 반영"** 이다.
현재 구조는 이 목적을 **전혀 달성하지 못하고 있다.**

### 1-2. 근거 (2026-08-02 실측)

| 확인 | 결과 |
|---|---|
| `lib/web_app.dart` release 경로 | `InAppLocalhostServer(documentRoot: 'assets/vue_app/')` → `http://localhost:8080/` |
| `prafta-app-frontend` 배포 스크립트 | **없음** (`prafta-web-frontend` 에만 `deploy-web.ps1` 존재) |
| `AWS_배포현황_및_운영전환가이드.md` 내 앱 프론트 언급 | **없음** |
| 로컬호스트 서빙 도입 시점 | 초기 커밋 `fb7f9e5` — 처음부터 번들 방식, 이후 재검토 없음 |

즉 **앱 프론트는 어디에도 호스팅된 적이 없다.** 웹뷰에서 현재 얻고 있는 이점은
"UI 를 Vue 로 작성할 수 있다" 뿐이고, OTA 갱신 경로는 배선되지 않았다.

### 1-3. 실제로 발생한 비용

2026-08-02, **로그인 화면 푸터 문구 한 줄**(`고객센터 1234-5678` → 이메일) 수정 때문에
Vue 재빌드 → `assets/vue_app/` 복사 → Flutter 빌드 116 생성이 필요했다.
Flutter 코드는 한 줄도 바뀌지 않았다. iOS 는 이런 변경도 **스토어 심사**를 거쳐야 반영된다.

## 2. 목표 / 비목표

### 목표

- Vue 만 바뀐 변경은 **웹 배포만으로** 설치된 앱에 반영된다.
- 원격 로딩이 실패해도 앱이 사용 불가 상태가 되지 않는다(번들 폴백).
- 잘못된 원격 배포를 **앱 업데이트 없이** 되돌릴 수 있다.

### 비목표 (이번 범위 아님)

- Flutter 네이티브 코드의 OTA 갱신 — 불가능하며 시도하지 않는다.
- 오프라인 전면 동작 — 로그인부터 API 가 필요해 애초에 성립하지 않는다.
- 안드로이드/iOS 서로 다른 로딩 전략 — **양 플랫폼 동일 전략**을 유지한다.

## 4. 목표 구조

### 4-1. 로딩 전략 — 원격 우선, 번들 폴백

```
셸 기동
  ├─ 원격 시도: https://<앱 프론트 호스트>/  (타임아웃 T초)
  │    ├─ 성공 → 원격 Vue 사용 ✅ (웹 배포만으로 갱신)
  │    └─ 실패/타임아웃 → 번들 폴백
  └─ 번들 폴백: InAppLocalhostServer('assets/vue_app/')  ← 현행 경로 그대로
```

**번들은 제거하지 않는다.** 스토어 릴리즈마다 갱신되는 "바닥"으로 남긴다.
평상시엔 쓰이지 않지만, 원격 장애 시 앱이 벽돌이 되는 것을 막는 유일한 수단이다.

### 4-2. 킬 스위치 / 버전 핀

원격 진입 전에 가벼운 매니페스트를 먼저 읽는다.

```json
// https://<host>/app-manifest.json  (CloudFront no-cache)
{
  "enabled": true,              // false → 즉시 번들 폴백 (앱 업데이트 없이 원격 중단)
  "minShellBridgeVersion": 3,   // 이 값보다 낮은 셸은 원격을 쓰지 않는다
  "entry": "/"                  // 필요 시 특정 버전 경로로 핀 (예: "/r/2026-08-02/")
}
```

- 원격 배포가 잘못됐을 때 **매니페스트만 바꿔 전 사용자를 번들로 되돌린다.**
- 매니페스트 조회 실패 시에는 **원격 시도(기존 정책)** 로 진행할지 **번들 폴백**으로 갈지
  §5 D3 에서 확정한다.

### 4-3. 브리지 버전 규약 (★이 작업의 핵심 리스크)

원격 Vue 는 최신인데 설치된 셸은 구버전일 수 있다. 이번 주에만 브리지가 2개 늘었다
(`REQUEST_CAMERA_PERMISSION` 08-01, `OPEN_APP_SETTINGS` 07-31).

**셸 → Vue 로 능력을 알린다.** `UserScript` 로 문서 시작 시점에 주입:

```js
window.__SHELL__ = {
  bridgeVersion: 3,
  platform: 'ios' | 'android',
  appVersion: '1.0.0',
  handlers: ['JS_CONSOLE','GET_GPS','GET_DEVICE_INFO','GET_APP_FOREGROUND_SEC',
             'GET_PUSH_TOKEN','SCAN_QR','OPEN_APP_SETTINGS','REQUEST_CAMERA_PERMISSION'],
};
```

**Vue 규약 (엄수)**
1. 브리지 호출 전 `handlers` 포함 여부를 확인한다.
2. 없으면 **기능을 조용히 낮추거나** "앱 업데이트가 필요해요" 로 명확히 안내한다.
   화면이 죽거나 무한 로딩에 빠지면 안 된다.
3. 새 브리지가 **필수인** 기능은 `minShellBridgeVersion` 을 올려 구셸을 번들로 보낸다.

#### 현재 브리지 목록 (v1 기준선)

| 방향 | 이름 | 래퍼 |
|---|---|---|
| Vue→네이티브 | `JS_CONSOLE` | (직접) |
| Vue→네이티브 | `GET_GPS` | `gpsBridge.js` |
| Vue→네이티브 | `GET_DEVICE_INFO` | `deviceBridge.js` |
| Vue→네이티브 | `GET_APP_FOREGROUND_SEC` | `foregroundBridge.js` |
| Vue→네이티브 | `GET_PUSH_TOKEN` | `pushTokenBridge.js` |
| Vue→네이티브 | `SCAN_QR` | (qr 호출부) |
| Vue→네이티브 | `OPEN_APP_SETTINGS` | `appSettingsBridge.js` |
| Vue→네이티브 | `REQUEST_CAMERA_PERMISSION` | `cameraPermissionBridge.js` |
| 네이티브→Vue | 푸시 토큰 refresh 콜백 | `pushTokenBridge.js` |
| 네이티브→Vue | 푸시 탭(open) 라우팅 | `pushRouteBridge.js` |

> **네이티브→Vue 방향도 계약이다.** 셸이 호출하는 `window.__on*` 콜백 이름이 원격 Vue 에서
> 사라지면 푸시 탭 라우팅이 죽는다. 이 방향은 기능 탐지가 불가능하므로 **콜백 이름은 절대
> 변경·삭제하지 않는다**(추가만 허용).

### (3) ★결함 2건 — 실기기에서만 드러남

**결함 A — 콜드스타트 라우팅 덮어쓰기 (앱FE `8959f4a8`, 양 플랫폼 공통)**

매핑을 추가했는데도 **전부 MainView 에서 멈췄다.**
셸은 `onLoadStop` 에서 `__onPushOpened` 를 호출하는데, 그 시점에 라우터는 아직 초기 이동
(`/` → `beforeEach` 의 `ensureAccessToken` 네트워크 대기 → `/MainView` replace)을 진행 중이다.
곧바로 `push` 하면 **뒤늦게 완료된 초기 이동이 목적지를 덮어쓴다.**
→ `router.isReady()` 로 초기 이동 확정을 기다린 뒤 push. 성공/실패 로깅 추가
   (종전 `.catch(() => {})` 가 실패를 통째로 삼켜 **무증상**이라 진단이 어려웠다).

**결함 B — ★iOS 전용 payload 유실 (셸 `2bbe2eb`)**

결함 A 수정 후 **안드로이드는 정상, iOS 만 여전히 메인화면**.

원격 판정(매니페스트 조회) 중 **`about:blank` 선행 로드의 `onLoadStop`** 이 먼저 발화해
보류 payload(`_pendingPushData`)를 flush 한다. 그런데 `about:blank` 에는 Vue 가 없어
`window.__onPushOpened && ...` 가드가 조용히 no-op 되는데, **`_pendingPushData` 는 이미 소비**된
뒤라 실제 앱 페이지가 뜬 시점엔 전달할 데이터가 없다.
안드로이드는 `getInitialMessage` 해소 시점이 달라 선행 flush 를 타지 않아 **미재현**.

> **근본 원인은 "전달 성공을 확인하지 않고 소비한 fire-and-forget 구조"다.**

→ JS 가 핸들러 존재 여부를 boolean 으로 반환하게 바꿔 **실제 전달을 확인**하고, 미등록이면
   300ms×10회(3s) 재시도(재시도 중 실제 앱 페이지로 전환되면 그때 성공), 끝내 실패하면
   **보류로 되돌려** 다음 `onLoadStop` 이 재시도한다 → **유실 경로 제거**.

| R-7 | QR 스캔(순회점검·일용직 입실) | 원격/번들 양쪽 정상 |
| R-8 | 출퇴근 GPS · 외근 등록 | 원격/번들 양쪽 정상 |
| R-9 | 파일 첨부(사진 촬영·갤러리) | 원격/번들 양쪽 정상 |

### 7-5. 캐시 / 배포 (C)

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| C-1 | 웹 배포 직후 앱 재기동 | **새 버전이 즉시 반영**(index.html no-cache 확인) |
| C-2 | 배포 직후 CloudFront 무효화 전 | 낡은 청크 참조로 깨지지 않음 |
| C-3 | 연속 2회 배포 | 중간 버전에 고착되지 않음 |
| C-4 | 배포 롤백(이전 커밋 재배포) | 앱에서 이전 화면으로 복귀 |
| C-5 | 오프라인 상태에서 앱 재기동(직전 원격 성공) | 번들 폴백으로 진입(원격 캐시에 의존하지 않음) |

### 7-6. 보안 (S)

| ID | 항목 | 기대 결과 |
|---|---|---|
| S-1 | 원격 로딩이 **HTTPS 전용**인지 | http:// 로는 원격 진입 불가 |
| S-2 | 원격 호스트 화이트리스트 | 매니페스트 `entry` 가 임의 외부 도메인을 가리켜도 **우리 호스트가 아니면 거부** |
| S-3 | 인증서 오류 시 | 진입 거부 → 번들 폴백. `onReceivedServerTrustAuthRequest` 가 **무조건 PROCEED 하지 않도록** 재검토 ★현행 코드는 무조건 PROCEED 다 → **✅ 해소, 단 대가 있었음**: 게이트 신설이 iOS 웹뷰 전멸을 유발(§6-3(3)). 판정은 `server_trust_policy.dart` 단일 출처 + 회귀 테스트. **`UNSPECIFIED`=유효 인증서 정상 결과이므로 PROCEED 대상** |
| S-4 | 토큰/세션 저장 위치 | 원격 오리진 전환으로 `sessionStorage` 의 `gv_*` 클레임이 유실되지 않는지 확인 ★**오리진이 바뀌면 스토리지가 분리된다 — 로그인 유지에 직결** |
| S-5 | ATS 축소 가능 여부 | T7 결과 반영 |

> **S-3·S-4 는 설계 단계에서 반드시 다뤄야 한다.**
> 특히 S-4: 현재 `http://localhost:8080` 오리진에 저장된 세션이 원격 오리진으로 바뀌면
> **전 사용자가 재로그인**하게 된다. 전환 시 1회 재로그인을 감수할지, 마이그레이션
> 경로를 둘지 §5 에 결정 항목으로 추가해야 한다. → **D7 로 승격 필요**

### 7-7. 플랫폼 매트릭스

7-1 ~ 7-6 을 **iOS 실기기 + 안드로이드 실기기** 양쪽에서 수행한다.
시뮬레이터/에뮬레이터 결과는 참고용이며 통과 판정 근거로 쓰지 않는다
(QR 검은 화면 건에서 실기기와 결과가 갈린 전례).

### 7-8. 단계적 롤아웃

전량 통과 후에도 즉시 전면 적용하지 않는다.

1. `enabled:false` 상태로 배포 → **전원 번들** (원격 코드가 실기기에 있지만 미사용)
2. 내부 인원만 원격 강제(디버그 스위치) → 수일 사용
3. `enabled:true` 전환 → 전체 원격
4. 이상 시 `enabled:false` 로 즉시 회귀 (앱 업데이트 불필요)

## 8. 롤백 절차

| 상황 | 조치 | 소요 |
|---|---|---|
| 원격 Vue 에 결함 | 이전 커밋 재배포(C-4) | 수 분 |
| 원격 자체가 불안정 | 매니페스트 `enabled:false` | 즉시 |
| 매니페스트/호스트 장애 | 앱이 자동으로 번들 폴백 | 자동 |
| 셸 로딩 로직 자체가 결함 | **앱 업데이트 필요** ← 이것만 되돌릴 수 없다 |

마지막 행 때문에 §7 이 중요하다. **셸 로딩 로직은 원격으로 못 고친다.**

## 9. 리스크 대장

| 리스크 | 영향 | 완화 |
|---|---|---|
| 브리지 스큐로 구셸 사용자 기능 파손 | 높음 | §4-3 규약 + B 시험 전수 + `minShellBridgeVersion` |
| 오리진 변경으로 전 사용자 재로그인 | 중간 | D7 에서 확정 (S-4) |
| 원격 배포 사고가 전 사용자에 즉시 전파 | 높음 | 킬 스위치 + 단계적 롤아웃 + 번들 폴백 |
| 첫 화면 지연 | 중간 | 타임아웃 D2 실측 + CloudFront |
| Apple 4.2 "최소 기능" 지적 | 낮음 | 웹뷰 콘텐츠 원격 로딩은 허용됨. 네이티브 기능(QR·GPS·푸시) 보유 소명 유지 |
| 셸 로딩 로직 결함 = 원격 복구 불가 | 높음 | §7 전량 통과 + 단계적 롤아웃 1단계(코드는 있으나 미사용) |
| **iframe 을 통한 브리지 우회 (H-1)** | 높음 | **✅ 봉쇄 완료 `9041885` — 2중 방어.** ① **1차**: 화이트리스트 밖 서브프레임 로드 자체 차단(`shouldOverrideUrlLoading`) ② **2차(심층)**: `forMainFrameOnly: true` — 1차가 뚫려도 제3자 iframe 에는 `__SHELL__`·`__APP_BASE_URL__` **주입 자체를 하지 않는다**(핸들러 목록 = 앱 능력 명세이므로 비노출). 정상 앱은 메인프레임 단일 origin 이라 무영향. ※번들(localhost) 시절엔 콘텐츠 출처가 우리 자산뿐이라 무해했으나, 원격 로딩에서 위험해진 **이 전환 특유의 신규 리스크** |
| **웹뷰 콜백의 iOS/안드 의미 차이** | 높음 | **⚠️ 실현됨(§6-3(3)) — iOS 웹뷰 전멸 3일.** 서버신뢰 챌린지는 iOS 에서 **유효 인증서에도 매 https 연결마다** 발생하고 정상 결과가 `UNSPECIFIED` 로 온다. 안드 검증만으로는 재현 불가 → `flutter test` + **iOS TestFlight 스모크 필수**(CLAUDE.md 규칙 승격) |
