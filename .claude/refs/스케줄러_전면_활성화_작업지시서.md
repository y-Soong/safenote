## 3. Phase 0 — 선행 코드 변경 (배포 1회)

### 3-1. 스케줄러 스레드풀 상향 ★모든 배치의 전제

현재 `application.properties` 에 `spring.task.scheduling.*` 설정이 **전혀 없어 스레드 1개**다(운영 로그상 14종 전부 `[scheduling-1]`).
이 상태로 연차 자동부여처럼 오래 도는 배치를 켜면 **그동안 PUSH 전송(30초 워커)과 TBM 자동시작이 그대로 밀린다.**

```properties
spring.task.scheduling.pool.size=${TASK_SCHEDULING_POOL_SIZE:5}
```

> 5로 잡는 근거: 동시 실행 가능성이 있는 상시 워커 3종(Push 30초 / TbmAutoStart 30초 / AttdReminder 매분) +
> 일배치 동시 구간(00:00 두 건) 여유. 상향은 스레드만 늘릴 뿐 배치 간 순서를 보장하지 않으므로,
> **같은 데이터를 만지는 배치가 동시에 돌지 않는지**는 cron 시각 분리로 유지한다(현행 그대로).

### 3-2. 누락된 게이트 키 3종 추가

세 스케줄러는 `@Value("${...:false}")` 로 **점 표기 프로퍼티를 읽고 있어 켤 수는 있으나**,
`application.properties` 에 `${ENV:기본값}` 매핑 줄이 없어 **운영 파일의 ENV 스타일 키가 무시된다.**
나머지 11종이 전부 ENV 매핑 관례를 쓰므로 관례를 통일한다.

```properties
prafta.leave.auto-grant.enabled=${LEAVE_AUTO_GRANT_ENABLED:false}
prafta.leave.auto-grant.cron=${LEAVE_AUTO_GRANT_CRON:0 30 0 * * *}
prafta.notice.ack-cleanup.enabled=${NOTICE_ACK_CLEANUP_ENABLED:false}
prafta.notice.ack-cleanup.cron=${NOTICE_ACK_CLEANUP_CRON:0 10 4 * * *}
prafta.attd-reminder.worker.enabled=${ATTD_REMINDER_WORKER_ENABLED:false}
prafta.attd-reminder.worker.cron=${ATTD_REMINDER_WORKER_CRON:0 * * * * *}
```

- 코드 기본값은 **false 유지**(형상 안전). 운영 ON 은 §4 에서 운영 파일로 명시한다.
- cron 키도 함께 매핑해야 §4 의 **cron 임시 단축 검증**이 가능하다.

### 3-3. `HolidaySyncScheduler` 스케줄 복원

`@Scheduled` 4줄이 전부 주석 처리돼 있다(그중 2줄은 과거 검증용 3분/2분 주기 잔재).

```java
// 현행(주석 상태)
//    @Scheduled(cron = "0 10 3 25 12 *")      // syncNextYear 원래 의도
//    @Scheduled(cron = "0 0/3 * * * *")       // ← 검증 잔재, 복원 금지
//    @Scheduled(cron = "0 0 4 1 * *")         // resyncThisYear 원래 의도
//    @Scheduled(cron = "0 0/2 * * * *")       // ← 검증 잔재, 복원 금지
```

조치:
1. 원래 의도 cron 2개만 복원하되 **게이트 프로퍼티 + cron 프로퍼티화**(다른 13종 관례에 맞춤)
2. **★API 서비스키 확인이 선행 조건**: `holiday.api.service-key=${HOLIDAY_API_SERVICE_KEY:}` 의 **기본값이 빈 문자열**이다.
   운영 파일에 키가 없으면 스케줄을 켜도 호출이 실패한다. 08-19 실측은 ENABLED/CRON 계열만 조회했으므로 **미확인 상태** → §4-0 에서 확인
3. 2028 공휴일 공백은 이번 검증(cron 단축)으로 즉시 채운다

### 7-2. ★오늘 발견된 함정 2건 (재발 방지)

**함정 A — `.properties` 값 뒤의 `#` 은 주석이 아니다**

```properties
DAILY_USER_EXPIRE_ENABLED=true   # 기본값 true지만 명시   ← 값이 "true   # 기본값..." 이 된다
```

`java.util.Properties` 는 **줄 맨 앞의 `#` 만** 주석으로 본다. 값 뒤에 붙이면 문자열의 일부가 되어
boolean 바인딩이 실패하고 **기동 자체가 깨진다**(`BeanCreationException`). 주석은 반드시 윗줄에 쓴다.
→ 운영 반영 전 로컬 파일에서 발견·수정 완료. **로컬 검증이 실제로 사고를 막은 사례.**

**함정 B — `platform-bootstrap.properties` 를 로컬에서 통째로 import 하면 운영 DB 에 붙는다**

그 파일에는 스케줄러 토글 외에 `DB_URL` / `DB_USERNAME` / `DB_PASSWORD`(**운영 RDS**),
`FIREBASE_CREDENTIALS_PATH`(실제 PUSH), `PPURIO_*`(실제 SMS) 가 함께 들어 있다. 로컬 기동 검증에
이 파일을 import 하면 **로컬에서 띄운 앱이 운영 DB 에 연결된 채 14종 배치를 전부 돌린다.**
→ 토글만 발췌한 `C:\PRAFTA\secrets\scheduler-toggles.local.properties` 를 별도로 만들어 사용한다.

**★검증 중 발견한 함정 2건 (C·D — §7-2 의 A·B 에 이어)**

- **함정 C — 공휴일 키가 비면 기동 자체가 죽는다**: `HolidayApiClient` 는 게이트 OFF 여도 무조건 생성되는 `@Component` 이고 생성자에서 fail-fast(`IllegalStateException`, 3376ae17·7월부터). "키 없어도 호출만 실패" 전제는 틀렸다. 로컬은 토글 파일에 `holiday.api.service-key=local-dummy-key` 직접 지정으로 통과. **운영 함의: 시크릿 파일 재생성 시 `HOLIDAY_API_SERVICE_KEY` 가 누락되면 백엔드 전체 기동 불가**(과거 "재생성이 PUSH 토글을 조용히 껐다" 전례가 이 키에선 기동 사망으로 격상). §8-2 반영 시 키 존재를 반드시 재확인.
- **함정 D — 개발 머신 시스템 환경변수에 FIREBASE 실키**: `FIREBASE_CREDENTIALS_PATH=C:\PRAFTA\firebase-sa.json` 이 머신 스코프에 있어 "토글 파일에 미포함=skip" 전제가 깨진다(로컬 PUSH 워커 ON=개발 DB 실토큰으로 실발송 위험). 토글 파일에 `push.fcm.credentials-path=`(빈값 직접 지정)으로 봉쇄 — import 파일이 `application.properties` 를 덮는 우선순위 실증됨.
