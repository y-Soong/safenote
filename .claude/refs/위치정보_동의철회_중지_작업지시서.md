# 위치정보 동의 철회·중지 도입 작업지시서

작성 2026-09-01 · 근거: 위치정보법 제24조(개인위치정보주체의 권리), 위치기반서비스 이용약관 제7조·제11조
선행 완료: 3년 보존기간 파기 배치(`GpsRetentionScheduler`, 커밋 89cfa2d8, 게이트 OFF 상태 운영 배포)

## §0. 배경과 확정 사항

### 0-1. 왜 하는가

약관과 법이 보장한 **동의 철회·일시 중지**를 행사할 수단이 서비스에 없다. 현재 위치기반서비스
이용약관(`TERMS_ID='005'`)은 `REQUIRED_YN='Y'` 이고, 로그인 게이트가 미동의 상태로는 진입을 막고
거부 시 로그아웃시킨다(`TermsAgreeView.vue:237`). 즉 **철회 상태가 물리적으로 존재할 수 없다.**

위치정보법 제24조①의 철회권은 필수/선택 동의 여부와 무관하게 보장 대상이며, 미이행은
법 제24조 위반(과태료 2천만원 이하)에 해당한다.

### 0-2. 사업 판단(사용자 확정)

**위치정보는 PRAFTA 서비스의 핵심 기능이다.** 따라서

- 가입 시 005 는 **필수로 동의받는다**(선택으로 내리지 않는다)
- 동의가 없는 상태(철회·중지·재동의 대기)에서는 **출퇴근·TBM 참석 등 이벤트를 차단**한다
- 차단 시 안내 후 **재동의로 유도**한다

법적으로도 위치정보가 "서비스 제공에 필요한 최소한"이면 미동의자에 대한 서비스 제공 거부는 정당하다.
쟁점은 "제공 거부"가 아니라 **"철회할 수단이 존재하는가"** 이며, 본 작업이 그것을 만든다.

### 0-3. 확정된 설계 (변경 금지 — 재논의는 사용자 승인 필요)

| # | 항목 | 확정 내용 |
|---|---|---|
| 1 | 사업장 지오펜스 | 저장 시 **주소 + 중심좌표 + 반경** 필수. 기존 결측분 마이그레이션. 신규 기본 반경 100m |
| 2 | 관리자 확인 화면 | 철회·중지 상태를 조회하는 **신규 화면**. 이력 관리 필수 |
| 3 | 배지 | 외근인데 좌표가 없는 건에 **전용 배지**. 원인 3종 구분 |
| 4-1 | 철회 | 해당 사용자 **위치정보(좌표) 전부 파기**. 재동의 전까지 미수집 |
| 4-2 | 중지 | 과거 좌표 **유지**. 재동의 전까지 미수집 |
| 4-3 | 이벤트 차단 | 철회·중지 시 출퇴근·TBM 등 이벤트 차단 → alert → 재동의 유도 |
| ① | 게이트 분리 | 005 는 **가입 필수 유지 + 로그인 게이트에서만 제외** (신규 컬럼) |
| ② | 오버나이트 | 진행 중인 근태는 **출근 시점의 동의 버전을 유효**로 인정 |
| ③ | 중지 2종 | **본인 중지**와 **재동의 대기**(약관 버전업)를 다른 상태로 분리 |
| ④ | 파기 이력 | 파기 사실을 이력으로 남긴다. **★좌표는 어떤 형태로도 남기지 않는다** |
| ⑤ | 006 가입 편입 | 연동 제3자 제공 동의를 가입 화면에 노출(단, **연동 사업장 한정**) |

### 0-4. 파기 범위 (4-1 상세 — 확정)

| 대상 | 처리 | 근거 |
|---|---|---|
| GPS 좌표 (평문 + 암호문 4컬럼 × 3테이블) | **파기(NULL)** | 개인위치정보 그 자체 |
| 행 자체 | **유지** | 지우면 근태·TBM 이수 기록이 함께 소멸(고객사 3년 보존 의무) |
| "외근이었다"는 판정(= 행의 존재) | **유지** | 판정 결과이지 좌표가 아님 |
| `OFFSITE_REASON`(외근 사유) | **유지** | 운영 실측 평균 4.3자·최대 15자, 장소로 읽히는 건 100건 중 1건 |
| `ACCURACY`, `IS_MOCKED` | 유지 | 좌표 아님 |
| `IP_ADDR` | 유지 | 접속기록이지 위치정보 아님 |
| 위치정보 **확인자료**(법 제16조②) | **범위 밖** | 테이블 자체가 없음 — §11 후속 과제 |

기간 제한은 두지 않는다. 법 문언이 "**수집된** 개인위치정보"로 과거형이고 기간 단서가 없다.
마감 여부와 무관하게 해당 계정의 보유분 전부가 대상이다.

### 0-5. 범위 밖 (이번 작업에서 하지 않음)

- **위치정보 확인자료**(제16조② 자동 기록·보존, 제24조③ 열람권) — 별건. §11 참조
- 3년 보존기간 파기 배치 — 이미 배포됨. 게이트 개방 시점만 별도 판단
- 약관 v04 본문의 서비스 반영(`TB_TERMS` 등록) — 별건

## §1. 상태 모델

### 1-1. 동의 상태 4종

| 상태값 | 의미 | 과거 좌표 | 이후 수집 | 이벤트 |
|---|---|---|---|---|
| `AGREED` | 동의 | 유지 | 수집 | 허용 |
| `SUSPENDED` | **본인 중지**(제24조②) | **유지** | 중단 | 차단 |
| `PENDING_REAGREE` | **재동의 대기**(약관 버전업) | **유지** | 중단 | 차단 |
| `WITHDRAWN` | **철회**(제24조①) | **전부 파기** | 중단 | 차단 |

### 1-2. 전이

```
                 ┌──────────── 재동의 ────────────┐
                 │                                │
  AGREED ──본인 중지──> SUSPENDED ─────────────────┤
     │                                            │
     ├──약관 버전업──> PENDING_REAGREE ────────────┤
     │                                            │
     └──철회(좌표 파기)──> WITHDRAWN ──────────────┘
```

- **약관 버전업은 철회가 아니다.** 회사 사정으로 문서가 바뀐 것이므로 과거 좌표를 파기하지 않는다
  (`PENDING_REAGREE`). 이것을 철회로 처리하면 개정할 때마다 전 사용자의 위치정보가 소멸한다
- `WITHDRAWN` → 재동의는 가능하나 **파기된 좌표는 복구되지 않는다**. 사전 고지 필수
- `SUSPENDED` 는 **본인만** 설정/해제한다(관리자 대행 금지)

### 1-3. ★`SUSPENDED` 와 `PENDING_REAGREE` 를 반드시 분리하는 이유

법 제24조②는 본인의 일시 중지 요구에 대해 **"거절하여서는 아니 되며"** 라고 명시한다. 본인 중지에
대한 이벤트 차단은 향후 재검토 여지가 있는 반면, 재동의 대기는 유효한 동의가 없는 상태라 차단이
명백히 타당하다. **지금 상태를 나눠 두지 않으면 나중에 분리할 수 없다.**

### 2-1. 약관 게이트 분리 — ★현행/이력 짝 테이블

```sql
ALTER TABLE TB_TERMS            ADD COLUMN LOGIN_GATE_YN VARCHAR(1) NOT NULL DEFAULT 'Y'
    COMMENT '로그인 게이트 대상 여부[Y:게이트가 미동의를 잡음/N:제외]';
ALTER TABLE TB_TERMS_ID_VERSION ADD COLUMN LOGIN_GATE_YN VARCHAR(1) NOT NULL DEFAULT 'Y'
```

> **★★함정**: `TB_TERMS`(현행, 가입·게이트가 읽음)와 `TB_TERMS_ID_VERSION`(이력, 관리 화면이 읽음)은
> 반드시 짝으로 처리한다. 2026-07-20 `prafta-terms-real-content-1.sql` 이 현행만 UPDATE 하고 이력을
> 누락해 6건 중 5건에서 현행 약관이 관리 화면에 보이지 않는 사고가 있었다.

**왜 컬럼을 추가하는가**: 현재 `REQUIRED_YN` 하나가 두 곳을 동시에 제어한다.

```
가입 목록      BaseinfoMapper.selectJoinTermsList        WHERE B.REQUIRED_YN = 'Y'
로그인 게이트   Terms01Mapper.selectPendingRequiredTerms  WHERE B.REQUIRED_YN = 'Y'
```

005 는 **가입 때는 받고 게이트는 안 잡아야 하는 제3의 부류**라 한 컬럼으로 표현할 수 없다.
005 를 `REQUIRED_YN='N'` 으로 내리면 가입 화면에서도 사라져 신규 가입자가 전원 미동의로 시작한다.

### 2-2. 동의 상태 확장

```sql
ALTER TABLE TB_TERMS_USER_AGR_MGMT ADD COLUMN CONSENT_STATE VARCHAR(20) NULL
    COMMENT '동의 상태[AGREED/SUSPENDED/PENDING_REAGREE/WITHDRAWN] — NULL=상태 관리 대상 아닌 약관';
```

> **★`AGR_YN` 을 없애거나 의미를 바꾸지 않는다.** `AGREED` 는 `AGR_YN='Y'`, 나머지 셋은 전부
> `AGR_YN='N'` 으로 유지한다. 그래야 기존 `AGR_YN='Y'` 조건을 쓰는 모든 쿼리가 **수정 없이 정확하게**
> 동작한다(중지·철회·재동의대기 = 미동의). 이것이 무회귀의 핵심 장치다.

`AGR_SOURCE` 허용값에 다음을 추가한다(코드 상수만 확장, 컬럼 변경 없음).

- `SYSTEM` — 약관 버전업으로 `PENDING_REAGREE` 전이
- `ADMIN` — 관리자 대행(현재 미사용, 예약)

후자는 "그래서 무엇을 지웠다"로 성격이 다르다.

## §3. 백엔드

### 3-1. ★위치 수집 전 동의 확인 (신규 — 이번 작업의 몸통)

현재 백엔드에 **`005` 를 참조하는 코드가 한 줄도 없다.** 로그인 게이트가 강제하고 있어 확인할 필요가
없었기 때문이다. 게이트에서 빼는 순간 이 판정을 새로 만들어야 한다.

```
LocationConsentService
  ├─ resolveState(cmpnyCd, userCd)            → 4-state
  ├─ isCollectAllowed(cmpnyCd, userCd)        → AGREED 만 true
  └─ isCollectAllowedForAttd(…, attdId)       → ② 오버나이트 예외 포함
```

- **판정 단일 출처**로 만든다. 근태·TBM·향후 기능이 모두 이 서비스를 경유한다
- 상태 판정은 `TB_TERMS_USER_AGR_MGMT.CONSENT_STATE` 를 본다. NULL 이면 `AGR_YN` 으로 폴백
  (기존 사용자 승계 — §6-2)

### 3-2. ★② 오버나이트 예외

`TB_TERMS.STR_DATE` 는 `varchar(8)` 날짜라 **시행 시점이 자정**이다. 오버나이트 근무자는 정의상
자정을 넘기므로, 약관을 개정할 때마다 **오버나이트 근무자 전원이 퇴근 시점에 재동의 팝업을 만난다.**

→ **진행 중인 근태(출근 O, 퇴근 X)는 출근 시점의 동의 버전을 유효로 인정**한다. 퇴근까지 마친 뒤
다음 이벤트부터 재동의를 요구한다. 이 예외는 `PENDING_REAGREE` 에만 적용하고,
`WITHDRAWN`·`SUSPENDED`(본인 의사) 에는 적용하지 않는다.

### 3-3. 이벤트 게이트 (4-3)

차단 대상은 **위치정보에 의존하는 이벤트**다.

| 기능 | 차단 | 비고 |
|---|---|---|
| 출근 / 퇴근 | ✅ | |
| TBM 입실 (`GPS_VERIFY_TYPE_CD='AUTO'`) | ✅ | 운영 27건 중 19건 |
| TBM 입실 (`DISABLED`·`MANUAL`) | ✅ | 확정 설계에 따라 함께 차단 |
| 일용직 QR 입실 | ✅ | 확정 설계에 따라 차단 |

응답은 전용 오류코드로 내려 클라이언트가 재동의 화면으로 분기할 수 있게 한다.

```
ATTD_403_xxx / TBM_403_xxx  →  { code, message, consentState, termsId:'005', termsVersion }
```

### 3-4. 철회 / 중지 / 재동의 EP

```
POST /appApi/terms01/location-consent/withdraw    철회 (좌표 파기 동반)
POST /appApi/terms01/location-consent/suspend     본인 중지
POST /appApi/terms01/location-consent/resume      재동의
GET  /appApi/terms01/location-consent             현재 상태 조회
```

- **본인만 호출 가능**하다. 관리자 대행 철회는 만들지 않는다(오조작 시 복구 불가)
- 철회는 **단일 트랜잭션**에서 ①상태 전이 ②동의 이력 ③좌표 파기 ④파기 이력을 처리한다
- 파기 실패 시 상태 전이도 롤백한다. "철회는 됐는데 안 지워진" 상태를 만들지 않는다

### 3-5. 파기 실행

3년 배치(`GpsRetentionMapper`)와 **동일한 UPDATE 형태**이고 `WHERE` 만 바뀐다.

```
3년 배치 : WHERE 수집일 < cutoff       AND 좌표 IS NOT NULL  LIMIT n
철회     : WHERE CMPNY_CD=? AND USER_CD=? AND 좌표 IS NOT NULL
```

대상 3테이블:

| 테이블 | 좌표 컬럼 | 비고 |
|---|---|---|
| `TB_USER_ATTD_GPS` | `LAT`,`LON`,`LAT_ENC`,`LON_ENC` | 출퇴근 |
| `TB_TBM_ATTENDANCE` | `ENTRY_GPS_LAT`,`LON`,`_ENC` 2 | TBM 입실 |
| `TB_TBM_SESSION` | `MANAGER_GPS_LAT`,`LON`,`_ENC` 2 | **본인이 개설한 세션의 관리자 좌표** |

- **★평문·암호문을 반드시 쌍으로 NULL 처리**한다. 읽기 폴백이 "`*_ENC` 가 NULL 이면 평문 컬럼"
  (`GpsCoordCrypto.resolveToBigDecimal`)이라 암호문만 지우면 **파기한 좌표가 되살아난다**
- 파기 전에 건수·최초/최종 수집일을 집계해 파기 이력에 남긴다
- 일용직(`TB_DAILY_USER`) 계통도 동일하게 처리한다

### 3-6. 관리자 조회 API (2번)

- 회사 내 사용자별 현재 상태 + 최근 전이 이력
- **★`canManageNode` 게이트 필수.** `assertSiteAccess` 만으로는 일반 사원의 전 직원 조회를 막지 못한다
  (본 프로젝트에서 3회 재발한 함정). 이 화면은 "누가 위치정보 동의를 철회했는가"라 그 자체로 민감하다
- **일용직 포함**. `TB_TERMS_USER_AGR_HIST.USER_CD` 주석이 두 계통 모두를 대상으로 명시한다

### 3-7. 약관 버전업 → `PENDING_REAGREE` 전이

약관 버전이 올라가면 `TB_TERMS_USER_AGR_MGMT` 의 PK `(CMPNY_CD, USER_CD, TERMS_ID, TERMS_VERSION)`
가 어긋나 매칭 행이 사라진다. 이때 **조용히 미동의로 떨어지지 않도록** 신규 버전 행을
`PENDING_REAGREE` 로 생성한다(`AGR_SOURCE='SYSTEM'`).

### 3-8. 가입 화면 약관 목록 (①·⑤)

```
005 : REQUIRED_YN='Y' 유지 → 가입 화면에 필수로 계속 노출
006 : 선택으로 노출하되 ★가입 시점에 사업장이 ACTIVE 연동인 경우에만
```

> **★006 을 무조건 노출하면 안 되는 이유**: 006 게이트 해제 판정이 **"응답 행 존재"(Y/N 무관)** 이다
> (`ConsentMapper`). 가입 때 무조건 물어 `'N'` 을 저장하면, **나중에 그 사업장이 새로 연동돼도 게이트가
> 다시 뜨지 않아** 하청 직원 전원이 미동의로 굳는다. 연동 여부는 `ConsentMapper.countActiveSiteLinkMember`
> 와 동일 조건으로 판정한다.

### 3-9. 사업장 저장 검증 (1번)

- 주소 · 중심좌표(LAT/LON) · 반경 **전부 필수**. 하나라도 없으면 저장 거부
- 반경은 숫자만 허용, 하한 설정(예: 10m 미만 거부 — `'0'` 유입 차단), 상한도 검토
- 신규 생성 시 반경 기본값 **100m**
- **주소 → 좌표 지오코딩**을 함께 넣는다. 주소만 받고 좌표를 안 채우면 지오펜스가 그려지지 않아
  필수화의 의미가 없다(운영 13곳 중 주소는 100% 있는데 좌표는 7곳이 없다)
- **★미러(연동) 사업장 예외**: `LINK_SRC_SITE_CD IS NOT NULL` 인 사업장은 수정 잠금이라 하청이 고칠 수
  없다. 원청 값이 결측이면 저장 필수 규칙을 만족시킬 방법이 없으므로, 미러는 검증 대상에서 제외하고
  **원본(원청) 쪽에서 채우도록** 안내한다

## §6. 마이그레이션

`prafta-location-consent-2-migration.sql` — **개발·운영 양쪽 적용**

### 6-1. 사업장

1. `GPS_RANGE` 값 정규화: `NULL`·`''`·`'0'` → `100`
2. 중심좌표 결측 7곳: 주소 기반 지오코딩으로 채운다. **일괄 SQL 로는 불가**하므로 별도 스크립트 또는
   관리 화면에서 처리하고, 완료 여부를 검증 쿼리로 확인한다
3. **★적용 전 고객사 안내**: 미설정 사업장에 반경이 생기는 순간 **그 사업장의 외근 판정이 새로 살아난다.**
   정상 출근이 외근으로 뒤집힐 수 있고, 외근일 때만 좌표를 저장하므로 수집량도 늘어난다.
   기존 값이 150·200·500 으로 제각각인 것을 보면 현장별 편차가 크므로, 가능하면 **일괄 100m 대신
   현장별 실측값**을 받는다

### 6-2. 기존 동의 상태 승계

```sql
UPDATE TB_TERMS_USER_AGR_MGMT
   SET CONSENT_STATE = CASE WHEN AGR_YN = 'Y' THEN 'AGREED' ELSE 'WITHDRAWN' END
 WHERE TERMS_ID = '005';
```

- 현재 005 는 필수라 **사실상 전원이 `AGR_YN='Y'`** 다. 예외 행이 있으면 먼저 원인을 확인한다
- 승계 전 건수를 기록하고, 승계 후 `AGREED` 건수와 대조한다

|---|---|

## §8. 함정 목록 (착수 전 정독)

1. **약관 테이블은 현행·이력 짝으로** — `TB_TERMS` + `TB_TERMS_ID_VERSION`. 2026-07-20 실사고
2. **평문·암호문 쌍 파기** — 암호문만 지우면 폴백으로 좌표가 되살아난다
3. **`canManageNode` 게이트** — 신규 웹 조회 화면. 3회 재발
4. **매퍼 XML 주석** — 주석 속 `<` 는 기동 실패, 주석 속 `#{}` 는 조회 전멸. 수정 후 스캔 필수
5. **`SITE_CD` 술어** — `NODE_CD` 는 사업장마다 중복(`n1` 등). 부서 조건에 `SITE_CD` 필수
6. **DB 마이그레이션 양환경 동시 적용**
7. **크로스 네임스페이스 refid 금지** — 기동은 성공하고 첫 API 호출에 앱 전체가 죽는다
8. **`GET_LOCK` 락 이름 64자 제한** — 신규 락은 `MD5(#{lockKey})` 래핑
9. **일용직 계통 누락 주의** — `TB_USER` / `TB_DAILY_USER` 두 계통
10. **`(CMPNY_CD, USER_CD)` 복합키** — `USER_CD` 는 회사별 채번이라 단독 식별 불가

## §9. 단계 분할

| 단계 | 내용 | 선행 | 배포 단위 |
|---|---|---|---|
| **S1** | 사업장 좌표·반경 필수화 + 지오코딩 + 마이그레이션 | 없음(독립) | 단독 배포 가능 |
