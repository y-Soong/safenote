## 1. 전환 방식 결정

**1차(필수): RDS 파라미터 그룹 `time_zone = Asia/Seoul`** — DB 전역 적용. Workbench 수동 세션까지
KST가 되어, 이후 수동 SQL의 NOW()도 KST(재오염 원천 차단). `time_zone`은 동적 파라미터라 **인스턴스
재부팅 불필요**(단, 이미 맺어진 커넥션에는 미적용 — 그래서 §3의 "앱 정지 → 전환 → 기동" 순서가 필수).

**2차(권장, 벨트): 백엔드 DB_URL에 `connectionTimeZone=Asia/Seoul&forceConnectionTimeZoneToSession=true` 추가**
— 파라미터 그룹이 어떤 이유로든 원복돼도 앱 커넥션은 항상 KST 세션을 강제. (EC2 환경변수 DB_URL 수정,
배포·운영 매뉴얼의 서비스 재기동 절차와 함께)

## 2. 보정(마이그레이션) 대상 원칙 (분류 확정 — 2026-08-30)

- 대상: **DATETIME 283컬럼**(전 컬럼 − 예외 2) 중 **벽시계가 @CUTOVER_UTC 이후인 행만** +9h.
- 제외(Java-KST 기록): `tb_near_miss.OCCUR_DTIME`, `tb_cmpny_share_snapshot_nearmiss.OCCUR_DTIME`.
- 제외: varchar 일자/시각(YYYYMMDD, HHmm 등 — Java 기록, TZ 무관), DATE 타입 7개.
- MIXED(한 컬럼에 NOW/Java 병행 기록): **0건 확인** — 행 단위 판별 불가 케이스 없음.
- @CUTOVER_UTC(이관 경계) 결정: **AWS 콘솔에서 RDS `prafta-db` 인스턴스 생성 시각(UTC)을 확인**해
  보정 SQL 상단 `SET @CUTOVER_UTC = '...'` 에 기입(사용자 수행). 이전 벽시계 행 = 덤프 이식분(KST, 무보정),
  이후 = 라이브(UTC, +9h). 그레이존(경계 직전 9시간의 개발 기록 행이 과보정될 가능성)은 전부
  실고객 이전 테스트 데이터라 수용(§5).

## 5. 알려진 한계 (보정하지 않는 것)

- DATE 타입 컬럼(기준정보 UPDATE_DATE 등): 시각이 없어 KST 00~09시 기록분의 하루 밀림을 소급 판별
  불가. 기준정보 수정일 수준이라 영향 미미 — 보정하지 않고 기록만 남긴다.
- ID 채번의 날짜 접두(D20260830…, H…): 과거 발번 ID의 날짜부가 KST와 최대 하루 어긋난 채 남는다.
  식별자일 뿐 판정에 쓰이지 않아 무해. 전환 후 신규 발번은 KST.
- 과거 로그 파일(prafta.log)의 시각: 로그는 JVM(KST) 기준이라 원래 정상.
- (잠복 주의) TB_TBM_ATTENDANCE_EVENT.EVENT_TIME 은 DDL 주석상 "클라이언트 보고" 컬럼이나 현재
  쓰기 경로가 전무(0행). 향후 이벤트 적재 구현 시 **DB NOW() 기록으로 통일**할 것 — 클라이언트
  시각(KST 문자열)을 넣으면 Tbm04Mapper 의 CONVERT_TZ 표시가 이중 밀림이 된다(전환 후엔 무관).

## 6. 검증 쿼리 (확정본은 보정 SQL 파일 하단에 동봉)

- (A) 사전(실행 직전 Workbench에서 재확인 — 2026-08-30 운영 실측 기준값 병기):
  ```sql
  -- ①커버리지: 285 여야 함(=보정 283 + 예외 2). 285 초과면 이후 DDL로 늘어난 것 - 중단·보고
  SELECT COUNT(*) FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND DATA_TYPE='datetime';
  -- ②std_time_rule 테이블 부재 확인: 0 이어야 함(개발 전용 - 있으면 보정 누락이므로 중단)
  SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA=DATABASE()
   AND TABLE_NAME IN ('tb_attd_std_time_rule','tb_attd_std_time_rule_his');
  -- ③기록자 없는 컬럼 0건 재확인: 전부 0 이어야 함
  SELECT (SELECT COUNT(*) FROM tb_tbm_attendance_event) AS ev,
         (SELECT COUNT(*) FROM tb_tbm_edu_mtrl WHERE GEN_AT IS NOT NULL) AS gen,
         (SELECT COUNT(*) FROM tb_tbm_pwd_fail) AS pf;
  -- ④기준 표본 기록: TBM 세션 T202608300001022 ENDED_AT 벽시계 = 01:49 (보정 후 10:49 기대)
  ```
  Workbench "오류 시 계속 실행" 옵션이 꺼져 있는지 확인(보정 SQL 가드가 오류 정지에 의존).
- (B) 사후: 표본 재조회 — ENDED_AT=10:49 여야 함. `NOW()` 가 KST인지(`DATE_FORMAT(NOW(),'%H')` ≈ 현재 KST 시),
  미래 시각 행 0건 검사(`col > NOW()` 이상치), 행수 불변 확인.
  추가(security Low #4): `SELECT CONVERT_TZ(NOW(), @@SESSION.time_zone, '+09:00');` 가 **NULL 이 아닌지** 확인
  — 전환 후 세션 TZ 가 명명 존('Asia/Seoul')이 되므로 mysql tz 테이블 부재 시 CONVERT_TZ 가 NULL 을 반환해
  CONVERT_TZ 적용 화면(TBM/LBS)의 행이 조용히 사라진다(RDS 는 기본 적재라 현실 위험 낮음 — 확인만).
- (C) 화면: Tbm_04 종료일시(=10:49), 요청함 요청일시, 로그인(비번 5회 실패 → 잠금 N분 안내), 근태 출퇴근 1건.

## 8. 전환 후 코드 정합 (검증 완료 사항)

- `CONVERT_TZ(col, @@SESSION.time_zone, '+09:00')` 보정 지점(Tbm04Mapper, PlatformLocationMapper):
  KST 세션에서 no-op — **회귀 없음, 제거 불요**(제거해도 무방하나 남겨두면 세션 TZ에 대한 방어가 유지됨).
- Platform_05 epoch(UNIX_TIMESTAMP) 지점: 전환+보정 후 정합(KST 벽시계 × KST 세션 = 올바른 epoch).
- 비밀번호 잠금/LBS 수정(Phase 1): DB 서버 시계 기준 판정이라 전환 전/후 모두 올바름.
- 전수조사의 "표시 -9h" 결함 대부분은 전환+보정으로 자동 해소(별도 화면 수정 불요).
