## 0. 공통 원칙

### 브랜치 전략 (2026-07-19 확정)

```
develop 브랜치에서 작업 → 커밋
    ↓ 검증 완료 시
main 병합 → origin push        (git checkout main → git merge develop → git push origin main)
    ↓
운영 배포                       (배포 스크립트가 origin/main 을 자동으로 받아 배포)
    ↓
develop 복귀                    (git checkout develop)
```

- **배포는 git 에 push 된 코드만 나간다.** 배포 스크립트는 로컬 작업 트리를 쓰지 않고, `origin/main`(기본)을 임시 worktree 에 받아 빌드한다. 미커밋/미push 변경은 물리적으로 배포될 수 없다.
- repo 구조: 웹/백엔드/.claude = `C:\PRAFTA` 단일 repo (`github.com/y-Soong/safenote`). Flutter 만 별도 repo (`C:\PRAFTA\PRAFTA_FLUTTER`, `safenote_flutter`).

## 1. 백엔드 배포 (Spring Boot → EC2)

### 표준 절차 (스크립트 — 권장)

```powershell
cd C:\PRAFTA\PRAFTA\prafta-backend
powershell -ExecutionPolicy Bypass -File .\scripts\deploy-backend.ps1
```

옵션:
| 옵션 | 용도 |
|---|---|
| `-Ref origin/develop` | 특정 브랜치 배포 (개발 WAS 생기면) |
| `-Ref <커밋해시>` | 특정 커밋 배포 = **이전 버전 롤백 수단** |
| `-UseWorkingTree` | (비상용) 로컬 작업 트리 그대로 배포 |

스크립트가 자동으로: fetch → worktree 빌드 → `.new` 업로드 → 기존 JAR `.prev` 백업 → 재기동 → 헬스체크 → **실패 시 자동 롤백** → 커밋 해시 기록.

결과 해석:
- 초록 "배포 완료" = 끝.
- 노랑 "롤백 성공" = 신규 버전 문제로 이전 버전 자동 복구됨. 서비스는 정상. 로그로 원인 확인.
- 빨강 "수동 조치 필요" = 롤백도 실패. 아래 완전 수동 절차로 대응.

⚠️ **신규 마이그레이션 SQL 이 있으면 반드시 백엔드 배포 전에 §4 절차로 선적용** (Flyway 도입 전까지).

### 완전 수동 절차 (스크립트 불가 시)

```powershell

$env:JAVA_HOME = "C:\Java\jdk-21.0.2"

# 산출물: build\libs\prafta-backend-0.0.1-SNAPSHOT.jar
```

```bash

# 3) 서버에서 백업 → 교체 → 재기동
ssh -i C:/Users/dudjs/.ssh/prafta-key.pem ec2-user@3.38.237.103
  cp -f ~/prafta/prafta-backend.jar ~/prafta/prafta-backend.jar.prev
```

## 4. DB 운영 (RDS MySQL)

### 접속 방법

RDS 는 퍼블릭 액세스가 없다. **백엔드 EC2 를 경유**해서만 접속:

```bash
ssh -i C:/Users/dudjs/.ssh/prafta-key.pem ec2-user@3.38.237.103
mysql prafta        # 접속정보는 ~/.my.cnf 에 저장돼 있어 인자 불필요
```

- Workbench 접속: **Standard TCP/IP over SSH** — SSH 호스트 `3.38.237.103:22`/`ec2-user`/pem 키, MySQL 호스트 `prafta-db.cj2yeu0mepo8.ap-northeast-2.rds.amazonaws.com:3306`, 계정 `prafta`. 연결 이름을 "PRAFTA-운영(주의)" 처럼 명확히 할 것.
- 로컬 개발 DB 와 운영 DB 는 별개다. Claude 세션의 MCP `prafta-mysql` 은 **로컬 DB** 를 본다 — 운영 DB 를 보고 있다고 착각하지 말 것.

### 스키마 변경(마이그레이션 SQL) 적용 절차

1. **사전 스냅샷**: RDS 콘솔 → `prafta-db` → 작업 → 스냅샷 생성 (되돌릴 지점 확보)
2. SQL 파일 업로드: `scp -i <키> migration.sql ec2-user@3.38.237.103:/tmp/`
3. 적용: `mysql prafta < /tmp/migration.sql`
4. 검증 후 `/tmp` 의 SQL 파일 삭제
5. 백엔드가 새 스키마를 요구하면 **백엔드 배포와 순서 조율** (통상: 하위호환 스키마 먼저 적용 → 백엔드 배포)
※ Flyway 도입(요청서 준비됨) 후에는 이 수동 절차가 사라지고 배포 시 자동 적용된다.

### 주의사항 (과거 사고 이력 기반)

- `lower_case_table_names=1` 파라미터 그룹(`prafta-mysql80-params`) 필수 — **인스턴스 생성 시에만 지정 가능**. 인스턴스 재생성할 일이 있으면 반드시 이 파라미터 그룹으로.
- 함수/프로시저 로드는 `log_bin_trust_function_creators=1` 필요 + 덤프의 `DEFINER` 절 제거 필요.
- 백업: 자동 백업 보존 **1일** (무료 플랜 제한 — 유료 전환 시 7일로 확대 예정). 중요 작업 전에는 수동 스냅샷을 찍을 것.

## 5. AI 스택 운영 (EC2 `prafta-ai` — 평소 중지)

### 시연 때 켜기

1. EC2 콘솔 → `prafta-ai` → **인스턴스 시작**
2. **1~2분 대기** → 끝. (docker 자동기동 + `restart: unless-stopped` + TEI 모델 캐시 → pgvector·TEI 자동 준비, 백엔드 재연결 자동 — 설정 변경·재기동 불필요)

## 6. 인증서·인프라 유지보수

### HTTPS 인증서 (Let's Encrypt, origin.prafta.com)

- **자동갱신**: `certbot-renew.timer`(systemd) + **DNS-01**(Cloudflare API hook) — 2026-07-19 구성. 80 포트 불필요.
- 상태 확인:
  ```bash
  sudo certbot certificates                  # 만료일 확인
  systemctl list-timers | grep certbot      # 타이머 동작 확인
  sudo certbot renew --dry-run              # 갱신 사이클 검증 (실제 갱신 안 함)
  ```
- 구성 요소: 훅 `/usr/local/bin/certbot-cf-{auth,cleanup}.sh`, 토큰 `/etc/letsencrypt/cloudflare-token`(600, 로컬 사본 `C:\PRAFTA\secrets\cloudflare-dns-token.txt`)
- Cloudflare 토큰을 재발급(폐기)하면 갱신이 깨진다 — 재발급 시 서버 토큰 파일도 교체할 것.
- ⚠️ pip 로 certbot 플러그인 설치 금지(2026-07-19 사고 — awscli·certbot 동반 파손됨. hook 방식이 정답).

### CloudFront / 보안그룹 — 건드리면 안 되는 것

| 항목 | 값 | 주의 |
|---|---|---|
| 웹 배포 | `E37OL8Q9Q1FSLZ` (prafta.com) | 오류페이지 404/403→/index.html+200 유지 (SPA) |
| API 배포 | `E1RO89G48H78J7` (api.prafta.com) | 오리진 **https-only + TLSv1.2**, 오리진요청정책 **AllViewer**, 오류페이지 없음 — 셋 다 변경 금지 |
| 보안그룹 `prafta-backend-sg` | SSH 22(내IP) + 443(`pl-22a6434b`)만 | **이 두 줄 외에 아무것도 없는 게 정상.** 80 없음. SSH 삭제 시 서버 접속 불가 |
| ACM 검증 CNAME (`_e5fd79f...`) | Cloudflare 에 유지 | 삭제 시 CloudFront 인증서 갱신 실패 |

## 7. 장애 대응 요약

| 증상 | 1차 확인 | 대응 |
|---|---|---|
| API 무응답/504 | §0 헬스체크 규칙으로 판정 → 서버 로그 `journalctl -u prafta-backend` | 앱 문제면 직전 커밋 롤백: `deploy-backend.ps1 -Ref <이전커밋>` |
| 배포 직후 API 다운 | 스크립트가 자동 롤백했는지 출력 확인 | 자동 롤백 실패 시 §1 수동 롤백 |
| 웹 옛 화면 | CloudFront 캐시 | 무효화 실행 + 강력 새로고침 |
| 웹 API 호출 실패(CORS 등) | index.html 에 `__APP_CONFIG__` 있는지 / 신규 게이트가 OPTIONS 를 차단하는지(§6-15 함정) | 없으면 웹 재배포 / 게이트에 사전요청 통과 추가 |
| AI 기능 무응답 | `prafta-ai` EC2 가 켜져 있는지 → AI 토큰 쿼터 소진 여부(Platform_03) | 콘솔에서 시작 후 1~2분 대기 / 한도 상향 |
| 인증서 만료 임박 경고 | `sudo certbot certificates` + `renew --dry-run` | dry-run 실패 시 Cloudflare 토큰 유효성 확인 |
| DB 접속 불가 | RDS 콘솔 상태 / 백엔드 로그의 접속 에러 | RDS stop 상태면 시작 (stop 후 7일이면 자동 재시작됨) |

문의/이력: 배포 이력 `deploy-history.log`, 인프라 전환 이력·함정 목록은 `AWS_배포현황_및_운영전환가이드.md` §6 참조.
