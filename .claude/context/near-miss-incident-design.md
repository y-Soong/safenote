# 아차사고/사건 보고 도메인 — 설계 제안서

> 상태: **설계 제안(미구현)**. 개발 착수 전 안전보건 담당/노무사 검토 권장.
> 배경: 근로자가 올리는 "위험성평가 요청" 중 아차사고를 관리자가 구분해 별도 처리하려는 요구.
> 핵심 결론: 아차사고는 위험성평가(산안법 §36)의 한 *타입*이 아니라, 위험성평가를 촉발하는 **별도 '사건' 도메인**이다 → `tb_risk_assessment`와 분리하고 **연계(link)** 한다.
> 관련 코드: `prafta-web-frontend/src/views/risk/popup/RiskAssessInfo.vue`, `prafta-app-frontend` risk01, 테이블 `tb_risk_assessment`(PK: CMPNY_CD,SITE_CD,PROCESS_CD,ASSESSMENT_CD), 첨부 `tb_file_info`.

---

## 1. 분리 근거 (요약)

- **모델 부정합**: `tb_risk_assessment`는 빈도×강도→위험도, 개선 전/후 재평가 구조(평가 전용). 아차사고는 발생일시·경위·잠재중대성·즉시조치·재발방지 같은 *사건 보고* 속성이 필요한데 평가 테이블엔 칸이 없다.
- **법적 성격 차이**: 위험성평가=사전 예방 평가(기록 3년 보존, 산안법 §36). 아차사고=① 산안법 §36 *수시 위험성평가*를 촉발하는 사건, ② 실제 부상 시 §57 산업재해 기록·보고로 연결. 즉 아차사고는 평가의 종류가 아니라 *입력 사건*.
- **중대재해처벌법 관점**: 중처법 §4·시행령 §4(유해·위험요인 확인·개선 절차, 종사자 의견청취). 아차사고 보고는 *종사자가 위험을 알린 증거 + 재발방지 이행 증거*. 평가에 뭉뚱그리면 "신호를 인지하고도 조사 없이 평가만 처리"한 불리한 기록이 될 수 있음. 분리·연계가 입증에 유리.

## 2. DDL — `tb_near_miss` (최소안, 단일 헤더 테이블)

```sql
CREATE TABLE `tb_near_miss` (
    `CMPNY_CD`              varchar(50)  NOT NULL COMMENT '회사코드',
    `SITE_CD`               varchar(50)  NOT NULL COMMENT '사업장코드',
    `NEAR_MISS_ID`          varchar(20)  NOT NULL COMMENT '사건 ID (사업장별 채번: NM + YYYYMMDD + SEQ)',
    `INCIDENT_TYPE_CD`      varchar(10)  NOT NULL COMMENT '사건유형[SYS061] 100:아차사고 200:경미사고 300:유해·위험요인발견',
    `PROCESS_CD`            varchar(10)           DEFAULT NULL COMMENT '공정코드[COM002]',
    `OCCUR_DTIME`           datetime     NOT NULL COMMENT '발생일시',
    `LOCATION_DESC`         varchar(200)          DEFAULT NULL COMMENT '발생장소(직접입력)',
    `DESCRIPTION`           varchar(500) NOT NULL COMMENT '사건 경위(무슨 일이 있었나)',
    `POTENTIAL_SEVERITY_CD` varchar(10)           DEFAULT NULL COMMENT '잠재적 중대성[SYS062] 100:경미 200:중대 300:치명(실제 사고였다면)',
    `IMMEDIATE_ACTION_DESC` varchar(500)          DEFAULT NULL COMMENT '즉시 조치사항',
    `CAUSE_DESC`            varchar(500)          DEFAULT NULL COMMENT '추정 원인',
    `PREVENTION_DESC`       varchar(500)          DEFAULT NULL COMMENT '재발방지 대책',
    `FILE_MGMT_CD`          varchar(50)           DEFAULT NULL COMMENT '현장 사진(tb_file_info 관리코드)',
    `REPORT_STATUS_CD`      varchar(10)  NOT NULL DEFAULT '100' COMMENT '처리상태[SYS063] 100:접수 200:검토중 300:조치중 400:완료 900:반려',
    `REPORTER_ID`           varchar(50)  NOT NULL COMMENT '보고자(tb_user.USER_CD)',
    `REPORT_DTIME`          datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '보고일시',
    `REVIEWER_ID`           varchar(50)           DEFAULT NULL COMMENT '검토 관리자(tb_user.USER_CD)',
    `REVIEW_DTIME`          datetime              DEFAULT NULL COMMENT '검토(분류)일시',
    `SRC_PROCESS_CD`        varchar(10)           DEFAULT NULL COMMENT '원 위험성평가요청 공정코드(재분류 출처)',
    `SRC_ASSESSMENT_CD`     varchar(10)           DEFAULT NULL COMMENT '원 위험성평가요청 ID(tb_risk_assessment.ASSESSMENT_CD, 재분류 출처)',
    `USE_YN`                varchar(2)   NOT NULL DEFAULT 'Y' COMMENT '사용여부',
    `INSERT_NO`             varchar(50)           DEFAULT 'SYSTEM' COMMENT '입력자',
    `INSERT_DATE`           datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '입력일시',
    `UPDATE_NO`             varchar(50)           DEFAULT NULL COMMENT '수정자',
    `UPDATE_DATE`           datetime              DEFAULT NULL COMMENT '수정일시',
    PRIMARY KEY (`CMPNY_CD`, `SITE_CD`, `NEAR_MISS_ID`),
    KEY `IX_TB_NEAR_MISS_STATUS` (`CMPNY_CD`, `SITE_CD`, `REPORT_STATUS_CD`),
    KEY `IX_TB_NEAR_MISS_REPORTER` (`CMPNY_CD`, `REPORTER_ID`),
    KEY `IX_TB_NEAR_MISS_SRC` (`CMPNY_CD`, `SITE_CD`, `SRC_PROCESS_CD`, `SRC_ASSESSMENT_CD`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='아차사고/사건 보고';
```

### 신규 시스템 코드그룹 (현재 SYS060까지 사용 → 신규 SYS061~)
`tb_syst_val_m`(그룹) + `tb_syst_val_d`(코드값)에 등록.

| 그룹 | 그룹명 | 코드값 |
|---|---|---|
| **SYS061** | 사건유형 | 100 아차사고 / 200 경미사고 / 300 유해·위험요인발견 |
| **SYS062** | 잠재적 중대성 | 100 경미 / 200 중대 / 300 치명 |
| **SYS063** | 사건 처리상태 | 100 접수 / 200 검토중 / 300 조치중 / 400 완료 / 900 반려 |

### 확장 여지 (최소안에서 제외)
- 후속 수시평가 연계 키 `LINK_PROCESS_CD/LINK_ASSESSMENT_CD`(출처 `SRC_*`와 방향 반대라 분리).
- 목격자/관계자 다건 → `tb_near_miss_witness` 자식 테이블.
- `tb_file_info`가 관리코드 1개로 다중 사진을 못 묶으면 첨부 자식 테이블.

## 3. 채널·역할 매트릭스 (앱 vs 웹) — 권고: **하이브리드**

> 질문("앱에서 올리고 관리자는 웹에서만? 앱에서도?")에 대한 권고. 단일 채널보다 역할별 분담이 현실적.

| 행위 | 근로자(앱) | 현장/안전관리자(앱) | 관리자(웹) | 비고 |
|---|:---:|:---:|:---:|---|
| 아차사고 직접 보고 | ● | ● | ○ | 근로자 주 채널은 앱 |
| 위험성평가요청 → 아차사고 재분류 | | | ● | RiskAssessInfo에서 전환 |
| 1차 확인 / 접수→검토중 / 임시조치 메모 | | ● | ● | 현장 즉시성 → 앱 허용 |
| 정밀 조사(원인·재발방지) / 완결 | | △(간단) | ● | 텍스트·첨부 많음 → 웹 중심 |
| 수시 위험성평가 생성·연계 | | | ● | 평가 도메인 연결 |
| 통계·이행점검(중처법 대응) | | | ● | 경영책임자 라인 |
| 중대성 높은 건 푸시 알림 | | ● | ● | tb_noti_outbox 재사용 |

**설계 의도**
- **즉시성(앱)**: 아차사고는 "지금 위험을 봤다"가 핵심. 보고·1차 인지·임시조치는 현장에서 폰으로 즉시.
- **깊이(웹)**: 원인분석·재발방지·평가 연계·통계는 입력량이 많고 책임 기록이라 PC(웹)가 적합.
- 앱 관리자 기능은 "읽기 + 상태 전환 + 짧은 메모"로 한정하고, 본격 조사 폼은 웹 전용으로 두어 데이터 품질·책임 추적을 확보.

## 4. 서비스 시나리오

### 4-A. 기본 플로우 (근로자 앱 직접 보고)
1. **보고(근로자/앱)** — 작업자가 지게차 후진 충돌 위험을 목격. 앱 "아차사고 보고"에서 유형=아차사고, 발생일시, 장소(3공정), 경위, 잠재중대성=중대, 사진, 즉시조치(후진경보 점검 요청)를 입력 → 제출.
   - `INSERT tb_near_miss` (`REPORT_STATUS_CD='100'(접수)`, `REPORTER_ID`=본인, `SRC_*`=NULL).
2. **알림** — 잠재중대성≥중대면 사업장 안전관리자에게 푸시(`tb_noti_outbox` 재사용). 경미는 목록 배지만.
3. **1차 확인(관리자/앱)** — 안전관리자가 앱 목록에서 건을 열어 경위·사진 확인, 임시조치 메모 입력, `접수→검토중(200)` 전환. (`REVIEWER_ID/REVIEW_DTIME` 기록)
4. **정밀 조사(관리자/웹)** — 관리자가 웹 "사건 관리"에서 추정원인·재발방지대책 입력, `검토중→조치중(300)`.
5. **(선택) 수시 위험성평가 연계** — 재발방지로 평가가 필요하면 웹에서 "수시 위험성평가 생성" → `tb_risk_assessment` INSERT, 생성된 키를 (확장) `LINK_*`에 기록해 추적 체인 완성.
6. **완결(관리자/웹)** — 재발방지 조치 완료 확인 후 `조치중→완료(400)`. 보존(물리삭제 금지, `USE_YN`).
7. **통계** — 사업장별 아차사고 건수/유형/잠재중대성 분포를 안전 선행지표로 집계(중처법 이행점검 근거).

### 4-B. 분기: 위험성평가요청 → 아차사고 재분류
1. 근로자가 앱에서 일반 "위험요인"을 올려 `tb_risk_assessment` 접수.
2. 관리자가 웹 `RiskAssessInfo`에서 검토 중 "이건 아차사고다" 판단 → **[아차사고로 전환]** 액션.
   - `INSERT tb_near_miss` 하면서 `SRC_PROCESS_CD/SRC_ASSESSMENT_CD`에 원 평가건 키 기록(출처 연결).
   - 원 `tb_risk_assessment` 건은 상태를 "아차사고로 이관"으로 닫음(또는 `USE_YN='N'`) — 이중 관리 방지.
3. 이후 4-A의 4단계(정밀 조사)부터 동일.

### 4-C. 분기: 실제 부상이 있는 경미사고
- `INCIDENT_TYPE_CD=200(경미사고)`처럼 실제 부상이 있으면 산안법 §57 산업재해 기록·보고 의무 영역과 겹침.
- 이 분기에서는 웹에 **"산업재해 보고 대상 여부 체크"** 게이트를 띄워, 산업재해조사표 등 별도 의무 이행을 누락하지 않도록 안내(본 도메인은 보고/조사 추적, 법정 신고 자체는 별도 절차).

### 상태 전이 (SYS063)
```
[100 접수] ──확인──▶ [200 검토중] ──조사착수──▶ [300 조치중] ──완료──▶ [400 완료]
     │                    │                          │
     └──반려(900)─────────┴──────────────────────────┘   (오접수/중복/평가건이 맞음 등)
```
- 접수→검토중: 앱/웹 관리자
- 검토중→조치중→완료: 웹 관리자(정밀 조사 동반)
- 반려: 어느 단계든 사유 입력 후 가능

## 6. API 개략 (앱 완전분리 원칙 — app-010 참조)
- **앱(근로자/관리자)**: `/appApi/nearmiss/*` (보고 등록, 내 보고 목록, 사업장 목록[권한], 상세, 상태전환). 앱 백엔드 `com.prafta.app.nearmiss.*` 신규(web 호출 금지).
- **웹(관리자)**: `/web` 별도 컨트롤러(목록·정밀조사·완결·위험성평가 연계·통계).
- 식별자(cmpnyCd/userCd/siteCd)는 JWT 클레임에서만 도출, 사업장 스코프·관리노드 권한 가드 필수(IDOR 차단).

## 7. 결정 필요 사항
1. 앱 관리자 조치 범위: "상태전환+임시조치"까지만 vs 재발방지까지(권고: 전자, 정밀조사는 웹).
2. 재분류 시 원 `tb_risk_assessment` 처리: 상태 "이관"으로 닫기 vs `USE_YN='N'`(권고: 이관 상태값 신설로 추적 보존).
3. 잠재중대성 표현: 코드 3등급(본안) vs 위험성평가식 점수(빈도×강도) — 아차사고는 단일 등급이 단순·적합.
4. 경미사고(실부상) 산업재해 보고 게이트를 본 도메인에 포함할지/별도 안내만 할지.
5. 보존기간 정책: 위험성평가 3년 기조 적용(권고) — 물리삭제 금지 확정.
