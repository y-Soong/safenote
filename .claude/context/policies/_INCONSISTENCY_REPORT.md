## B. 정책서 ↔ 기술 정책서 불일치 (즉시 조치 필요)

### B-1. ★ JWT 토큰 만료 시간 (Critical)

| 출처 | Access Token | Refresh Token |
| --- | --- | --- |
| 공통 정책서 §3.4 | **1시간** | **48시간** |
| `security.md` §8 (prafta 컨텍스트) | 30분 | 14일 |

**문제**: 두 곳이 완전히 다른 값을 말한다. security 에이전트는 1시간을 초과하면 High로 올려야 하는지 30분을 초과하면 High로 올려야 하는지 모호함.

**현재 코드 영향 추정**: 코드에 어느 쪽 값이 박혀 있는지 모름. `application.properties` 또는 `JwtUtil`을 사용자가 직접 확인 필요.

**권고**:
- 사용자가 비즈니스 정책 기준(1시간 / 48시간)을 확정한다는 입장이면, security.md §8을 정책서에 맞춰 수정 (위에서 제안한 수정안 반영).
- 다른 값으로 운영 중이면 공통 정책서를 docx에서 갱신.
- **확정 전까지 신규 인증 작업 시 어느 쪽도 단정 짓지 않는다.**

### B-2. PII 컬럼 목록 (Medium)

| 출처 | PII 컬럼 |
| --- | --- |
| 공통 §3.1 회원가입 필수 입력 | 회사코드, 아이디, 비밀번호, 이름, 휴대폰, 사업장, 생년월일 |
| 공통 §3.1 선택 입력 | 이메일, 성별 |
| `security.md` §3 (알려진 PII) | mblNo, email, userNm (RRN은 별도 확인) |

**문제**: 공통 정책서에 "생년월일"이 필수 입력으로 명시되어 있으나, security.md의 PII 점검 대상에 포함되어 있지 않음. 한국 개인정보보호법상 생년월일은 PII에 해당.

**권고**: security.md §3 PII 컬럼 목록에 `birthDate`(또는 실제 DB 컬럼명) 추가. AES-GCM 암호화 + HMAC 검색 컬럼 대상에 포함 여부 확인 필요.

### B-3. 감사 로그 대상 (Medium)

| 출처 | 감사 로그 대상 |
| --- | --- |
| 공통 §11.3 | 권한 변경, 사업장 권한 변경, 조직 구조 변경(노드 생성/삭제, 담당 정/부 지정), 사용자 상태 변경, 다운로드, 상세 위치 조회, 중요 데이터 삭제, **일일계정관리 화면 액션**(점유 유지 ON/OFF, 슬롯 비우기, 최대 슬롯 수 변경, 계정 등록 토글) |
| `security.md` | 감사 로그 명시 항목 없음 (Critical/High 점검 포인트만 존재) |
| `qa.md` 5(e) | "삭제 항목 통계 반영" 정도만 간접 언급 |

**문제**: 비즈니스 정책서가 감사 로그를 명시적으로 요구하지만, 기술 정책서에는 점검 항목이 없음. 신규 작업에서 감사 로그가 누락되어도 security/qa가 잡지 못함.

**권고**: security.md에 다음 점검 포인트 추가:
- 공통 §11.3 명시 행위 코드에 감사 로그 기록 누락 → **High**
- 감사 로그 기록은 있으나 "누가/언제/무엇을/왜" 4요소 누락 → **Medium**

### B-4. 일일계정 슬롯 데이터 모델 (Low — 단순 표기 불일치)

| 출처 | slotKind 값 |
| --- | --- |
| 공통 §5.4 | `self` / `qr` (내부 코드) |
| 공통 §5.5.2 | `slotKind` 컬럼명 명시, 값 `self` / `qr` |
| `developer.md` | 슬롯 관련 직접 언급 없음 (DTO 명명 규칙만 존재) |

**현재 운영**: 코드에 이미 이 컬럼이 있다면 정책서와 일치하는지 확인. memory에 따르면 `TB_DAILY_USER_SLOT` 테이블이 존재하므로 컬럼명 검증 필요.

**권고**: DB 스키마(`schema-full.sql`)와 정책서 §5.4/§5.5.2의 슬롯 구성 요소가 일치하는지 사용자가 1회 검증.

## C. 정책서 내부 모호성 (개정 권고)

### C-1. 근태 §6.6 "1일 2구간 제한" vs §1.4 핵심 운영 원칙

| 출처 | 내용 |
| --- | --- |
| 근태 §1.4 | "1일 최대 **2구간 근무, 1일 최대 2회 출근 제한**" |
| 근태 §6.6 | "1일 2구간 제한" (제목만, 본문 별도 확인 필요) |

두 표현이 의미하는 바가 같은지, 아니면 "2구간"과 "2회 출근"이 별개 개념인지 본문에서 더 명확히 할 필요. 신규 작업 시 사용자에게 의미 확인 후 진행.

### C-2. GPS 미확인 처리 책임 분담

| 출처 | 내용 |
| --- | --- |
| 공통 §6.2, §11.2 | "GPS 미확인은 등록은 허용하되 확인 필요 상태로 관리" |
| 근태 §7.3 | (별도 정독 필요) |

공통 정책서는 "근태 정책서 참조"라고만 적혀 있고, 근태 §7.3에 실제 처리 흐름이 있다. 두 정책서가 같은 말을 하고 있는지 사용자 1회 검증 권고.

## E. 향후 정책서 운영 권고

1. **docx 원본 갱신 시 항상 분할 .md 재갱신**: 사용자가 docx만 수정하면 .md는 stale. 갱신 스크립트(`.claude/migrations/sync-policies.sh`) 도입 권고.
2. **정책서에 코드 식별자 명시 권장**: 정책서 본문에 "slotKind", "userCd", "ACCOUNT_STATUS" 같은 코드 컬럼명을 명시적으로 적으면 코드↔정책서 매핑이 쉬워진다.
3. **버전 표기 일관성**: docx 파일명 표기 통일 (`v1.1` vs `v1_1` 등 혼재).
4. **단일 출처 선언 확산**: 재기획서 §1.2 같은 "단일 출처 선언" 패턴을 다른 정책서에도 도입하면 충돌 해소가 깔끔.
