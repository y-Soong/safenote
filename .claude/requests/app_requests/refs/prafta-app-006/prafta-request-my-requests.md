## 1. 개요

### 1.1 배경
PRAFTA 모바일 앱에서 사용자가 **본인이 등록한 4종 근태 요청**(스케줄 수정·근태 보정·초과근무·연차)의 전체 이력을 단일 리스트로 조회할 수 있는 화면을 신규로 구축한다.

기존에는 사용자가 요청을 등록한 뒤 처리 결과를 확인할 통합 화면이 없어, 메인 홈의 "승인 요청 N건 대기" KPI를 통해서만 처리 상태를 인지할 수 있었다. 본 화면은 등록 후 처리 흐름을 사용자가 직접 추적할 수 있는 단일 진입점이 된다.

핵심 설계 원칙:
- **대기 우선 정렬 기본값**: 사용자가 가장 먼저 확인해야 할 것은 본인이 처리를 기다리는 건. 진입 즉시 처리 대기 건이 상단에 노출된다.
- **3종 다중 필터 + 독립 정렬**: 상태·기간·유형의 3종 필터 트리거를 가로 배치, 각 트리거 탭 시 전용 바텀시트 노출. 정렬은 별도 우상단 버튼으로 분리. 다중 필터를 가진 모바일 화면의 표준 패턴 사용.
- **상태만 컬러 시그널**: 카드 시각 정보는 상태(대기·승인·반려) 색상에만 컬러 사용. 신청 유형은 텍스트로만 표시하여 카드 상단의 시각 충돌 제거.
- **절대 날짜 표기**: 상대시간("3일 전") 대신 절대 날짜("2026년 5월 22일")로 통일. 처리 완료 건은 요청·처리일자 모두 노출, 대기 건은 요청일자만.
- **관리자 화면 정보 구조 재사용**: 웹 관리자의 "요청 승인 관리" 화면의 핵심 정보 항목을 모바일 단일 스크롤 카드 리스트로 변환.

### 1.2 화면 위치
- **앱 네비게이션**: 메인 홈 화면 → 근태 조회 카드 → "승인 요청" KPI 카드 클릭 → 본 화면
- **추가 진입점**: 알림 센터의 요청 처리 결과 알림 → 본 화면 또는 요청 상세
- **파일 위치**: `prafta-web-frontend/src/views/req/MyRequestsView.vue`

### 1.3 화면 구성
1. **서브 헤더** (56px): 좌측 백 버튼 + 중앙 "내 승인 요청" 타이틀
2. **필터 영역**:
   - 상단 행: 좌측 총 건수 + (필터 적용 시) 필터 N 태그 / 우측 정렬 버튼
   - 하단 행: 3종 필터 트리거 (상태 / 기간 / 유형) 가로 스크롤 + (활성 시) 초기화 버튼
3. **리스트 영역**: 요청 카드 세로 배치 (카드 간 10px 간격)
4. **요청 카드** 1개당:
   - 상단: 좌측 유형 텍스트 / 우측 상태 배지
   - 본문 1행: 대상일자
   - 본문 2행~: 요청 내용 요약
   - (반려 시) 회색 톤 반려 사유 인라인 박스
   - 하단 메타: 좌측 요청·처리 절대 일자 / 우측 "자세히 >" 진입

### 1.4 시안 파일
구체적 UI는 `prafta_my_requests.html` 참조. 총 7개 화면 케이스를 담고 있다:
1. **기본 — 필터 미적용**: 대기 3건 + 승인 1건 + 반려 1건 혼재
2. **필터 3종 적용 후**: 상태 2개 + 기간 + 유형 2개 → 필터 결과 2건. 트리거 모두 활성 + 초기화 버튼 노출
3. **상태 필터 바텀시트**: 다중 선택 체크박스 (대기 / 승인 / 반려). 푸터 [초기화 / N개 선택 적용]
4. **기간 필터 바텀시트**: 프리셋 칩(최근 7일·30일·3개월·올해) + from~to 직접 입력
5. **유형 필터 바텀시트**: 다중 선택 체크박스 (스케줄 수정 / 근태 보정 / 초과근무 / 연차)
6. **정렬 옵션 바텀시트**: 라디오 단일 선택 (대기 우선 / 최근 요청순 / 대상일자 가까운순)
7. **필터 적용 후 빈 상태**: 회색 원형 + inbox 아이콘 + "선택한 조건의 요청이 없어요"

## 2. 핵심 정보 모델

### 2.1 요청 유형 4종

본 화면에서 노출하는 요청 유형은 `prafta-request-attendance-forms.md` §3에서 정의한 4종과 동일하다.

| 유형 | REQ_TYPE | 표시 방식 | 등록 화면 |
|---|---|---|---|
| **스케줄 수정** | `SCHED_MODIFY` | Secondary 컬러 텍스트 (`#6B7280`, 13/500) | `AttdScheduleModifyForm.vue` |
| **근태 보정** | `ATTD_MODIFY` | 동일 | `AttdCorrectionForm.vue` |
| **초과근무** | `OT_REGISTER` | 동일 | `AttdOvertimeForm.vue` |
| **연차** | `LEAVE_REQUEST` | 동일 | `AttdLeaveForm.vue` |

**시각 톤 부여 정책**: 유형 4종은 **컬러 칩이 아닌 단순 텍스트**로만 표시한다. 이는 상태 배지(대기·승인·반려)의 컬러 시그널과 충돌을 방지하기 위함이다. 카드 상단에서 유일한 컬러 정보는 상태 배지이며, 유형은 보조 정보로 텍스트만 노출한다.

### 2.2 요청 상태 4종

`tb_user_attd_req.REQ_STATUS` 컬럼 값에 따라 카드 우상단 상태 배지가 결정된다.

| 상태 | REQ_STATUS | 배지 색상 | 의미 |
|---|---|---|---|
| **대기** | `REQUESTED` | Warning (Orange) | 관리자 처리 대기 중. 사용자 액션 없음 |
| **승인** | `APPROVED` | Primary (Green) | 관리자가 승인 처리함. 근태/스케줄에 반영됨 |
| **반려** | `REJECTED` | Danger (Red) | 관리자가 반려함. 회색 톤 반려 사유 인라인 노출 |
| **취소** | `CANCELED` | Neutral (Gray) | 사용자가 본인 요청을 취소함 (대기 상태에서만 가능) |

배지 구조: tint 배경 + dot(6px) + 라벨 + 배지 텍스트 색. 색상으로만 정보 전달하지 않도록 dot + 라벨 텍스트 3중 표현.

**[정책 확정 필요]** 사용자가 본인 대기 요청을 취소할 수 있는지 여부. 현재 정책서에 명시되어 있지 않다면 본 화면에서는 취소 액션 미구현하고 상태값만 표현하도록 처리 — 7.2 질문 사항 참조.

### 2.3 카드 본문 표시 규칙 (유형별)

요청 등록 시 사용자가 입력한 정보를 요약 표시한다.

#### 2.3.1 스케줄 수정

- **대상일자**: `2026-05-25 (월)`
- **요청 내용**: `{현재 근무명} → {변경 근무명}` (예: `ST001 정규근무 → ST002 야간근무`)
- 2구간 스케줄의 경우 1구간/2구간 각각 1줄씩 총 2줄: 첫 줄 `1구간 ST001 → ST003`, 둘째 줄 `2구간 ST002 → ST004`

#### 2.3.2 근태 보정

- **대상일자**: `2026-05-18 (월)`
- **요청 내용**: **1구간이면 1줄**, **1+2구간 보정이면 구간별 1줄씩 총 2줄**
  - 1구간 케이스 1줄 형식: `출근 09:00 → 08:30 / 퇴근 18:00 (변경 없음)`
  - 1+2구간 케이스 2줄 형식:
    - `1구간: 출근 09:00 → 08:30 / 퇴근 13:00 (변경 없음)`
    - `2구간: 출근 14:00 → 14:30 / 퇴근 22:00 (변경 없음)`
- 변경 없는 항목은 `(변경 없음)` 회색으로 표시
- 구분자는 ` / `(공백 + 슬래시 + 공백)로 통일

#### 2.3.3 초과근무

- **대상일자**: `2026-05-19 (화)`
- **요청 내용**: `{구간} {시작} → {종료} ({합계})` (예: `1구간 18:00 → 19:30 (1시간 30분)`)
- 1+2구간 동시 신청 시 2줄로 표시

#### 2.3.4 연차

- **대상일자**: `2026-05-29 (금)` (시작일자 기준)
- **요청 내용**: `{사용 단위} · {연차 종류}` (예: `하루 · 연차`, `반차 (앞) · 연차`, `2시간 (14:00~16:00) · 가족돌봄휴가`)
- 다일 연차의 경우 대상일자에 시작~종료 표시: `2026-05-29 (금) ~ 2026-05-31 (일)` / 요청 내용 `3일 · 연차`

### 2.4 카드 하단 메타 — 날짜 표기 규칙

상대시간("X일 전") 표현은 사용하지 않는다. 절대 날짜로 통일한다.

| 상태 | 메타 표시 형식 | 예시 |
|---|---|---|
| **대기** | `YYYY년 M월 D일 요청` (요청일자만) | `2026년 5월 22일 요청` |
| **승인** | `YYYY년 M월 D일 요청 / YYYY년 M월 D일 승인` | `2026년 5월 14일 요청 / 2026년 5월 15일 승인` |
| **반려** | `YYYY년 M월 D일 요청 / YYYY년 M월 D일 반려` | `2026년 5월 12일 요청 / 2026년 5월 13일 반려` |
| **취소** | `YYYY년 M월 D일 요청 / YYYY년 M월 D일 취소` | 동일 패턴 |

- 처리일자가 없는 (대기) 건은 `/` 뒤를 생략하고 요청일자만 노출
- 폰트 12/400, Tertiary 컬러 (`--color-text-tertiary`)

### 2.5 반려 사유 표시

- 상태가 `REJECTED`인 카드만 본문 아래에 인라인 박스로 반려 사유 노출
- 박스 스타일: **회색 톤 배경** (`--color-bg`, `#F9FAFB`) + Secondary 컬러 텍스트 (`#6B7280`)
- "반려 사유" 라벨은 Primary text 컬러 + 500 weight로 강조
- 구분자: `·`
- 형식: `<span class="label">반려 사유</span> · {사유 본문}`
- 박스 라운드 8px, 패딩 8px 10px, 폰트 12/400, line-height 17px
- 사유 텍스트는 카드 안에서 전문 노출 (line-clamp 사용 안 함). `tb_user_attd_req.REJECT_REASON` 컬럼 값 그대로

**시각 강조 제외 결정 근거**: Danger tint 배경(붉은 톤)은 카드 우측 상태 배지의 Danger와 시각적으로 중복되어 강조 효과가 떨어지고, 회색 톤으로 분리하면 상태 배지의 컬러 시그널을 보존하면서 정보 위계도 명확해진다.

## 3. 비즈니스 규칙 (정책서 출처 명시)

### 3.1 정렬 정책

#### 3.1.1 3가지 정렬 옵션

| 옵션 | 정렬 키 | 기본값 여부 |
|---|---|:---:|
| **대기 우선** | REQ_STATUS = REQUESTED 우선 → 그 외는 REQ_DATETIME DESC | ✓ 기본 |
| **최근 요청순** | REQ_DATETIME DESC | |
| **대상일자 가까운순** | TARGET_YMD 오름차순 (오늘 가까운 순 = 오늘 기준 ABS(TARGET_YMD - TODAY) ASC) | |

이전 검토 단계에서 거론되었던 "처리 결과순" 옵션은 사용자 합의로 제외했다 (대기 우선 정렬과 의미 중복).

#### 3.1.2 대기 우선 정렬의 세부 동작

진입 시 기본값. 다음 순서로 정렬:
1. `REQ_STATUS = 'REQUESTED'` 건 (대기) 상단
2. 대기 건 내부에서는 요청 일시 최신순 (REQ_DATETIME DESC)
3. 대기 외 건은 모두 그 아래에 요청 일시 최신순으로 배치

**[정책 확정 필요]** 대기 외 건의 정렬 기준 — 7.3 질문 사항 참조.

#### 3.1.3 정렬 UI

- 우상단 정렬 버튼: 현재 정렬명 + 아래 chevron (`sort-btn` 클래스 참조)
- 탭 시 바텀시트 호출 (가이드 §4.9.2)
- 바텀시트 구성: 핸들 + "정렬" 타이틀 + 닫기(X) / 3개 옵션 / 현재 선택 항목 우측에 채워진 라디오 표시
- 옵션 선택 시 즉시 적용 + 바텀시트 자동 닫힘
- 라디오 단일 선택 패턴 (다중 선택 아님)

### 3.2 다중 필터 정책 — 3종 필터 트리거

3종 필터(상태 / 기간 / 유형)를 가로 배치된 트리거 칩으로 노출하고, 각 트리거 탭 시 전용 바텀시트가 열린다.

#### 3.2.1 트리거 칩 공통 규격

- 캡슐형 (높이 32px, padding 0 8px 0 12px)
- 비활성 상태: 흰 배경 + 0.5px 보더 + Secondary 텍스트
- 활성 상태: Primary tint 배경 + Primary tint 보더 + Primary 텍스트
- 우측에 chevron-down 아이콘 (14×14px)
- 다중 선택 트리거(상태/유형): 활성 시 좌측에 선택 개수 배지 (Primary 채움, 흰 글씨)
- 기간 트리거: 값이 짧으면 직접 표시(`5/1 ~ 5/24`), 값이 없을 때는 "기간"만

#### 3.2.2 상태 필터 (다중 선택)

- 옵션 3개: 대기 / 승인 / 반려 (취소 상태는 정책 확정 후 추가)
- 각 옵션은 좌측 dot + 라벨 형식 (상태 컬러 시각 단서 유지)
- 체크박스 다중 선택
- 푸터: [초기화] (회색 보더) + [N개 선택 적용] (Primary)
- "0개 선택 적용"은 비활성. 최소 1개 이상 선택해야 적용 가능 (전체 해제 = 필터 미적용)

#### 3.2.3 기간 필터 (from-to 범위)

- 기준 일자: `tb_user_attd_req.REQ_DATETIME`의 날짜 부분 (= 요청한 시점의 일자)
- 프리셋 칩 4개: 최근 7일 / 최근 30일 / 최근 3개월 / 올해
- 프리셋 클릭 시 from-to 인풋 자동 채움
- from-to 인풋: 일자 셀렉터 호출 (기존 prafta 일자 셀렉터 패턴 따름)
- 적용 후 트리거 라벨: `M/D ~ M/D` 형식 요약 표시 (월·일만, 연도 생략)
- **[정책 확정 필요]** 기간 기준이 요청일인지 대상일인지 — 7.4 질문 사항 참조

#### 3.2.4 유형 필터 (다중 선택)

- 옵션 4개: 스케줄 수정 / 근태 보정 / 초과근무 / 연차
- 각 옵션은 텍스트만 표시 (컬러 칩 사용 안 함 — §2.1 동일 원칙)
- 체크박스 다중 선택
- 푸터 패턴은 상태 필터와 동일

#### 3.2.5 필터 적용 표시

- 1개 이상의 필터가 활성일 때:
  - 상단 행의 총 건수 옆에 `필터 N` 태그 노출 (N = 활성 필터 개수)
  - 트리거 행 끝에 **초기화 버튼** 노출 (`X 초기화`, 텍스트 + X 아이콘)
- 초기화 버튼 클릭 시 3종 필터 모두 리셋 + 트리거 모두 비활성 상태로 복귀

#### 3.2.6 필터·정렬 간 독립성

- 필터와 정렬은 서로 독립적으로 적용된다
- 필터 변경 시 정렬값은 유지된다 (예: "대상일자 가까운순" 정렬 + "상태=대기" 필터 동시 가능)
- 초기화 버튼은 필터만 리셋, 정렬은 영향받지 않음

### 3.3 빈 상태 처리

3가지 빈 상태 케이스가 존재한다:

| 케이스 | 메시지 | 보조 텍스트 |
|---|---|---|
| 전체 요청이 0건 (사용자가 한 번도 요청한 적 없음) | "아직 등록한 요청이 없어요" | "근태 화면에서 요청을 등록할 수 있어요" |
| 필터링 후 0건 | "선택한 조건의 요청이 없어요" | "필터를 변경해 보세요" |
| 검색 후 0건 (검색 도입 시) | "검색 결과가 없어요" | "다른 키워드로 검색해 보세요" |

빈 상태 일러스트: 회색 원형 배경 (56×56px) + inbox 아이콘 (Tertiary 컬러) → 메시지 → 보조 텍스트 순. 가이드 §9.3 빈 상태 패턴 준수.

### 3.4 자세히 보기 진입

- 카드 우하단 "자세히 >" 또는 카드 전체 탭 시 해당 요청의 상세 화면으로 이동
- 상세 화면은 별도 작업 (본 화면 범위 외)
- 상세 화면에서는 등록 시 입력한 모든 필드 + 처리 이력 타임라인 + (대기 상태이고 정책상 허용 시) 취소 액션 노출

**[정책 확정 필요]** 요청 상세 화면이 별도 화면인지, 본 화면에서 카드 인라인 확장인지 — 7.5 질문 사항 참조. 본 작업 요청서는 별도 화면 가정.

### 3.5 데이터 범위

#### 3.5.1 조회 범위

- 본인이 등록한 요청만 (`tb_user_attd_req.USER_CD = 현재 사용자`)
- 4종 REQ_TYPE 모두 포함 (`SCHED_MODIFY`, `ATTD_MODIFY`, `OT_REGISTER`, `LEAVE_REQUEST`)
- 본인 소속 사업장 기준 (`tb_user_attd_req.SITE_CD` 자동 일치)

#### 3.5.2 보존 기간

- 별도 만료 정책 없음 (전체 이력 노출)
- **[정책 확정 필요]** 1년 또는 6개월 이전 건은 별도 화면(보관함)으로 이동시킬지, 메인 리스트에 모두 노출할지 — 7.6 질문 사항 참조

#### 3.5.3 페이지네이션

- 무한 스크롤 또는 페이지네이션 적용 — **[정책 확정 필요]** 7.7 질문 사항 참조
- 기본 가정: 무한 스크롤 (한 번에 20건 로드)

### 3.6 메인 홈의 "승인 요청 N건 대기" 일치

메인 홈 화면(`prafta-request-home.md` §3.3.2)의 KPI 수치와 본 화면의 "대기" 상태 건수는 **항상 일치**해야 한다. 두 화면은 동일한 데이터셋(`REQ_STATUS = 'REQUESTED'` AND `USER_CD = 현재 사용자`)을 표시한다.

본 화면 진입 후 사용자가 요청을 취소하거나(허용 시) 관리자가 처리하여 상태가 변경되면, 메인 홈의 KPI 카운트도 갱신되어야 한다 (실시간 또는 메인 진입 시 재호출).

## 6. DB 구조 검토 및 추가 작업 필요 사항

### 6.1 `tb_user_attd_req` 컬럼 확장 — `REJECT_REASON`

- 현재 컬럼 확인 필요. 반려 사유를 저장할 텍스트 컬럼이 없다면 `REJECT_REASON varchar(500)` 추가
- 관리자 화면의 결재 처리 시 입력한 반려 사유가 이 컬럼에 저장되어야 함

### 6.2 `CANCELED` 상태값 신규 추가

- 현재 `REQ_STATUS` 컬럼이 enum 형식인지 자유 텍스트인지 확인
- enum 또는 공통코드라면 `CANCELED` 신규 추가 필요
- **[정책 확정 후 적용]** 사용자 취소 기능 도입 여부에 따라 결정 — 7.2 질문 사항

### 6.3 `tb_user_attd_req.PROCESSED_AT` 컬럼

- 관리자가 처리한 일시를 저장할 컬럼이 있는지 확인
- 없다면 `PROCESSED_AT datetime` 추가
- 메타 영역의 "YYYY년 M월 D일 승인/반려" 표시에 사용

### 6.4 REQ_TYPE에 SCHED_MODIFY 추가 (선행 작업과 동일)

- `prafta-request-attendance-forms.md` §6.1과 동일 요구사항
- 본 화면이 SCHED_MODIFY 유형을 노출하려면 등록 측에서 먼저 신규 코드가 정의되어 있어야 함
- 선행 작업으로 처리됨을 가정

## 7. 정책서 출처 확인 필요 사항 (planner 작업)

planner가 `.claude/context/policies/INDEX.md`를 매핑하여 출처를 확정해야 할 항목:

| # | 항목 | 본 시안의 가정 | 정책서 확인 필요 |
|---|---|---|---|
| 7.1 | 유형 텍스트 표시 결정 | 컬러 칩 없이 텍스트만 (상태 색상과 시각 충돌 회피) | 디자인 가이드 또는 정책서에 유형 시각 표현 규칙이 별도 정의되어 있는지 |
| 7.2 | 사용자 취소 가능 여부 | 본 화면은 취소 액션 미구현, 상태값(CANCELED)만 표현 가능하도록 둠 | 대기 상태 요청을 사용자가 직접 취소할 수 있는지. 가능 시 취소 가능 기한·조건 |
| 7.3 | 대기 외 건의 정렬 기준 | "대기 우선" 정렬에서 대기 외 건은 요청 일시 최신순 (REQ_DATETIME DESC) | 처리 일시(PROCESSED_AT) 기준 정렬이 더 적절한지 |
| 7.4 | 기간 필터의 기준 일자 | 요청일자(REQ_DATETIME) 기준 | 대상일자(TARGET_YMD) 기준이 더 적절한지, 또는 두 가지 옵션을 제공할지 |
| 7.5 | 요청 상세 화면 | 별도 화면으로 진입 | 카드 인라인 확장 패턴 vs 별도 화면. 별도 화면이라면 별도 작업 요청서 분리 필요 |
| 7.6 | 요청 데이터 보존 기간 | 만료 없이 전체 이력 노출 | 1년·6개월 이전 건의 보관함 분리 필요 여부 |
| 7.7 | 페이지네이션 방식 | 무한 스크롤 20건씩 | 페이지네이션 또는 무한 스크롤. limit 값 정책 |
| 7.8 | 메인 홈 카운트 갱신 시점 | 본 화면에서 상태 변경 후 메인 진입 시 재호출 | 실시간 갱신(WebSocket 등)이 필요한지, 폴링·재호출로 충분한지 |
| 7.9 | 알림 진입 동선 | 처리 결과 알림 → 본 화면 또는 요청 상세 직접 진입 | 알림 클릭 시 진입 위치(목록/상세) 정책 |
| 7.10 | 반려 후 재요청 흐름 | 본 화면에서 별도 처리 없음 (사용자가 직접 등록 화면에서 새 요청 등록) | 반려 건에서 "재요청" 액션을 제공할지, 새 요청과 동일하게 처리할지 |
| 7.11 | 다중 선택 필터의 빈 선택 처리 | 전체 해제 = 필터 미적용으로 처리 ("0개 선택 적용" 버튼은 비활성) | 정책서에 명시 또는 본 작업으로 신설 |

## 8. 비기능 요구사항

### 8.1 디자인 시스템 준수
- 색상/폰트/간격은 모두 CSS 변수만 사용 (하드코딩 금지)
- 인라인 SVG 아이콘 사용 (CDN 의존 금지 — `prafta-request-attendance-forms.md` §8.2 동일 원칙)
- 모바일 first (360~414px 기준 폭)
- 터치 영역 최소 44×44px (가이드 §7.1)

### 8.2 성능
- 초기 진입 시: 단일 API 호출 (§5.1) 으로 첫 페이지 20건 일괄 로드
- 무한 스크롤 시: 다음 페이지만 증분 로드
- 필터 변경 시: 백엔드 재호출 (offset=0부터 다시 로드)
- 정렬 변경 시: 백엔드 재호출
- 필터·정렬 조합은 모두 백엔드 측에서 처리. 클라이언트 측 필터링·정렬 없음

### 8.3 접근성
- 색상 단독 의존 금지: 상태는 dot + 라벨 + 색상 3중
- 모든 아이콘 버튼에 aria-label
- 시간·날짜 표시는 `tabular-nums` 적용으로 정렬 일관성
- 바텀시트는 ESC 키 또는 dimmer 탭으로 닫기 가능 (모바일은 핸들 바 하단 드래그)

### 8.4 에러 처리
- 네트워크 오류 / 401 / 403 / 500 등 표준 패턴 (prafta 기존 화면 패턴 따름)
- 빈 상태와 에러 상태는 구분: 에러 상태는 "다시 시도하기" 버튼 노출, 빈 상태는 액션 버튼 없음

### 8.5 카드 영역 일관성
- 모든 카드는 케이스(유형·상태)와 무관하게 동일한 구조 유지
- 반려 사유 박스는 카드 안의 선택 영역. 다른 상태에서는 해당 영역만 생략, 카드 골격은 동일
- 가이드 §9.3 평가 기준 준수

## 10. 결정 사항 요약 (시안 작성 시점)

본 시안은 사용자와의 다회 이터레이션을 통해 확정됨. 주요 결정:

1. **메인 진입점 단일화**: 메인 홈 화면 "승인 요청" KPI에서만 진입. 별도 탭 또는 메뉴 진입 없음.
2. **대기 우선 정렬 기본값**: 진입 시 처리 대기 건이 최상단. 사용자의 다음 액션 판단을 돕는다.
3. **4종 요청 통합 리스트**: 스케줄 수정·근태 보정·초과근무·연차를 단일 리스트에 통합.
4. **3종 다중 필터**: 상태(다중 선택) / 기간(from-to) / 유형(다중 선택). 가로 트리거 + 바텀시트 패턴.
5. **정렬과 필터 분리**: 정렬은 우상단 버튼, 필터는 트리거 행. 독립 작동.
6. **정렬 옵션 3개로 축소**: "처리 결과순"은 "대기 우선" 정렬과 의미 중복으로 제거.
7. **유형 텍스트 단순화**: 컬러 칩 제거하고 Secondary 텍스트로만 표시. 카드 상단에서 유일한 컬러 시그널은 **상태 배지**.
8. **절대 날짜 표기**: 상대시간("X일 전") → 절대 날짜("YYYY년 M월 D일 요청/승인/반려"). 처리일 없는 대기 건은 `/` 뒤 생략.
9. **근태 보정 한 줄 처리**: 1구간이면 1줄(`출근 ... / 퇴근 ...`), 1+2구간이면 구간별 1줄씩 2줄.
10. **반려 사유 회색 톤**: Danger tint(붉은) → Neutral 회색 톤 배경. 우측 상태 배지의 Danger와 시각 중복 방지.
11. **상태 표현 3중**: 색상 + dot + 라벨로 색맹 사용자 대응. 가이드 §7.1 준수.
12. **반려 사유 인라인 노출**: 반려 건은 카드 안에 사유 전문 노출. 별도 화면 진입 없이 즉시 다음 액션 판단 가능.
13. **다중 선택 단일 적용**: 상태·유형은 다중 선택, 정렬은 단일 선택(라디오).
14. **빈 상태 3종 구분**: 전체 0건 / 필터 0건 / 검색 0건(미래)을 메시지로 구분.
15. **취소 액션 보류**: 사용자 직접 취소 정책 확정 전까지는 상태값만 표현. 7.2 정책 확정 후 추가.
16. **관리자 화면 정보 구조 재사용**: 웹 관리자의 "요청 정보" 우측 패널 정보 항목을 모바일 카드 본문에 그대로 반영. 일관된 데이터 모델 유지.
17. **필터 초기화 버튼**: 1개 이상 필터 활성 시 자동 노출. 정렬은 영향받지 않음.
18. **기간 필터 프리셋**: 4개 프리셋(최근 7일·30일·3개월·올해) + from-to 직접 입력 병행.
