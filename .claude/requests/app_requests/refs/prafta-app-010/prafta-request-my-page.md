## 1. 개요

### 1.1 배경
PRAFTA 모바일 앱의 **사용자 마이페이지**를 신규로 구축한다. 사용자가 본인의 계정·개인정보·연차 결재선을 관리하고, 로그아웃·회원 탈퇴를 수행할 수 있는 단일 진입점이 된다.

본 작업은 다음 3가지를 포함한다:
1. **계정 정보 관리** — 개인정보 조회·수정, 비밀번호 변경
2. **연차 결재선 프리셋 관리** — `prafta-request-attendance-forms.md` v1.1 §3.4.19에서 후속 작업으로 분리된 프리셋 CRUD 화면. 본 작업으로 확정.
3. **세션 관리** — 로그아웃, 회원 탈퇴

핵심 설계 원칙:
- **수정 가능 vs 읽기 전용 명확 분리**: 소속·아이디·입사일 등 관리자 영역은 회색 톤 읽기 전용. 본인 정보(이름·연락처·생년월일·성별)는 수정 가능. 시각 톤으로 즉시 구분.
- **파괴적 액션의 시각 비중 통제**: 로그아웃은 빈번한 액션이라 풀폭 secondary 버튼으로, 회원 탈퇴는 빈도가 매우 낮으면서 되돌릴 수 없는 액션이라 작은 텍스트 링크로 처리. 카카오·토스·네이버 등 한국 모바일 앱의 보편적 패턴.
- **결재선 프리셋의 단일 진입점**: 연차 신청 폼 안에서는 "현재 신청에 쓸 결재선을 선택"만, 프리셋 자체의 CRUD는 마이페이지로 분리. 진입 동선이 두 곳으로 분산되지 않도록.
- **추가 게이트(가이드 §5.7)**: 회원 탈퇴는 확인 체크박스 + Danger 버튼의 2단 게이트. 단순 모달 한 번으로 끝나지 않도록.

### 1.3 화면 구성 (6개 화면 + 2개 모달)
1. **마이페이지 메인** (탭 진입 화면): 프로필 카드 + 메뉴 리스트 2개 그룹 + 하단 로그아웃 버튼 + 회원 탈퇴 텍스트 링크
2. **개인정보 수정** (풀스크린): 3개 그룹 (소속 정보 읽기 전용 / 기본 정보 / 연락처)
3. **비밀번호 변경** (풀스크린): 3필드 + 규칙 가이드
4. **연차 결재선 관리** (풀스크린): 프리셋 카드 리스트 + 추가 버튼
5. **프리셋 편집** (풀스크린): 이름 + 기본 토글 + 결재자 리스트 + 헤더 우측 삭제
6. **결재자 추가** (바텀시트): 검색 + 최근 사용 + 다중 선택
7. **로그아웃 확인 모달**: 단일 질문, 부가 설명 없음
8. **회원 탈퇴 확인 모달**: 사용자 호명 + 안내 콜아웃 + 확인 체크박스 + Danger 버튼

### 1.4 시안 파일
구체적 UI는 `prafta_my_page.html` 참조. 8개 화면 케이스를 단일 페이지에 가로 배치.

## 3. 비즈니스 규칙 (정책서 출처 명시)

### 3.1 마이페이지 메인

#### 3.1.1 헤더
- 좌측 정렬 타이틀: **"마이페이지"** (title-1, 22/700)
- 우측: 알림 아이콘 + 카운트 배지 (홈 헤더와 동일 컴포넌트 재사용 권장)
- 백 버튼 없음 (탭 진입 화면)

#### 3.1.2 프로필 카드
- 데이터 소스: 인증된 사용자의 `tb_user_mgmt` (USER_NM, SITE_NM, DEPT_NM)
- 사업장명·부서명은 메인 화면에서 "보기"만. 수정은 관리자만 가능 (공통 정책서 §7.2)

#### 3.1.3 하단 액션 배치 — 한국 모바일 앱 보편 패턴

```
[메뉴 리스트]
   ⋮
[로그아웃] ← 풀폭 Secondary 버튼 (48px, 좌측 아이콘 + 텍스트)
[회원 탈퇴] ← 텍스트 링크 (중앙 정렬, 13/500, tertiary, 밑줄)

PRAFTA SAFETY NOTE v1.0.0 ← 앱 버전 (caption, tertiary)
```

설계 의도:
- **로그아웃**은 사용자가 본인 의지로 자주 누를 수 있는 액션. 메뉴 리스트의 한 행으로 묻히지 않고 풀폭 버튼으로 노출.
- **회원 탈퇴**는 빈도가 매우 낮고 파괴적이므로, 의도적으로 시각 비중을 낮춰서 실수 클릭을 방지. 작은 텍스트 링크로 처리. 모달 안에서 다시 확인 게이트를 거친다.

#### 3.1.4 알림 아이콘
- 메인 홈과 동일하게 마이페이지에도 노출
- 카운트는 홈과 동일한 데이터 소스 (`/api/app/notifications/unread-count`)
- 진입 시 알림 센터로 이동 (본 작업 범위 외)

### 3.2 개인정보 수정

#### 3.2.1 화면 구성 — 3개 그룹

**그룹 1: 소속 정보 (읽기 전용)**

| 항목 | 컬럼 | 표시 형식 |
|---|---|---|
| 아이디 | `tb_user_mgmt.USER_CD` | 그대로 |
| 사업장 | `tb_user_mgmt.SITE_CD` → `tb_site_mgmt.SITE_NM` | 사업장명 |
| 소속부서 | `tb_user_mgmt.DEPT_CD` → `tb_dept_mgmt.DEPT_NM` | 부서명 |
| 입사일 | `tb_user_mgmt.HIRE_DATE` | YYYY-MM-DD |

- 모든 행은 `--color-bg` 톤 회색 배경으로 읽기 전용임을 시각화
- 섹션 라벨 우측에 안내 텍스트: "수정은 관리자 문의"
- 입사일 변경은 마스터관리자만 가능 (근태관리 정책서 §8.5.2). 본 화면에서는 변경 진입 동선 없음.

**그룹 2: 기본 정보 (수정 가능)**

| 항목 | 컬럼 | 입력 방식 | 검증 |
|---|---|---|---|
| 이름 | `tb_user_mgmt.USER_NM` | text input | 1자 이상 50자 이내, 공백만 입력 금지 |
| 성별 | `tb_user_mgmt.GENDER` | select (남성/여성) | 회원가입 시 선택 항목이므로 미설정 허용. select 옵션에 "선택 안 함" 포함 검토 (§7.2 질문 사항) |
| 생년월일 | `tb_user_mgmt.BIRTH_DATE` | date input | YYYY-MM-DD, 미래 일자 불가, 현재 기준 만 14세 이상 (§7.3 질문 사항 — 정책 확정 필요) |

**그룹 3: 연락처 (수정 가능 + 인증 필요)**

| 항목 | 컬럼 | 입력 방식 | 검증 |
|---|---|---|---|
| 휴대폰 | `tb_user_mgmt.MOBILE_NO` | tel input + [인증요청] 버튼 | 010-XXXX-XXXX 형식. **변경 시 인증 필수** |
| 인증번호 | (서버 검증 후 폐기) | text input + [확인] 버튼 | 6자리 숫자. SMS로 발송된 코드와 일치 시 변경 허용 |
| 이메일 | `tb_user_mgmt.EMAIL` | email input | RFC 5322 기본 검증. **인증 없이 변경 허용** (선택 입력 항목이므로) |

**화면 하단 메타 표시**:
- "마지막 로그인 · YYYY-MM-DD HH:MM:SS" — 정보성, 캡션 톤. 위치는 화면 최하단 중앙 정렬.

#### 3.2.2 이름 변경 정책 (확정 사항)

- **인증 없이 즉시 변경 가능**: 별도 본인 확인 절차 없음
- **변경 빈도 제한 없음**: 사용자가 횟수 제한 없이 변경 가능
- **이력 데이터 처리**:
  - 근태·안전·승인 기록의 식별 키는 `USER_CD`이므로 변경 영향 없음
  - 변경 시점 **이후** 생성되는 알림·승인 화면 등은 새 이름으로 표시
  - 변경 시점 **이전**의 알림 본문에 박힌 이름은 그대로 유지 (재계산 안 함)
- **이력 보존 불필요**: 별도 변경 이력 테이블 없이 `tb_user_mgmt.USER_NM` 단일 컬럼 UPDATE
  - 단, 공통 §11.3 감사 로그 대상은 아님 (개인 식별 정보의 자기 수정은 감사 범위 외)

#### 3.2.3 휴대폰 변경 흐름

1. 사용자가 휴대폰 input의 값을 변경 → 변경된 순간 [저장] 버튼은 disabled
2. [인증요청] 버튼 탭 → SMS 발송 + [인증요청] 버튼이 카운트다운 모드 ("재요청 60초")
3. 사용자가 인증번호 6자리 입력 + [확인] 탭 → 서버 검증
4. 검증 성공 → 인증번호 행이 success 톤으로 변경 ("인증 완료") + [저장] 버튼 활성화
5. [저장] 탭 → `tb_user_mgmt.MOBILE_NO` UPDATE
6. 검증 실패 → 인증번호 행 helper에 danger 톤 ("인증번호가 올바르지 않아요")

#### 3.2.4 이메일 변경 흐름

- 인증 없이 즉시 수정 가능. 폼 저장 시 함께 처리.
- 이메일 미입력 허용 (회원가입 시 선택 입력 — 공통 정책서 §3.1)

#### 3.2.5 푸터 액션

- [취소] Secondary: 변경 사항 폐기, 마이페이지 메인으로 복귀
- [저장] Primary: 변경 사항 일괄 저장

저장 가능 조건:
- 변경된 항목이 1개 이상 있을 것
- 휴대폰을 변경한 경우 인증이 완료되어 있을 것
- 모든 검증 통과

저장 실패 시 (예: 서버 422): 해당 필드 아래 인라인 helper에 danger 메시지 표시.

### 3.3 비밀번호 변경

#### 3.3.1 화면 구성

**입력 필드 3개**:
1. 현재 비밀번호
2. 새 비밀번호
3. 새 비밀번호 확인

**규칙 가이드 카드** (입력 필드 아래):
- 8자 이상
- 영문 대/소문자 포함
- 숫자 포함
- 특수문자 포함

각 규칙은 새 비밀번호 입력 시 실시간 충족 여부를 표시:
- 충족: Primary 컬러 체크 아이콘
- 미충족: tertiary 컬러 원 아이콘

**상단 안내 노트** (Info tint):
> 안전한 비밀번호 사용을 위해 **3개월마다** 변경을 권장합니다

(권장 사항이므로 실제 강제 변경 정책은 별도 — §7.4 질문 사항)

#### 3.3.2 검증 규칙

| 검증 | 조건 | 실패 시 메시지 |
|---|---|---|
| 현재 비밀번호 일치 | 서버 검증 (`bcrypt compare`) | "현재 비밀번호가 일치하지 않습니다" (해당 필드 아래) |
| 새 비밀번호 규칙 | 위 4개 규칙 모두 충족 | 가이드 카드에 미충족 항목 표시 |
| 새 비밀번호 일치 | 새 비밀번호 == 새 비밀번호 확인 | "비밀번호가 일치하지 않아요" (확인 필드 아래) |
| 현재 ≠ 새 | 동일 시 변경 불가 | "현재 비밀번호와 다르게 설정해 주세요" |

[변경하기] 버튼은 모든 검증 통과 시에만 활성화 (실시간).

#### 3.3.3 변경 후 처리

- 비밀번호 변경 성공 → 토스트 "비밀번호가 변경되었습니다" + 마이페이지 메인으로 복귀
- **세션 처리**: 현재 세션은 유지. 강제 재로그인 없음. (공통 정책서 §3.4에 명시된 토큰 관리 정책을 따름)
- **다른 디바이스 세션은 별도 정책** — §7.5 질문 사항

### 3.4 연차 결재선 관리 (프리셋 CRUD)

본 화면은 `prafta-request-attendance-forms.md` v1.1 §3.4.19에서 후속 작업으로 분리된 "프리셋 관리 화면"의 구현체다.

#### 3.4.1 화면 구성

```
[헤더] ← 백 + "연차 결재선 관리"

[안내 노트] (Info tint)
연차 신청 시 기본 프리셋이 자동 적용됩니다.
신청 폼에서 다른 프리셋으로 전환할 수 있어요.

[프리셋 카드 리스트]
┌───────────────────────────────────┐
│ [기본] 팀 결재선        [수정 ✎] │
│ 박지훈 → 김영수                   │
└───────────────────────────────────┘
┌───────────────────────────────────┐
│ 본부장 포함             [수정 ✎] │
│ 박지훈 → 김영수 → 이상철           │
└───────────────────────────────────┘
...

[+ 새 프리셋 추가]  ← 점선 카드 (dashed border)
```

#### 3.4.2 프리셋 카드 구성

| 영역 | 내용 |
|---|---|
| 상단 좌측 | (기본 프리셋만) "기본" Primary tint 배지 + 프리셋 이름 (body-strong) |
| 상단 우측 | [수정 ✎] 아이콘 버튼 (32×32) |
| 하단 | 결재자 이름을 "→"로 연결한 한 줄 (body-sm, secondary) |

- 카드 전체가 탭 영역 → 프리셋 편집 화면으로 이동
- [수정 ✎] 버튼도 동일 진입. 카드 우측에 시각적 진입 단서를 명시하기 위함.

#### 3.4.3 빈 상태

프리셋이 0개일 때:
- 카드 리스트 영역에 빈 상태 일러스트 + "아직 결재선이 없어요" + "연차 신청 시 결재자를 직접 지정하거나, 미리 자주 쓰는 결재선을 등록해 두세요"
- [+ 새 프리셋 추가] 버튼은 그대로 노출

**참고**: 사용자가 한 번도 연차 신청을 안 한 상태. 첫 연차 신청 시 즉석 구성하면 자동으로 '기본' 프리셋이 생성되므로 (작업지시서 §3.4.16), 일반적으로 빈 상태는 흔치 않다.

#### 3.4.4 카드 정렬

- `IS_DEFAULT = 'Y'` 우선
- 그 다음 `MOD_DATE DESC` (최근 수정 순)

#### 3.4.5 비활성 결재자가 포함된 프리셋

- 프리셋 멤버 중 한 명이라도 `tb_user_mgmt.USE_YN = 'N'` 또는 탈퇴 상태인 경우
- 카드 우상단에 Warning 배지 "확인 필요" 노출
- 카드 진입 후 편집 화면에서 해당 결재자 행에 Warning 강조 + 안내 메시지 ("이 사용자는 더 이상 활성 상태가 아니에요. 다른 결재자로 교체해 주세요")

### 3.5 프리셋 편집

#### 3.5.1 진입 경로
- 마이페이지 → 연차 결재선 관리 → 프리셋 카드 탭 (기존 프리셋 수정)
- 마이페이지 → 연차 결재선 관리 → [+ 새 프리셋 추가] (신규 생성 — 같은 화면, 빈 폼)

#### 3.5.2 화면 구성

```
[헤더] ← 백 + "프리셋 편집" + [🗑 삭제]  ← 신규 생성 시 [삭제] 미노출

[프리셋 이름]
[ 팀 결재선                              ]  ← text input

[기본 프리셋으로 사용]      [● 토글 ●]
└ 연차 신청 시 자동 적용됩니다.

[결재자]  · 위에서 아래 순서대로 결재됩니다
┌──────────────────────────────────────┐
│ ① 박지훈                              │
│   2본부 · 팀장        [⬆][⬇][✕]      │
└──────────────────────────────────────┘
┌──────────────────────────────────────┐
│ ② 김영수                              │
│   2본부 · 본부장      [⬆][⬇][✕]      │
└──────────────────────────────────────┘

[+ 결재자 추가]  ← 점선 카드

[푸터]
[취소] [저장]
```

#### 3.5.3 프리셋 이름

- text input, body-strong 톤
- 검증: 1자 이상 50자 이내, 공백만 입력 금지
- 중복 검증 (저장 시): 동일 사용자의 다른 프리셋과 이름이 같으면 422 + 인라인 에러 "이미 같은 이름의 프리셋이 있어요"
- (CMPNY_CD, USER_CD, PURPOSE_TYPE, PRESET_NM) 유니크 제약 (선행 작업지시서 §4.1.10)

#### 3.5.4 기본 프리셋 토글

- 토글 ON: 본 프리셋을 기본으로 지정. 저장 시 다른 프리셋의 `IS_DEFAULT`는 자동 'N'으로 다운그레이드 (백엔드 처리)
- 토글 OFF: 기본 지정 해제. **단, 현재 본 프리셋이 유일한 기본 프리셋이면 OFF 불가** — 사용자에게 토스트 "최소 1개의 기본 프리셋이 필요해요. 다른 프리셋을 먼저 기본으로 지정해 주세요"
  - (DB 제약: 사용자당 정확히 1개의 기본 프리셋 — 작업지시서 §4.1.10)
- 신규 생성 시 사용자가 첫 프리셋을 만들면 토글이 강제로 ON으로 시작 (=첫 프리셋은 자동 기본)

**예외**: 프리셋이 0개 상태에서 신규 생성 시 토글은 ON으로 고정, 사용자가 OFF 할 수 없음. 이유 안내 헬퍼: "첫 프리셋은 자동으로 기본이 됩니다"

#### 3.5.5 결재자 리스트

각 결재자 행:
- 좌측: 순번 ①②③ (Primary tint 원형 배지)
- 중앙: 결재자 이름 (body-strong) + 부서·직급 (body-sm, secondary)
- 우측: [⬆] [⬇] [✕] 액션 버튼

**순서 변경**:
- [⬆][⬇] 한 칸씩 이동
- 첫 번째 행의 [⬆]은 비활성, 마지막 행의 [⬇]은 비활성
- 길게 누르기 + 드래그 정렬은 1차 구현에서 제외 (선행 작업지시서 §3.4.14.4와 동일)

**삭제**:
- [✕] 탭 → 즉시 삭제 (확인 모달 없음 — 신규/편집 모두 저장 전이라 되돌릴 비용 낮음)
- 모두 삭제하여 0명이 되면 빈 상태 메시지: "결재자를 1명 이상 추가해 주세요"
- 0명 상태에서는 [저장] 버튼 disabled

**추가**:
- [+ 결재자 추가] 점선 카드 탭 → 결재자 추가 바텀시트 호출 (§3.6)

#### 3.5.6 프리셋 삭제 (헤더 우측 🗑)

- 기존 프리셋 편집 시에만 노출. 신규 생성 시 미노출.
- 탭 시 확인 모달:
  - 타이틀: "'{프리셋 이름}'을(를) 삭제할까요?"
  - 본문: "이 작업은 되돌릴 수 없습니다"
  - 액션: [취소] / [삭제] Danger
- 삭제 처리: `tb_user_approval_preset.USE_YN = 'N'` (소프트 삭제)
- 멤버는 ON DELETE CASCADE로 자동 처리 (작업지시서 §4.1.11)
- **기본 프리셋 삭제 제약**:
  - 사용자가 보유한 유일한 기본 프리셋인 경우 + 다른 프리셋이 1개 이상 있는 경우 → 삭제 시 다음 최신 프리셋을 자동 기본으로 승격
  - 사용자의 유일한 프리셋(=기본)인 경우 → 삭제 가능. 사용자는 프리셋 없는 상태가 됨. (다음 연차 신청 시 즉석 구성 + 자동 기본 생성 흐름 — 선행 작업지시서 §3.4.16 step 3)

#### 3.5.7 푸터 액션

- [취소] Secondary: 변경 사항 폐기. 변경 사항이 있으면 "변경 사항을 저장하지 않고 나갈까요?" 확인 모달
- [저장] Primary:
  - 신규: `tb_user_approval_preset` INSERT + `tb_user_approval_preset_member` INSERT × N
  - 수정: `tb_user_approval_preset` UPDATE + 멤버 삭제 후 재 INSERT (또는 diff 처리)

저장 가능 조건:
- 프리셋 이름 1자 이상
- 결재자 1명 이상
- 결재자에 본인이 포함되지 않음 (자기 결재 차단 — 공통 §9.5)
- 결재자 중복 없음

### 3.6 결재자 추가 바텀시트

`prafta-request-attendance-forms.md` v1.1 §3.4.14.2의 `LeaveApproverPickerSheet.vue`와 **동일한 컴포넌트를 재사용**한다. UI·검색 동작·다중 선택은 동일.

#### 3.6.1 재사용 조건

- 검색 API는 동일한 `/api/app/attd/req/leave/approver-search` 사용 (사용자 결재자 후보는 동일 도메인이므로)
- 시안 5-2 (빈 상태 + 최근 사용한 결재자), 시안 5-3 (검색 결과) 모두 동일
- 차이점: 호출 컨텍스트가 "신청 폼"이 아닌 "프리셋 편집"이라는 점 → frontend가 추가된 결재자를 호출자(프리셋 편집 화면)에 emit으로 전달

#### 3.6.2 다중 선택 처리

- 사용자가 N명 체크 → 푸터 [N명 추가] 탭
- 시트가 닫히면서 프리셋 편집 화면의 결재자 리스트 맨 아래에 N명이 순서대로 추가
- 이미 리스트에 있는 사용자는 검색 결과에서 disabled 표시 (중복 방지)

#### 3.6.3 본인 검색 차단

- 본인(현재 로그인 사용자)은 검색 결과에서 항상 제외 (백엔드 필터링)
- 이유: 자기 결재 차단 (공통 §9.5)

| 본문 | "탈퇴 후 취소는 불가합니다" |
| 콜아웃 (회색 배경) | "출퇴근 및 근태 기록은 법령에 따라 **3년간 보존**됩니다." + (줄바꿈) + "탈퇴 후 재가입 시 기존 출퇴근 및 근태 기록은 연계되지 않습니다." |
| 체크박스 | "회원탈퇴 유의사항을 모두 확인했습니다" |
| 액션 | [취소] Secondary / [탈퇴하기] Danger |

**[탈퇴하기] 버튼 활성 조건**: 체크박스 체크 시에만 활성화 (가이드 §5.7 "추가 게이트" 패턴)

#### 3.8.3 처리 정책 (확정 사항)

| 데이터 | 처리 |
|---|---|
| 출퇴근·근태 기록 (`tb_user_attd_mgmt`) | **법령에 따라 3년 보존**. 삭제하지 않음. `USER_CD`는 그대로 유지. |
| 안전점검·위험성평가·TBM 참여 기록 | 보존. `USER_CD`는 그대로 유지. |
| 신청 중인 연차 (`tb_user_attd_req` WHERE `REQ_STATUS = 'REQUESTED'`) | **자동 취소 처리** (`REQ_STATUS = 'CANCELLED'`) + 결재자에게 알림 발송 |
| 결재선 프리셋 (`tb_user_approval_preset`, `tb_user_approval_preset_member`) | **탈퇴 즉시 삭제** (소프트 삭제 아닌 hard delete) |
| 사용자 정보 (`tb_user_mgmt`) | 계정 상태를 `USE_STATUS = 'WITHDRAWN'`로 변경. 로그인 차단. 개인 식별 정보(이름·휴대폰·이메일·생년월일·성별)는 **마스킹 처리** (예: 이름 "김여진" → "김○○", 휴대폰 마지막 4자리만 남김) |
| 재가입 | 재가입 시 기존 USER_CD와 **연계하지 않음**. 신규 USER_CD 발급. |

**3년 보존 근거**: 근로기준법 제42조 "사용자는 근로자명부와 대통령령으로 정하는 근로계약에 관한 중요한 서류를 3년간 보존하여야 한다"

**계정 상태 ENUM 확장**: 공통 정책서 §3.5는 "활성화 / 미사용 / 탈퇴" 3종을 정의. 본 작업에서 `USE_STATUS = 'WITHDRAWN'` 값을 사용하므로 정책서와 정합 확인 필요 — §7.6 질문 사항.

#### 3.8.4 처리 흐름

1. 사용자가 [탈퇴하기] 탭 → POST `/api/app/auth/withdraw`
2. 트랜잭션 내에서:
   - 신청 중인 연차를 모두 `CANCELLED` 처리, 결재자별 알림 발송 큐 등록
   - 결재선 프리셋·멤버 hard delete
   - `tb_user_mgmt` UPDATE: `USE_STATUS = 'WITHDRAWN'`, 개인정보 마스킹
   - `tb_user_withdrawal_history` INSERT (탈퇴 일시·USER_CD·CMPNY_CD·SITE_CD 보존, 사유는 본 작업에서 받지 않음 — §7.7 질문 사항)
3. 토큰 폐기 + 선점 해제 (로그아웃과 동일)
4. 풀스크린 인사말: "그동안 PRAFTA를 이용해 주셔서 감사합니다" + 3초 후 자동으로 로그인 화면 이동

| `EMAIL` | varchar(100) | **수정 가능** |
| `GENDER` | varchar(10) | **수정 가능** ('MALE' / 'FEMALE' — 코드값 확인 필요) |
| `BIRTH_DATE` | varchar(8) | **수정 가능** (YYYYMMDD) |
| `HIRE_DATE` | varchar(8) | 읽기 전용 (관리자만 수정 — 근태 §8.5.2) |
| `PASSWORD_HASH` | varchar(255) | 비밀번호 변경 시 UPDATE |
| `USE_STATUS` | varchar(20) | 탈퇴 시 'WITHDRAWN'로 변경 — §7.6 확인 필요 |
| `LAST_LOGIN_AT` | datetime | 표시용 |

#### 4.1.2 `tb_user_approval_preset` / `tb_user_approval_preset_member`
선행 작업지시서 §4.1.10~4.1.11에 정의된 결재선 프리셋 테이블. 본 작업의 §3.4~3.5 핵심 데이터 소스.

#### 4.1.3 `tb_user_attd_req` (사용자 근태 요청)
회원 탈퇴 시 본인의 `REQ_STATUS = 'REQUESTED'` 건들을 일괄 `CANCELLED` 처리.

### 4.2 신규 테이블 검토 필요

#### 4.2.1 `tb_user_withdrawal_history` (탈퇴 이력) — **신규 검토 필요**

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `WITHDRAWAL_ID` | varchar(20) PK | 자동 채번 |
| `USER_CD` | varchar(20) | 탈퇴한 사용자 (FK 아님, 단순 참조) |
| `CMPNY_CD` | varchar(50) | 회사코드 |
| `SITE_CD` | varchar(50) | 사업장코드 |
| `WITHDRAWAL_DATE` | datetime | 탈퇴 처리 일시 |
| `WITHDRAWAL_REASON` | varchar(500) | 탈퇴 사유 (본 작업에서는 받지 않음 — §7.7) |
| `MASKED_USER_NM` | varchar(50) | 마스킹된 이름 (감사용) |

**대안**: `tb_user_mgmt`에 `WITHDRAWAL_DATE`, `WITHDRAWAL_REASON` 컬럼 추가만으로 충분할 수 있음. 별도 이력 테이블 신설 여부는 백엔드 협의.

#### 4.2.2 `tb_user_mgmt.USE_STATUS` ENUM 값 확인

- 공통 정책서 §3.5에 "활성화 / 미사용 / 탈퇴" 명시
- 실제 DB 컬럼명·ENUM 값 확인 필요. `USE_YN` 컬럼만 있고 'WITHDRAWN' 같은 별도 상태가 없을 수 있음
- 없다면 컬럼 추가 또는 `USE_YN`을 확장하여 처리 — §7.6 질문 사항

## 5. 백엔드 API 명세 (필수)

> 백엔드 작업은 별도 백엔드 개발자(외부, 사람)가 담당. 아래 명세는 frontend 호출 기준 단일 출처.

### 5.1 GET /api/app/mypage/profile
**용도**: 마이페이지 메인 + 개인정보 수정 화면 초기 데이터 조회

**요청 파라미터**: 없음 (인증된 사용자 기준)

**응답**:
```json
{
  "userCd": "YJKIM",
  "userName": "김여진",
  "siteName": "중곡사업장",
  "deptName": "2본부",
  "hireDate": "2025-07-17",
  "mobileNo": "010-6766-8295",
  "email": "test@test.com",
  "gender": "FEMALE",
  "birthDate": "1993-09-16",
  "lastLoginAt": "2026-05-25T20:13:49",
  "presetCount": 3
}
```

**비고**:
- `presetCount`: 마이페이지 메인의 "연차 결재선 관리" 메뉴 우측 메타 표시용
- 사업장명·부서명은 ID가 아닌 이름을 직접 전달 (frontend가 ID 매핑 안 함)

### 5.2 PUT /api/app/mypage/profile
**용도**: 개인정보 수정 저장

**요청 Body**:
```json
{
  "userName": "김여진",
  "gender": "FEMALE",
  "birthDate": "19930916",
  "email": "test@test.com",
  "mobileNo": "010-6766-8295",
  "mobileVerificationToken": "vfy_abc123..."
}
```

**필드 의미**:
- `userName`, `gender`, `birthDate`, `email`: 변경된 항목만 또는 전체 전송 (백엔드와 협의)
- `mobileNo`: 휴대폰이 변경된 경우만 필수
- `mobileVerificationToken`: 휴대폰이 변경된 경우 §5.4의 인증 확인 응답 토큰 필수. 미동봉 시 422

**처리**:
1. 변경된 필드만 `tb_user_mgmt` UPDATE
2. 휴대폰 변경 시 `mobileVerificationToken`을 서버에 저장된 인증 세션과 대조하여 검증

**검증 (백엔드)**:
- `userName`: 1~50자, 공백 trim 후 1자 이상
- `gender`: ENUM 값 검증
- `birthDate`: YYYYMMDD 형식, 미래 일자 불가, 만 14세 이상
- `email`: RFC 5322 또는 빈 문자열 허용
- `mobileNo`: 010-XXXX-XXXX 형식

검증 실패 시 422 + 어느 필드가 문제인지 명시.

### 5.3 POST /api/app/mypage/mobile/request-verification
**용도**: 휴대폰 변경 시 SMS 인증번호 발송

**요청 Body**:
```json
{
  "mobileNo": "010-1234-5678"
}
```

**처리**:
1. 6자리 숫자 생성 → SMS 발송
2. 서버 메모리/Redis에 인증 세션 저장: (USER_CD, mobileNo, code, expiresAt: now + 3min)
3. **본인 휴대폰과 중복 검증**: 다른 사용자가 이미 사용 중인 번호는 422 + "이미 사용 중인 번호예요"

**응답**:
```json
{
  "expiresInSeconds": 180
}
```

### 5.4 POST /api/app/mypage/mobile/verify
**용도**: 휴대폰 인증번호 확인

**요청 Body**:
```json
{
  "mobileNo": "010-1234-5678",
  "verificationCode": "123456"
}
```

**응답 (성공)**:
```json
{
  "verified": true,
  "verificationToken": "vfy_abc123..."
}
```

**응답 (실패)**:
- 인증번호 불일치: 422 + `errorCode: INVALID_CODE`
- 만료: 422 + `errorCode: EXPIRED`
- 시도 횟수 초과 (5회): 422 + `errorCode: TOO_MANY_ATTEMPTS`

**처리**:
- 성공 시 `verificationToken` 발급, 5분 유효. §5.2 PUT 호출 시 동봉.

### 5.5 PUT /api/app/mypage/password
**용도**: 비밀번호 변경

**요청 Body**:
```json
{
  "currentPassword": "...",
  "newPassword": "..."
}
```

**처리**:
1. 현재 비밀번호 bcrypt 검증
2. 새 비밀번호 규칙 검증 (서버에서도 동일하게 — §3.3.1)
3. 현재 != 새 검증
4. `tb_user_mgmt.PASSWORD_HASH` UPDATE
5. **세션 유지** (현재 토큰 무효화 안 함)

**응답**:
```json
{ "success": true }
```

**에러**:
- 현재 비밀번호 불일치: 422 + `errorCode: INVALID_CURRENT_PASSWORD`
- 규칙 위반: 422 + `errorCode: PASSWORD_RULE_VIOLATION`
- 현재 == 새: 422 + `errorCode: SAME_AS_CURRENT`

### 5.6 GET /api/app/mypage/approval-presets
**용도**: 연차 결재선 관리 화면 진입 시 프리셋 목록 조회

      "presetId": "PRS20260520001",
      "presetName": "팀 결재선",
      "isDefault": true,
      "approverCount": 2,
      "summary": "박지훈 → 김영수",

      "approvers": [
        { "seq": 1, "userCd": "TEST02", "userName": "박지훈", "rankName": "팀장", "deptName": "2본부" },

### 5.7 GET /api/app/mypage/approval-presets/{presetId}
**용도**: 프리셋 편집 진입 시 단일 프리셋 상세 조회

**응답**: §5.6 응답의 단일 객체

### 5.8 POST /api/app/mypage/approval-presets
**용도**: 신규 프리셋 생성

**요청 Body**:
```json
{
  "presetName": "팀 결재선",
  "isDefault": true,
  "approvers": [
    { "userCd": "TEST02" },
    { "userCd": "KIMY01" }
  ]
}
```

**처리**:
1. 이름 중복 검증 — (CMPNY_CD, USER_CD, PURPOSE_TYPE, PRESET_NM) 유니크
2. `isDefault: true`인 경우 기존 기본 프리셋을 'N'으로 다운그레이드 (단일 트랜잭션)
3. `tb_user_approval_preset` INSERT
4. `tb_user_approval_preset_member` INSERT × N (STEP_SEQ는 배열 인덱스 + 1)

**응답**: 생성된 프리셋 (§5.7과 동일 구조)

**검증**:
- 이름 1~50자
- 결재자 1명 이상
- 결재자 중복 불가
- 결재자에 본인 포함 불가
- 결재자 모두 활성 사용자

### 5.9 PUT /api/app/mypage/approval-presets/{presetId}
**용도**: 프리셋 수정

**요청 Body**: §5.8과 동일

**처리**:
1. 이름 변경 시 중복 검증
2. `isDefault` 변경 시 기존 기본 프리셋 처리
3. `tb_user_approval_preset` UPDATE
4. 멤버 처리:
   - **방안 A**: 전체 멤버 DELETE 후 재 INSERT (단순)
   - **방안 B**: diff 처리 (변경된 항목만 UPDATE/INSERT/DELETE)
   - 권장: 방안 A. 데이터 양이 적고 순서 변경이 빈번하여 diff 비용이 더 큼.

### 5.10 DELETE /api/app/mypage/approval-presets/{presetId}
**용도**: 프리셋 삭제 (소프트 삭제)

**처리**:
1. `tb_user_approval_preset.USE_YN = 'N'` UPDATE
2. 본 프리셋이 유일한 기본 프리셋이었고 다른 프리셋이 있는 경우 → 가장 최근 수정된 다른 프리셋을 자동 기본으로 승격
3. 멤버는 그대로 보존 (소프트 삭제이므로)

**응답**: 삭제 후 갱신된 프리셋 목록 (§5.6과 동일)

### 5.11 POST /api/app/auth/logout
**용도**: 로그아웃

**요청 Body**: 없음 (인증된 사용자 기준)

**처리**:
1. 액세스 토큰 무효화 (Redis 블랙리스트 또는 토큰 버전 증가)
2. 리프레쉬 토큰 폐기
3. 본인 명의 선점 모두 해제

**응답**:
```json
{ "success": true }
```

### 5.12 POST /api/app/auth/withdraw
**용도**: 회원 탈퇴

**요청 Body**:
```json
{
  "confirmed": true
}
```

**처리** (단일 트랜잭션):
1. 사용자의 `REQ_STATUS = 'REQUESTED'`인 모든 `tb_user_attd_req` UPDATE → `CANCELLED`. 각 건의 결재자 알림 큐 등록.
2. 사용자의 `tb_user_approval_preset` + `tb_user_approval_preset_member` HARD DELETE
3. `tb_user_mgmt` UPDATE:
   - `USE_STATUS = 'WITHDRAWN'`
   - `USER_NM` → 마스킹 (예: "김여진" → "김○○")
   - `MOBILE_NO` → 마스킹 (예: "010-****-8295")
   - `EMAIL` → NULL
   - `GENDER` → NULL
   - `BIRTH_DATE` → NULL
   - `PASSWORD_HASH` → 무효화 (재로그인 불가)
   - `WITHDRAWAL_DATE` → now (컬럼 추가 필요 — §4.2.2)
4. `tb_user_withdrawal_history` INSERT (또는 `tb_user_mgmt`에 통합)
5. 토큰 폐기 + 선점 해제

**응답**:
```json
{ "success": true }
```

**보존 데이터** (DELETE 안 함):
- `tb_user_attd_mgmt` (출퇴근 기록) — 3년 보존
- `tb_user_attd_history` 또는 유사 (근태 이력)
- `tb_safety_*` (안전점검·위험성평가·TBM 등)

### 5.13 정책서 참조 출처
- 정확한 정책서 섹션 매핑은 planner가 `.claude/context/policies/INDEX.md`를 통해 확정
- 본 작업 요청서에 명시된 비즈니스 규칙(§3)은 시안 작성 시 검토된 내용이며, planner가 정책서 출처를 작업 로그 "상세 설명"에 명시해야 한다

## 6. DB 구조 검토 및 추가 작업 필요 사항

### 6.1 `tb_user_mgmt.USE_STATUS` 컬럼 / ENUM 검토

- 공통 정책서 §3.5는 "활성화 / 미사용 / 탈퇴" 3종을 정의
- 실제 DB에 이 ENUM이 어떻게 구현되어 있는지 확인 필요. `USE_YN`만 있다면 별도 컬럼 추가 또는 컬럼명·코드값 표준화
- 본 작업에서 탈퇴 시 'WITHDRAWN' 값을 INSERT 하려면 정합 보장 필요

### 6.2 탈퇴 이력 저장 구조

- **방안 A**: `tb_user_withdrawal_history` 신규 테이블 (§4.2.1)
- **방안 B**: `tb_user_mgmt`에 `WITHDRAWAL_DATE`, `WITHDRAWAL_REASON` 컬럼 추가
- 권장: 방안 B. 단순 추가이며 1:1 관계라 별도 테이블 비용이 크지 않음

### 6.3 개인정보 마스킹 규정

- 공통 정책서 §11.3 감사 로그 및 §5.6.4 슬롯점유이력에 마스킹 규정 일부 존재 (이름 "김○○", 휴대폰 "010-****-1234")
- 탈퇴 시 적용할 마스킹 규칙을 본 작업에서 확정 필요
- 정책서 §11에 마스킹 공통 규정 신설 검토 권장

### 6.4 휴대폰 인증 외부 SMS 게이트웨이

- §5.3 SMS 발송은 외부 SMS 게이트웨이 (예: Aligo, NHN Toast, 알리고 등) 연동 필요
- 이미 사용 중인 게이트웨이가 있는지 백엔드 협의
- 비용·일일 한도·발송 실패 처리 등 운영 정책 확정 필요

### 6.5 비밀번호 변경 후 다른 디바이스 세션 처리

- 본 작업은 "현재 세션 유지" 정책으로 명시
- 다른 디바이스의 액세스 토큰을 무효화할지 여부는 정책 확정 필요 (§7.5)
- 보안 권장: 변경 시 본인 외 모든 세션 강제 로그아웃

## 7. 정책서 출처 확인 / 결정 필요 사항 (planner 작업)

| # | 항목 | 본 시안의 가정 | 정책서 확인 / 결정 필요 |
|---|---|---|---|
| 7.1 | 회원가입 시 성별 필수 여부 | 공통 §3.1에 선택 입력으로 명시 — 마이페이지에서 미설정 가능 | 성별 select에 "선택 안 함" 옵션 포함 여부 |
| 7.2 | 성별 ENUM 코드값 | 'MALE' / 'FEMALE' 가정 | 실제 DB ENUM 또는 코드 테이블 확인 |
| 7.3 | 생년월일 변경 시 만 14세 미만 차단 | 본 시안에서 만 14세 이상 검증 적용 | 법적 미성년 가입 정책 (정보통신망법 등) 확인 |
| 7.4 | 비밀번호 정기 변경 강제 여부 | 본 시안은 "3개월 권장" 안내만, 강제 없음 | 정책서에 정기 변경 강제 규정이 있는지 — 없다면 본 작업으로 정책 신설 |
| 7.5 | 비밀번호 변경 시 다른 디바이스 세션 처리 | 본 시안은 현재 세션만 유지 | 보안 권장은 전체 세션 무효화. 정책 확정 필요 |
| 7.6 | `tb_user_mgmt.USE_STATUS` ENUM 값 | 'WITHDRAWN' 가정 | 실제 DB 컬럼·코드값 확인. 정책서 §3.5와 정합 보장 |
| 7.7 | 회원 탈퇴 사유 입력 여부 | 본 시안은 사유 미입력 | 일반 SaaS는 탈퇴 사유 수집 (서비스 개선용). 본 시스템에서도 받을지 결정. 받는다면 모달에 사유 입력 필드 추가 필요 |
| 7.8 | 탈퇴 후 재가입 가능 시점 | 본 시안은 즉시 재가입 가능으로 가정 | 카카오스타일 등 일반 서비스는 14~30일 대기. 노무 시스템 특성상 즉시 재가입 허용 여부 |
| 7.9 | 탈퇴 시 개인정보 마스킹 규칙 | 본 시안은 이름 "김○○", 휴대폰 "010-****-XXXX" 가정 | 공통 정책서 §11에 마스킹 공통 규정이 있는지. 없다면 본 작업으로 신설 |
| 7.10 | 신청 중인 연차 자동 취소 처리 | 본 시안은 자동 취소 + 결재자 알림 | 정책서에 명시적 조항이 있는지. 없다면 신설 |
| 7.11 | 다일 결재선 프리셋 중 기본 프리셋 삭제 정책 | 본 시안은 다음 최신 프리셋 자동 승격 | 정책서에 후속 처리 정의 없음 — 본 작업으로 정책 신설 |
| 7.12 | 마이페이지 알림 아이콘 노출 여부 | 홈과 동일하게 노출 | 마이페이지는 정보 관리 화면이라 알림 진입을 두지 않을 수도 있음. UX 결정 사항 |
| 7.13 | 비활성 결재자 포함 프리셋 처리 | "확인 필요" 배지 + 편집 화면에서 강조 | 자동 제거할지, 사용자가 수동 교체할지. 본 시안은 수동 교체 |
| 7.14 | 인증번호 시도 횟수 제한 | 본 시안 5회 가정 | 보안 정책상 표준값 확정 필요 |

## 8. 비기능 요구사항

### 8.1 디자인 시스템 준수
- 색상/폰트/간격은 모두 CSS 변수만 사용 (하드코딩 금지)
- 디자인 토큰은 PRAFTA 모바일 앱 디자인 가이드 §2 참조
- 모바일 first (360~414px 기준 폭, 시안은 390px 기준)
- 터치 영역 최소 44×44px (디자인 가이드 §7.1 준수)
- 인라인 SVG 아이콘 사용 (CDN 의존 금지 — `prafta-request-attendance-forms.md` §8.2와 동일 원칙)

### 8.2 보안
- 비밀번호는 절대 frontend 로그에 남기지 않음. 입력 필드는 type="password"
- 인증 토큰은 secure storage (KeyChain / Keystore) 또는 httpOnly 쿠키
- 휴대폰 인증번호는 frontend에 6자리만 보관, 검증 후 즉시 폐기
- 마이페이지 진입 시 인증 토큰 만료 → 자동 갱신 (공통 §3.4) 또는 재로그인

### 8.3 성능
- 마이페이지 메인 진입 시 단일 API 호출 (§5.1 `/api/app/mypage/profile`)
- 프리셋 목록 화면은 별도 호출 (§5.6) — 메인에는 카운트만 표시
- 프리셋 카드 리스트는 평균 1~5개 수준이라 페이지네이션 불필요

### 8.4 접근성
- 모든 폼 필드는 `<label for="">` 또는 `aria-label`로 라벨 연결
- 비밀번호 입력 시 type="password"이지만 시각 보조용 토글 [👁] 제공 (선택)
- 회원 탈퇴 모달의 체크박스는 `role="checkbox"` + `aria-checked` 명시
- 토글 스위치는 `role="switch"` + `aria-checked`

### 8.5 에러 처리
- 네트워크 오류 / 401 / 403 / 422 / 500 등 표준 패턴 (prafta 기존 화면 패턴 따름)
- 회원 탈퇴 처리 중 일부 단계 실패 시 트랜잭션 롤백 → 사용자에게 "탈퇴 처리에 문제가 발생했어요. 잠시 후 다시 시도해 주세요" 토스트
- 비밀번호 변경 시도 5회 초과 시 일정 시간 잠금 처리 — §7.4 확정 필요

### 8.6 데이터 일관성
- 개인정보 수정 저장 후 마이페이지 메인 + 홈 화면의 프로필 정보가 즉시 갱신되어야 함
  - 권장: Pinia store에서 사용자 정보를 중앙 관리, 수정 후 store 갱신
- 결재선 프리셋 변경 후 연차 신청 폼의 셀렉트가 즉시 갱신되어야 함
  - 권장: 연차 신청 폼 진입 시 항상 §5.6 재호출 (캐싱 안 함)

## 10. 결정 사항 요약 (시안 작성 시점)

본 시안은 사용자와의 다회 이터레이션을 거쳐 확정됨. 주요 결정 사항:

1. **5번째 탭 "마이" 추가**: 디자인 가이드 §8.1의 "탭 수 조정 가이드"에서 명시한 "마이" 탭 대체안 채택. 헤더 타이틀은 "마이페이지", 탭바 라벨은 공간 제약상 "마이" 유지.
2. **메뉴 그룹 라벨은 의미 기반으로만**: "계정", "결재" 2개만 사용. "기타" 같은 무의미 그룹 생성 금지.
3. **로그아웃·회원 탈퇴는 메뉴에서 분리**:
   - 로그아웃은 풀폭 secondary 버튼 (자주 누르는 액션)
   - 회원 탈퇴는 작은 텍스트 링크 (빈도 낮고 파괴적)
   - 카카오·토스·네이버 등 한국 모바일 앱의 보편 패턴
4. **개인정보 3그룹 분리**: 소속(읽기) / 기본(이름·성별·생년월일) / 연락처(휴대폰·이메일). 회색 배경으로 읽기 전용임을 시각화.
5. **이름 변경 정책**: 인증 없이 즉시 변경 가능, 빈도 제한 없음. 근태·안전 기록 키는 USER_CD라 변경 영향 없음.
6. **휴대폰 변경 시 인증 필수**: 인증요청 → 인증번호 확인 → 저장 가능. 이메일은 인증 없이 즉시 변경.
7. **비밀번호 규칙 실시간 표기**: 4개 규칙(8자/대소문자/숫자/특수) 입력 시 즉시 충족 여부 표기, 모두 충족 시 [변경하기] 활성화.
8. **연차 결재선 관리는 마이페이지 하위**: 선행 작업지시서 v1.1 §3.4.19에서 분리한 "후속 작업"의 진입점을 본 작업으로 확정.
9. **프리셋 편집 = 신규 생성 + 기존 수정 동일 화면**: 헤더 우측 [🗑]만 신규 생성 시 미노출.
10. **기본 프리셋 1개 강제**: 사용자가 보유한 프리셋이 1개 이상이면 정확히 1개는 기본. 삭제 시 자동 승격, 첫 프리셋 생성 시 자동 기본.
11. **결재자 추가 바텀시트는 선행 작업 컴포넌트 재사용**: `LeaveApproverPickerSheet.vue` = `PresetApproverPickerSheet.vue` 통합 운영.
12. **로그아웃 모달 단순화**: 타이틀 한 줄만, 부가 설명 없음.
13. **회원 탈퇴 모달 톤**: 사용자 이름 호명 + 본문 한 줄 + 회색 콜아웃 + 확인 체크박스 + Danger [탈퇴하기] 버튼. 체크 미체크 시 버튼 disabled (가이드 §5.7 추가 게이트).
14. **회원 탈퇴 처리 정책 확정**:
    - 출퇴근·근태 기록은 **법령에 따라 3년 보존** (근로기준법 §42)
    - 신청 중인 연차는 자동 취소 + 결재자 알림
    - 결재선 프리셋은 hard delete
    - 개인정보(이름·휴대폰·이메일·생년월일·성별)는 마스킹 처리
    - 재가입 시 기존 USER_CD와 미연계 (신규 발급)
15. **본 작업에서 다루지 않는 것**:
    - 결재선 프리셋의 LEAVE_REQUEST 외 다른 PURPOSE_TYPE 사용 (스케줄 수정·근태 보정·초과근무용 결재선) — 후속 작업
    - 노드 담당 정/부 기반 자동 추천 결재선 (선행 작업지시서 §6.10) — 후속 작업
    - 회원 탈퇴 사유 수집 (§7.7) — 정책 확정 후 별도 작업
    - 탈퇴 후 재가입 대기 기간 (§7.8) — 정책 확정 후 별도 작업
    - 비밀번호 정기 변경 강제 (§7.4) — 정책 확정 후 별도 작업
    - 알림 센터 진입 동선 — 선행 작업
