&#x20; 특히 주목할 점:

&#x20; - hireDateGrant()는 입사일 근속을 계산해 월차/본연차/근속가산 컴포넌트를 멱등키({USER\_CD}\_{YYYY}\_{GRANT\_TYPE}\_HIRE)로 INSERT합니다(grantComponent, 497행\~). 이건 사실상 KEEP\_AND\_BACKFILL의 핵심 알고리즘과

&#x20; 거의 동일합니다. 다만 userCds 리스트만 받고 handlingType을 받지 않으며, 올해분만 보충하는 단순 멱등 부여입니다.

&#x20; - cancelGrant()는 RESET\_ALL용 단건 강제취소(STATUS='CANCELED', DEL\_YN='N' 소프트)를 이미 제공합니다(LeaveGrantStatusService.java:50-58).



&#x20; 2) 없는 것 (입사일 수정과의 단절 지점)



&#x20; - 자동 정기 부여 스케줄러 미구현. hireDateGrant는 관리자가 Attd\_09에서 수동 트리거하는 "검증용"이고, 정책 기준 매년 자동 부여 배치는 없습니다(leave-domain-overview.md §3·§7에 정직하게 기록됨).

&#x20; - 입사일 수정 → 부여 조작의 연결 자체가 없음. 두 경로가 서로를 호출하지 않습니다:

&#x20;   - 경로 A: HireDateEditPop → user01.updateUserHireDate → HIRE\_DATE UPDATE + 이력만 (handlingType은 검증·이력기록만, 446-447행 NOTE로 미룸)

&#x20;   - 경로 B: Attd\_09 → attd09.hireDateGrant → 입사일 기준 부여 (handlingType 무관)

&#x20; - handlingType 3분기 처리 로직 부재 — APPLY\_NEW(no-op), RESET\_ALL(일괄 취소+재발급) 분기 없음.

&#x20; - 영향분석이 전부 근사. buildApproxImpact(456-492행)는 기존부여/사용/누락을 모두 "0일"로 하드코딩하고 시나리오 라벨·요약만 실제 계산합니다.



&#x20; 3) handlingType을 실제로 붙이려면 필요한 작업



&#x20; 이미 있는 블록(✅)과 새로 필요한 것(❌)을 처리방식별로 정리하면:



&#x20; 공통 토대

&#x20; - ❌ user01.updateUserHireDate의 NOTE 자리에 부여 오케스트레이션 호출 추가 — HIRE\_DATE UPDATE + 이력 INSERT + grant 조작을 한 트랜잭션으로 묶기. 현재 LeaveDashboardServiceImpl에 묶인 부여 로직을 공용

&#x20; 서비스로 추출해 user01에서 재사용하는 게 깔끔합니다.

&#x20; - ❌ 영향분석 실측화: buildApproxImpact → "변경 전 입사일 기준 기존 부여합 / 사용 / 변경 후 기준 누락분" 실제 집계로 교체.



&#x20; KEEP\_AND\_BACKFILL (가장 가까움)

&#x20; - ✅ 컴포넌트 산정·멱등 INSERT(grantComponent) 재사용 가능

&#x20; - ❌ 단, 멱등키가 "연도+종류" 기반이라 입사일이 과거로 당겨져 과거 연도분이 누락된 경우 그 과거 연도들까지 루프 백필하도록 확장 필요(현재는 올해분만)

&#x20; - ✅ 기존 부여 만료일 보존 — 신규분만 추가하면 되므로 자연 충족(UI 안내문과 일치)



&#x20; KEEP\_AND\_APPLY\_NEW

&#x20; - ✅ 사실상 현재 updateUserHireDate 동작(HIRE\_DATE만 UPDATE)이 이것 — 명시적 no-op 분기로 표시만 하면 됨



&#x20; RESET\_ALL (가장 손이 많이 감)

&#x20; - ✅ 단건 취소 cancelGrant 존재

&#x20; - ❌ "대상자의 활성 STATUTORY\_\* GRANT 전체 조회" 매퍼 + 각 건 cancelGrant → 변경 후 입사일 기준 전체 재발급 오케스트레이션 필요

&#x20; - ✅ 사용 이력(tb\_user\_leave\_use) 보존은 소프트 취소라 자동 충족(§8.5.8)



&#x20; 선택

&#x20; - ❌ §8.5.6 매트릭스(근속×방향 → 권장 처리방식) 자동 제안

&#x20; - ❌ hireDateGrant의 "테스트/검증용" 딱지 제거 후 정식 엔진 승격 또는 정기 스케줄러 신설

&#x20; 요약하면, 부여의 "조각"(INSERT·멱등·취소·STATUS·정책)은 거의 다 준비됐고, 빠진 건 이 조각들을 입사일 수정 트랜잭션 안에서 handlingType 분기로 묶어 호출하는 "오케스트레이션 레이어"와 영향분석 실측화입니다.

&#x20; 작업 규모로 보면 RESET\_ALL의 일괄 취소+재발급, 그리고 BACKFILL의 과거 연도 백필 확장이 가장 신경 쓸 부분입니다.
