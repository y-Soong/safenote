# TBM 모듈 개요 (Overview)

> 이 문서는 Prafta v2 TBM(Tool Box Meeting) 모듈의 전체 그림과 결정사항을 정리합니다.
> 모든 작업지시서 작성·구현 시 이 문서의 결정사항을 기준으로 합니다.

---

## 1. 모듈 위치 및 컨텍스트

### 1.1 Prafta 안전관리 전체 그림

Prafta 안전관리는 **자기규율 예방체계**의 흐름을 따릅니다:

```
순회점검 (정적 점검)
   ↓
위험성평가 (위험 식별 → 평가 → 조치)
   ↓
TBM (위험을 현장 근로자에게 전달)  ← 본 모듈
   ↓
[Phase 2] 사고 관리 (위 3개 + AI)
```

TBM은 **위험성평가 → 현장 전달의 연결고리** 역할입니다.

### 1.2 법적 배경

- **산업안전보건법 제29조 제1항**: 사업주는 근로자에게 정기적 안전보건교육 의무
- **2023.12 이후**: TBM이 정기 안전보건교육 시간으로 인정 가능 (가이드 기준)
- **2022.11 「중대재해 감축 로드맵」**: 위험성평가와 TBM을 자기규율 예방체계의 핵심 수단으로 명시
- **TBM 자체**는 법조항으로 강제되지 않으나, **안전교육 이수 입증 수단**으로 가장 강력

### 1.3 MVP 범위

| 구분 | 포함 / 제외 |
|---|---|
| **포함** | TBM 세션 CRUD, 콘텐츠 라이브러리, 출결, 일용직 QR, 위험성평가 연계 (옵션), 이력 조회, SSE 동기화 |
| **제외 (Phase 2+)** | 정기교육 시간 환산, 다국어, AI 콘텐츠 생성, 사고 관리 연계, 순회점검 연계, AI 퀴즈, 위험성평가 기반 자동 생성, 일용직 사진 등록 |

## 2. 핵심 설계 철학

### 2.1 책임 분리 — 가장 중요한 원칙

> **시스템은 기록만 한다. 판단은 사람이 한다. 책임도 사람이 진다.**

- 시스템은 **이상 신호를 플래그**로 표시할 뿐, **자동 판정하지 않음**
- 부정 사용·관리자 실수는 관리자 책임으로 명확히 분리
- "관리자가 봤다"는 사실을 데이터로 남기는 게 시스템의 역할

### 2.2 종이 TBM 대비 차별점

| 입증 레이어 | 종이 TBM | Prafta TBM |
|---|---|---|
| 시점 | 작성일자 위조 가능 | 서버 타임스탬프 (위조 불가) |
| 장소 | 어디서 작성했는지 모름 | GPS 검증 |
| 본인 | 필적만 (대리서명 가능) | 본인 디바이스 + 비번 + 서명 |
| 참여 시간 | 알 수 없음 | ENTRY/EXIT 시각 |
| 내용 인지 | 알 수 없음 | 콘텐츠 노출 + (Phase 2) 퀴즈 |

### 2.3 SME 친화 설계

- **QR 슬롯 모델**: 폰 없는 일용직도 디지털 출결 가능
- **관리자 부담 최소화**: 자동화로 일상 운영 부담 ↓
- **단순함 우선**: 옵션·정책 토글은 최소화

## 3. 도메인 결정사항 (확정)

### 3.1 TBM ≠ 정기교육

- TBM은 작업 전 안전점검회의로 독립된 활동
- TBM이 정기교육 시간으로 인정될 수 있으나, MVP에서는 시간 환산 모듈 미포함
- 데이터 모델은 확장 가능 구조 (`EDU_TYPE_CD`로 향후 정기교육·채용 시 교육 등 추가)

### 3.2 위험성평가 연계 (B+ 약한 강제)

- TBM 개설 시 **위험성평가 선택은 옵션**
- 미선택 시 UI에서 경고 안내: "위험성평가 연동되지 않은 TBM입니다. 개설하시겠습니까?"
- **다중 선택 허용** (한 TBM에 여러 위험성평가 연결 가능)
- Phase 2 사고 관리 출시 시 안내 문구 강화 예정

### 3.3 콘텐츠 스코프

- **회사 공통** (`SITE_CD IS NULL`): master, safe만 등록 가능, 모든 사업장에서 사용 가능
- **사업장** (`SITE_CD` 지정): 해당 사업장에서만 사용 가능
- 조회 시: `SITE_CD IS NULL OR SITE_CD = #{currentSiteCd}`

## 4. 인증 결정사항 (확정)

### 4.1 정규직 인증 흐름

| 단계 | 검증 |
|---|---|
| 입실 | 본인 디바이스 토큰 + GPS 반경 검증 + 입실 비번 |
| 종료 | 종료 비번 + 본인 서명 |

### 4.2 일용직(QR 사용자) 인증 흐름

| 단계 | 검증 |
|---|---|
| 입실 | 관리자가 일용직 QR 스캔 → 정보 확인 (이름, 휴대폰 끝자리, 만료일) → 입실 처리 |
| 종료 | 관리자가 일용직 QR 재스캔 → 서명창 → 일용직이 관리자 폰에서 직접 서명 |

### 4.3 일용직 QR 만료 정책

- **기본**: 당일 자정 자동 만료 (추후 스케줄러 구현)
- **슬롯 고정 처리 시**: 만료 없음
- **고정 해제 시**: 그날 자정에 만료
- **TBM 입실 시**: 만료된 QR 스캔 차단 → 에러 안내

### 4.4 GPS 검증

#### 수집 시점 및 디바이스

- **TBM 세션 개설 시점에 GPS 수집 시도** (DRAFT → OPENED 전이 시)
- **디바이스 유형 무관**: PC / 모바일 / 태블릿 어디서나 동일 흐름
- 기본 반경 100m (개설 시 관리자가 설정 가능)

#### 수집 결과별 처리

| 케이스 | GPS_VERIFY_TYPE_CD | 입실 시 검증 |
|---|---|---|
| GPS 수신 성공 (정확도 충분) | `AUTO` | GPS 반경 검증 활성 |
| GPS 수신 실패/부정확 (PC, 실내, 지하 등) | `MANUAL` | GPS 검증 스킵, 비번만 검증 |
| 관리자가 GPS 검증 비활성 선택 | `DISABLED` | GPS 검증 스킵, 비번만 검증 |

#### GPS 미수신 환경의 통합 처리 정책

다음 환경 모두를 **단일 정책으로 처리**:
- 지하 작업장 / 실내 대형 물류센터
- 데스크톱 PC (이더넷 연결)
- WiFi 학습 DB 미등록 외진 사업장
- 일반적인 GPS 미수신 상황

이 경우 시스템이 자동으로 안내 모달을 표시:

```
[안내 모달]
"위치 정보를 가져올 수 없습니다.
다음을 확인해주세요:
  ☐ 모든 참여 예정자가 현재 교육 장소에 있음을 확인했습니다

위 확인 후에도 진행하시려면 체크하시고 [개설]을 눌러주세요."
```

- 관리자가 체크 시: `GPS_VERIFY_TYPE_CD = 'MANUAL'`, `GPS_MANUAL_CONFIRM_YN = 'Y'`
- 미체크 시 개설 차단

#### 관리자 책임 명시 원칙

GPS 검증 스킵은 **관리자의 명시적 판단**으로 기록.
사고 발생 시 데이터 흔적: "이 세션은 관리자가 GPS 검증 없이 진행하기로 명시적으로 확인하여 개설했다."
**Prafta 책임 분리 철학과 부합** — 시스템은 정보 제공, 책임은 관리자.

### 4.5 비밀번호 정책

- **유효시간 없음** — 단 상태 기반 차단
  - 세션 `IN_PROGRESS` 이후 입실 비번 입력 불가
  - 세션 `COMPLETED` 이후 종료 비번 입력 불가
- **랜덤 6자리** (관리자가 구두 전달)
- **입실 비번 ≠ 종료 비번**
- **실패 시**: 무한 재시도 + 실패 로그

## 5. 흐름 결정사항 (확정)

### 5.1 세션 상태 전이

```
DRAFT (작성 중)
   ↓ 개설 (관리자 행위)
OPENED (입실 가능)
   ↓ 시작 (관리자 행위)
IN_PROGRESS (입실 차단, 콘텐츠 진행)
   ↓ 종료 (관리자 행위)
COMPLETED (종결)

(임의 시점) → CANCELLED
```

### 5.2 입실/지각자 정책

- **OPENED 상태**: 입실 가능 (관리자가 GPS 반경 내 비번 입력자만)
- **IN_PROGRESS 이후**: 입실 차단
- **지각자**: 별도 회차로 처리 (동일 교육 다회 개설 허용)

### 5.3 이탈 정책

- **자동 판정 없음**
- 백그라운드 진입, GPS 이탈 등은 **이벤트 로그에만 기록**
- 관리자가 종료 시점에 이상 신호 확인하고 필요 시 미이수 처리

### 5.4 종료 미처리자 처리

- 관리자가 **강제 종료** 가능
- **강제 종료 시 사유 필수 입력**
- **이수/미이수 관리자가 선택**
- 강제 종료 시 본인 서명 없음 (관리자 책임으로 분리)

### 5.5 콘텐츠 동기화 (Level 1.5)

- **슬라이드/콘텐츠 단위 동기화** (관리자가 다음/이전 → 모두 같은 화면)
- **영상 정밀 동기화 X** (각자 폰에서 재생, 사실상 관리자 폰 스피커로 공동 청취)
- **풀스크린은 개별 토글** (각자 자유롭게 확대/축소)
- **기술**: SSE (Server-Sent Events), Spring Boot `SseEmitter`

## 6. UI 결정사항 (확정)

### 6.1 교육 내용 (필수)

- **리치 텍스트 에디터** (예: Tiptap)
- **HTML 저장**
- **빈 값으로 개설 불가** (NOT NULL + validation)

### 6.2 첨부자료 (선택)

- **콘텐츠 라이브러리에서 선택** (이미지, YouTube URL, 자체 영상, PDF)
- **세션-콘텐츠 매핑** (M:N)
- **세션별 override 설명** 가능 (예: "오늘은 이 슬라이드의 ○○ 부분 중점")

### 6.3 풀스크린 동작

- 이미지/영상/PDF 모두 클릭 시 풀스크린 모달
- 우측 상단 X 버튼으로 닫기
- 풀스크린 중 슬라이드 변경 시: 풀스크린 유지, 사용자가 닫으면 현재 슬라이드 표시
- 영상 시작 위치: 매번 0초부터

## 7. 권한 결정사항 (확정)

### 7.1 권한 체계

Prafta 기본 4단계:

| 권한 코드 | 설명 |
|---|---|
| `master` | 회사 최고 권한 |
| `safe` | 안전관리 최고 권한 |
| `hr` | 근태 최고 권한 |
| `999999` | 일반 사용자 (근로자) |

기본 4개 외 회사별 커스텀 권한 가능 (화면/버튼 단위).

### 7.2 TBM 관련 권한 매트릭스

| 액션 | 권한 |
|---|---|
| 회사 공통 콘텐츠 등록/수정/삭제 | master, safe |
| 사업장 콘텐츠 등록/수정/삭제 | safe + 회사별 커스텀 권한 |
| 콘텐츠 사용 (TBM에 첨부) | 모든 관리자 권한 (자기 사업장 + 회사 공통) |
| TBM 세션 개설/진행/종료 | safe + 회사별 커스텀 권한 |
| 강제 종료, 미이수 처리 | 개설자 본인 또는 safe |
| 이력 조회 | master, safe + 회사별 커스텀 권한 |
| TBM 참여 (근로자) | 999999 + 본인 디바이스 |
| TBM 참여 (일용직 QR) | 관리자가 대신 처리 |

### 7.3 권한 체크 구현

- 기존 권한 시스템 활용 (Claude Code가 로컬에서 확인)
- JWT 토큰 → `JwtUtil.getAllClaimsAsMap()` 패턴
- 회사별 커스텀 권한: 화면/버튼 권한 체크 로직 활용

## 10. 외부 의존성 (Claude Code 로컬 확인 필요)

다음 테이블/모듈은 **이미 Prafta에 구현되어 있으며**, Claude Code가 로컬에서 정확한 컬럼명과 구조를 확인합니다.
헷갈리면 사용자에게 질문하도록 안내합니다.

| 항목 | 일반 참조명 (본 문서 사용) | 비고 |
|---|---|---|
| 정규직 사용자 | `TB_USER` | PK: `USER_ID` |
| 일용직 사용자 | `TB_DAILY_USER` | PK: `DAILY_USER_NO`, QR 토큰 발급 구조 |

### 10.1 기존 TBM 구현과의 매핑

⚠️ **중요**: Prafta에는 이미 TBM 콘텐츠/자료 등록 기능 일부가 구현되어 있습니다.

본 작업지시서는 **목표 설계(To-Be)**를 기술하며, 다음 원칙으로 Claude Code가 작업합니다:

1. **이미 구현된 부분 확인 우선**
   - 콘텐츠/자료 등록 관련 기존 테이블·서비스·컨트롤러 파악
   - 본 문서의 `TB_EDU_CONTENT`/`TB_EDU_SESSION_CONTENT` 등과 매핑

2. **테이블/컬럼명이 다른 경우**
   - 기존 명명이 합리적이면 → 기존 유지, 본 문서 참조만 매핑
   - 본 문서 명명이 더 좋으면 → 사용자와 협의 후 마이그레이션

3. **기능 중복 시**
   - 기존 기능을 우선 활용, 부족한 부분만 본 문서 사양으로 보강
   - 단, 본 문서의 결정사항(예: 위험성평가 연계, 일용직 QR 통합 등)은 누락되지 않게 검증

4. **불확실하면 사용자에게 질문**
   - "기존 TBM 모듈의 X 기능과 본 문서의 Y 기능이 매핑되는지 확인 부탁드립니다"
   - 임의 판단으로 진행하지 않음

본 문서의 8개 테이블 구조는 **목표 형태**이며, 실제 구현에서는 기존 테이블과 통합·매핑하는 과정이 필요합니다.
