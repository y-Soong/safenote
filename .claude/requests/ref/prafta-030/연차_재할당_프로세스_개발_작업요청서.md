## 1. 핵심 컨텍스트

### 1.1 시스템 구조 전제

- **실제 입사일**: 사실 데이터, 입력 오류 정정 외엔 변경하지 않음
- **인정 경력**: 별도 입력 항목 (개월 단위), 회사 약정으로 인정하는 타 직장 경력 등
- **산정 근속**: `실제 입사일 + 인정 경력`. 연차 부여 계산의 기준
- **연차 부여 엔진**: 데이터 변경 시 즉시 적용 안 됨. 별도 화면에서 관리자가 특정 인원 선택 후 엔진 실행
- **법정 부여 규칙 3종**: 입사일 기준 / 회계연도 비례부여 / 회계연도 차년도 일괄부여
- **가산연차**: 기본값 3년차부터 매 2년 1일 (회사별 커스텀 가능), 최대 25일

### 1.2 트리거 이벤트

연차 부여 엔진의 입력 데이터가 변경되는 케이스:

1. 실제 입사일 변경 (드물게 발생 - 입력 오류 정정)
2. 인정 경력 변경 (빈번 - 경력 증빙 제출, 추가 인정 등)
3. 법정 부여 규칙 변경 (1차 MVP에선 변경 불가, CS 처리)

### 1.3 동작 방식 핵심

```
[일반 흐름]
1. 인사담당자가 사용자 정보 변경 (입사일/인정경력 등)
2. 변경 사항은 즉시 적용되지 않음
3. 별도 화면에서 관리자가 재계산 대상 인원 선택
4. 재할당 옵션 선택 (옵션 1/2/3)
5. 시뮬레이션 결과 미리보기
6. 확정 시 적용
```

## 2. 재할당 옵션 정의

### 2.1 옵션 1: 기존 부여 유지 + 누락분만 소급 부여

**동작 방식:**
```
새 기준 부여 누적량(소멸 제외) - 변경 전 부여 누적량(소멸 제외) = 누락분
누락분 > 0: 누락분 추가 부여
누락분 <= 0: 추가 부여 없음 (회수 없음, 옵션 2와 동일 동작)
```

**핵심 원칙:**
- 사용한 연차는 부여 누적에 포함 (직원에게 제공한 혜택이므로)
- 차액은 "잔여량"이 아닌 "부여량" 기준 (정책 Y)
- 회사 손해 최소화 + 직원 권리 보장 균형

**계산 예시:**
```
[케이스]
변경 전: 월차 7일 부여, 5일 사용, 잔여 2일
새 기준: 2년차 연차 15일 받았어야 함

계산:
누락분 = 15 - 7 = 8일 추가 부여

결과:
- 기존 월차 7일 이력 유지 (잔여 2일)
- 추가 부여 2년차 연차 8일
- 직원 총 보유: 10일 (잔여 월차 2 + 추가 8)
- 직원 총 누적 혜택: 사용 5 + 보유 10 = 15일 (새 기준과 일치)
```

### 2.2 옵션 2: 기존 부여 유지 + 신규 부여만 변경된 입사일로 계산

**동작 방식:**
```
- 변경 시점 기준 현재 보유 연차는 모두 그대로 유지
- 변경 시점 이후 발생하는 부여만 새 산정 근속 기준으로 계산
- "신규 부여 시점"은 설정된 법정 부여 규칙에 따라 결정
  - 입사일 기준 모드: 다음 입사응당일이 도래하는 시점
  - 회계연도 모드: 다음 회계연도 시작일
```

**계산 예시:**
```
[케이스]
오늘: 2026-05-26
법정 부여 규칙: 입사일 기준
실제 입사일: 2026-05-25 (어제)
인정 경력: 48개월 → 60개월 (12개월 추가 인정)
변경 전 산정 근속: 4년차
변경 후 산정 근속: 5년차

옵션 2 적용:
- 현재 보유 연차 그대로 유지
- 다음 부여 시점 (2027-05-25)에 새 산정 근속(6년차) 기준으로 발생
- 6년차 연차 17일 발생 예정 (가산 +2)
```

### 2.3 옵션 3: 모든 부여 삭제 후 재계산

**동작 방식:**
```
- 변경 전 발생 이력을 모두 CANCELLED 상태로 변경
- 새 산정 근속 기준으로 처음부터 다시 발생 시뮬레이션
- 사용한 연차는 별도 추적하지 않음 (사용 이력은 근태 기록에만 남음)
```

**중요 제약:**
- 입력 오류 정정 사유에만 사용 권장 (UI 가이드 메시지로 안내)
- 사유는 자유 입력 (드롭다운 미리 지정 없음)
- 사용한 연차는 별도 차감 처리 없음
- 변경 전 데이터는 영구 보관 (감사 추적)

**계산 예시:**
```
[케이스]
변경 전: 2년차 연차 15일 부여, 3일 사용, 잔여 12일
새 기준: 2년차 연차 15일 (동일)

옵션 3 적용:
- 변경 전 부여 이력 CANCELLED
- 새 기준 2년차 연차 15일 신규 발생
- 사용한 3일은 별도 차감 없음 → 직원 보유 15일

결과:
- 회사 입장에서는 3일 손해 (이미 사용분 + 신규 부여)
- 그래서 입력 오류 정정 시에만 사용 권장
```

## 3. 1년 미만 월차 발생 기준

**채택 방식: 산정 근속 기준 (선택지 X)**

```
[발생 조건]
산정 근속 < 1년 (12개월): 1년 미만 월차 발생
산정 근속 >= 1년: 1년 미만 월차 미발생, 본 연차만 발생

[예시]
- 실제 입사일 2026-05-25, 인정 경력 0개월 → 산정 근속 1일 → 월차 발생
- 실제 입사일 2026-05-25, 인정 경력 6개월 → 산정 근속 6개월 → 월차 발생
- 실제 입사일 2026-05-25, 인정 경력 12개월 → 산정 근속 12개월 → 본 연차 즉시 발생
- 실제 입사일 2026-05-25, 인정 경력 48개월 → 산정 근속 4년차 → 본 연차 16일 발생
```

**근거:**
- 인정 경력을 포함한 산정 근속이 회사 정책상 "계속근로기간"으로 인정됨
- 산정 근속 1년 이상이면 1년 미만 월차의 입법 취지(신입자 보호)와 무관
- 한국 실무에서 일반적인 처리 방식

## 4. 입사일 변경 방향별 동작

### 4.1 과거로 변경 (산정 근속 증가)

- 인정 경력 증가 또는 실제 입사일 앞당김
- 새 기준 보유했어야 할 양 > 기존 보유량 (일반적)
- 옵션 1: 누락분 추가 부여 동작
- 옵션 2: 다음 부여 시점에 새 기준 적용
- 옵션 3: 회수 + 재부여

### 4.2 미래로 변경 (산정 근속 감소)

- 인정 경력 감소 또는 실제 입사일 늦춤 (드문 케이스)
- 새 기준 보유했어야 할 양 < 기존 보유량
- 옵션 1: 회수 없음 → 옵션 2와 동일 동작 (UI 안내)
- 옵션 2: 다음 부여 시점에 새 기준 적용
- 옵션 3: 회수 + 재부여 (사용한 연차는 추적 안 함)

## 5. 경계 케이스 처리

### 5.1 1년차 미만 → 1년차 이상 (산정 근속 증가로 경계 넘김)

```
[케이스]
변경 전: 산정 근속 0년 7개월 → 월차 7일 부여, 5일 사용, 잔여 2일
새 기준: 산정 근속 2년 7개월 → 2년차 연차 15일 보유했어야 함

옵션 1 적용:
- 기존 월차 7일 발생 이력 유지 (LEAVE_LAW_TYPE: STATUTORY_MONTHLY)
- 누락분 8일 추가 부여
  - LEAVE_LAW_TYPE: STATUTORY_ANNUAL (2년차 연차)
  - GRANT_REASON: INSADAY_CHANGE_BACKFILL
- 직원 보유: 잔여 월차 2일 + 추가 연차 8일 = 10일
```

### 5.2 1년차 이상 → 1년차 미만 (산정 근속 감소로 경계 넘김)

```
[케이스]
변경 전: 산정 근속 2년 5개월 → 2년차 연차 15일 보유
새 기준: 산정 근속 0년 5개월 → 월차 5일만 받았어야 함

옵션 1, 2 적용:
- 기존 2년차 연차 15일 그대로 유지 (회수 없음)
- 추가 부여 없음
- UI 안내: "본래 회수되어야 할 10일이 있으나 회수하지 않습니다"

옵션 3 적용 (입력 오류 정정 시):
- 기존 발생 이력 CANCELLED
- 새 기준 월차 5일 신규 발생
- 사용한 연차가 있어도 별도 차감 없음
```

## 6. 데이터 모델

### 6.1 발생 이력 테이블

```sql
TB_LEAVE_GRANT_HIST (연차 발생 이력)
├── GRANT_ID                BIGINT PRIMARY KEY
├── USER_ID                 BIGINT NOT NULL
├── GRANT_DATE              DATE NOT NULL          -- 발생일
├── GRANT_DAYS              DECIMAL(5,2) NOT NULL  -- 발생 일수
├── LEAVE_LAW_TYPE          VARCHAR(30) NOT NULL   -- 법정 분류 (아래 Enum)
├── GRANT_REASON            VARCHAR(30) NOT NULL   -- 발생 사유 (아래 Enum)
├── EXPIRE_DATE             DATE NOT NULL          -- 소멸일
├── STATUS                  VARCHAR(20) NOT NULL   -- 상태 (아래 Enum)
├── RELATED_HIRE_DATE       DATE                   -- 관련 입사일 (변경 시점 기준)
├── RELATED_SERVICE_MONTHS  INT                    -- 관련 인정 경력
├── PARENT_GRANT_ID         BIGINT                 -- 보전 부여인 경우 원본 참조
├── REMARK                  TEXT                   -- 비고 (수동 부여 시 사유 등)
├── GRANTED_BY              BIGINT NOT NULL        -- 작업자
├── CREATED_AT              TIMESTAMP NOT NULL
├── UPDATED_AT              TIMESTAMP NOT NULL
└── INDEX (USER_ID, GRANT_DATE)
```

### 6.2 Enum 정의

**LEAVE_LAW_TYPE (법정 분류):**
```
STATUTORY_MONTHLY    : 1년 미만 월차 (근기법 60조 2항)
STATUTORY_ANNUAL     : 1년 이상 연차 (근기법 60조 1항)
STATUTORY_BONUS      : 가산연차 (근기법 60조 4항)
AGREED               : 회사 약정 휴가
```

**GRANT_REASON (발생 사유):**
```
REGULAR_ACCRUAL          : 정상 자동 발생 (부여 엔진 실행 결과)
INSADAY_CHANGE_BACKFILL  : 입사일 변경 보전 (옵션 1 추가 부여)
HIREDATE_RESET           : 입사일 변경 후 옵션 3에 의한 재부여
MANUAL                   : 관리자 수동 부여
CORRECTION               : 오류 정정 (옵션 3 사용 시 기존 이력 취소 후 재부여)
```

**STATUS (상태):**
```
ACTIVE      : 정상 부여, 사용 가능
USED        : 사용 완료
EXPIRED     : 소멸
CANCELLED   : 부여 취소 (옵션 3 적용 등으로 무효화)
```

## 7. 핵심 함수 명세

### 7.1 산정 근속 계산

```
calculateServiceMonths(userId, baseDate): int
  - 실제 입사일과 인정 경력을 합산한 산정 근속 (개월)
  - baseDate 기준으로 계산
  - 산정 근속 < 12개월 → 1년 미만으로 판단
  - 산정 근속 >= 12개월 → 1년 이상으로 판단
```

### 7.2 새 기준 부여 누적 계산

```
calculateExpectedGrantTotal(
    userId,
    asOfDate,           // 기준 날짜 (보통 오늘)
    hireDate,           // 산정에 사용할 입사일
    serviceMonths,      // 산정에 사용할 인정 경력
    leaveAccrualRule    // 법정 부여 규칙
): GrantSimulationResult
```

**반환 값:**
```
{
  totalGranted: BigDecimal,        // 누적 부여량 (소멸분 제외)
  activeBalance: BigDecimal,       // 현재 살아있는 부여량
  grantHistory: List<GrantEntry>,  // 시뮬레이션된 발생 이력
  expectedNextGrant: GrantEntry    // 다음 발생 예정 정보
}
```

**GrantEntry 구조:**
```
{
  grantDate: Date,
  grantDays: BigDecimal,
  leaveLawType: LeaveLawType,
  expireDate: Date,
  status: GrantStatus  // 시뮬레이션이므로 ACTIVE/EXPIRED 중 하나
}
```

### 7.3 누락분 계산 (옵션 1)

```
calculateSupplementDays(
    userId,
    oldHireDate, oldServiceMonths,
    newHireDate, newServiceMonths,
    leaveAccrualRule,
    asOfDate
): SupplementResult
```

**계산 로직:**
```
oldExpected = calculateExpectedGrantTotal(userId, asOfDate, oldHireDate, oldServiceMonths, rule)
newExpected = calculateExpectedGrantTotal(userId, asOfDate, newHireDate, newServiceMonths, rule)

supplement = newExpected.totalGranted - oldExpected.totalGranted

if (supplement > 0):
  → 추가 부여 supplement 일수
else:
  → 추가 부여 없음 (옵션 2와 동일 동작)
```

**반환 값:**
```
{
  supplementDays: BigDecimal,        // 추가 부여 일수 (음수면 0 처리)
  shouldWithdrawDays: BigDecimal,    // 본래 회수되어야 할 일수 (UI 표시용, 실제 회수 안 함)
  leaveLawTypeForSupplement: LeaveLawType,  // 추가 부여분의 법정 분류
  expireDateForSupplement: Date,     // 추가 부여분의 소멸일
}
```

**추가 부여분의 소멸일 결정 로직:**
- 새 기준으로 동일한 발생 항목(예: 2년차 연차)의 정상 소멸일과 동일하게 설정
- 예: 새 기준이 2026-03-10에 2년차 연차 발생이면 소멸일은 2027-03-09

### 7.4 재할당 적용

```
applyReallocation(
    userId,
    oldHireDate, oldServiceMonths,
    newHireDate, newServiceMonths,
    option: ReallocationOption,
    reason: String,
    operatorId: Long
): ReallocationResult
```

**처리 흐름:**
```
Option 1:
  - calculateSupplementDays() 호출
  - supplementDays > 0이면 발생 이력 INSERT (GRANT_REASON: INSADAY_CHANGE_BACKFILL)
  - 사용자 정보의 hire_date / service_months 업데이트
  - 변경 이력 TB_HIREDATE_CHANGE_LOG INSERT

Option 2:
  - 사용자 정보의 hire_date / service_months 업데이트
  - 발생 이력 변경 없음
  - 변경 이력 TB_HIREDATE_CHANGE_LOG INSERT
  - 다음 부여 엔진 실행 시 새 값 기준으로 동작

Option 3:
  - 현재 ACTIVE/USED 상태 발생 이력을 모두 CANCELLED로 변경
  - 새 산정 근속 기준으로 발생 이력 새로 시뮬레이션 후 INSERT
  - 사용 이력은 별도 차감 처리 없음
  - 변경 이력 TB_HIREDATE_CHANGE_LOG INSERT
```

### 7.5 시뮬레이션 (적용 전 미리보기)

```
previewReallocation(
    userId,
    newHireDate, newServiceMonths,
    leaveAccrualRule
): ReallocationPreview
```

**반환 값:**

- 재계산 대상 사용자 다중 선택 가능
- 필터: "재계산 대기 상태", "특정 부서/조직", "변경 일자 범위" 등
- 엑셀 업로드도 지원 (1차 MVP 범위 결정 필요)

### 8.3 옵션 선택 화면

```
[변경 시 옵션 선택 모달]

옵션 1: 기존 부여 유지 + 누락분만 소급 부여 (기본 선택)
  - 시뮬레이션 결과: +N일 추가 부여 예정
  - 추가 부여분 소멸일: YYYY-MM-DD

옵션 2: 기존 부여 유지 + 신규 부여만 변경된 입사일로 계산
  - 다음 부여 시점: YYYY-MM-DD
  - 그때 발생할 일수: N일

옵션 3: 모든 부여 삭제 후 재계산 ⚠️
  - 주의: 연차를 모두 밀고 다시 만드는 작업입니다.
    입사일 자체가 잘못 입력된 경우에만 사용하세요.
  - 사유 입력 (필수, 자유 입력)
  - 취소될 부여 이력: N건 (N일)
  - 새로 생성될 부여 이력: N건 (N일)
```

### 8.4 시뮬레이션 결과 미리보기

**필수 표시 정보:**

```

- 변경 전 입사일 / 산정 근속
- 변경 후 입사일 / 산정 근속
- 변경 사유

[변경 전 발생 이력]
- 발생일, 일수, 분류, 소멸일, 상태
- 누적 부여량 / 현재 보유량

[새 기준 발생했어야 할 이력]
- 발생일, 일수, 분류, 소멸일
- 누적 부여량 / 보유했어야 할 양

[옵션별 처리 결과]
- 옵션 1: 추가 부여 N일, 최종 보유 M일
- 옵션 2: 다음 부여 시점/일수, 현재 보유 M일

[회수 표시 - 미래 변경 시]
⚠️ 본래 회수되어야 할 연차 N일이 있으나 회수하지 않습니다.
   회수 대상 상세:
   - YYYY-MM-DD 발생 X일 중 Y일
   - 사유: 새 기준 산정 근속 미달

[다음 부여 일정 변화]
- 변경 전 다음 부여 예정: YYYY-MM-DD, N일
- 변경 후 다음 부여 예정: YYYY-MM-DD, N일
```

### 8.5 안내 메시지 (상황별)

**미래 변경 시 (산정 근속 감소):**
```

이미 발생한 연차는 회수되지 않으므로, 옵션 1과 옵션 2가 동일하게 동작합니다.
```

```
추가 부여분은 법정 연차로 분류됩니다.
```

**경계 케이스 (1년차 이상 → 1년차 미만):**
```
인정 경력 변경으로 직원이 1년차 이상에서 1년차 미만 상태가 됩니다.
기존에 받은 본 연차는 회수되지 않습니다.
연차를 정리하려면 옵션 3을 사용하세요.
```

**옵션 3 선택 시:**

```
- 입사일 자체가 잘못 입력된 경우에만 사용하시기 바랍니다.
```

## 9. 미해결 사항 및 결정 사항

### 9.1 확정 사항

| 항목 | 결정 | 비고 |
|---|---|---|

| 옵션 2 다음 부여 시점 | 법정 부여 규칙에 따름 | A 선택지 |
| 변경 사유 분류 | 사전 정의 없음, 자유 입력 | UI 가이드 메시지로 안내 |
| 미리보기 정보 범위 | 모든 정보 표시 + 회수 표시 | 결정사항 6 |
| 1년 미만 월차 발생 기준 | 산정 근속 기준 (X 선택지) | 인정 경력 반영 |
| 자동 회수 정책 | 없음 (옵션 3만 예외) | a안 |
| 옵션 1, 2의 미래 변경 시 | 동일 동작 (UI 안내) | a안 |
| 관리자 회수 기능 | 없음 | 옵션 3으로 대체 |
| 부여 취소 기능 | 1차 MVP 제외, 2차 보류 | CS 대응 |

### 9.2 1차 MVP 범위

**포함:**
- 재할당 옵션 1, 2, 3 모두 구현
- 자동 차액 계산 + 시뮬레이션 미리보기
- 변경 이력 영구 보관
- 모바일 사용자 화면 (보유 연차, 만료일 표시)
- 안내 메시지 (상황별)

**제외 (2차 이후):**
- 부여 취소 기능 (관리자 실수 정정용)
- 회계연도 기준 자동 형평성 보전
- 연차 사용 촉진 자동화
- 단시간 근로자 비례 부여
- 약정 휴가 발생 규칙 커스터마이징

## 13. 작업 시 유의사항

1. **단순화 우선**: 1차 MVP는 복잡한 옵션 분기보다 핵심 동작의 정확성에 집중

5. **테스트 우선**: TC-101 ~ TC-107 (경계 케이스)는 반드시 통과 확인 후 배포
