\# 작업 명령서: HireDateEditPop 처리방식 자동 계산 폐기 및 수동 입력 전환



> 작성일: 2026-05-26

> 대상: Claude Code

> 우선순위: 높음



\---



\## 1. 작업 배경



\### 1.1 현재 문제

\- HireDateEditPop의 처리방식 자동 계산(KEEP\_AND\_BACKFILL, KEEP\_AND\_APPLY\_NEW, RESET\_ALL)이 케이스에 따라 회사/근로자 유불리가 일률적이지 않음

\- 명세서 정의와 실제 시스템 동작이 어긋나는 케이스 발견됨 (예: 17개 부여 케이스)

\- 자동 계산에 대한 노무적 정합성 검증이 어려움



\### 1.2 변경 방향

\- 처리방식 자동 계산 폐기

\- 관리자가 직접 연차 일수 조정

\- 시스템은 검증과 이력 기록만 수행

\- 자동 부여는 변경 후 다음 배치(자동 발생 규칙)부터 새 기준으로 동작

\## 2. 작업 범위



\### 2.1 폐기 대상



\*\*프론트엔드 (HireDateEditPop):\*\*

\- 처리방식 선택 라디오 버튼 UI 제거

&#x20; - KEEP\_AND\_BACKFILL (기존 부여 유지 + 누락분만 소급 부여)

&#x20; - KEEP\_AND\_APPLY\_NEW (기존 부여 유지 + 신규 부여만 변경된 입사일로 계산)

&#x20; - RESET\_ALL (모든 부여 삭제 후 재계산)

\- 영향 분석 영역에서 "처리방식 시뮬레이션" 부분 제거

&#x20; - 누락된 부여, 다음 부여 예정 시점은 유지



\*\*백엔드 (관련 서비스 로직):\*\*

\- `calculateBackfillShortfall` 함수 폐기 또는 비활성화

\- HANDLING\_TYPE 분기 로직 제거

\- 자동 부여/회수 처리 로직 제거 (관리자가 직접 입력하는 값으로 대체)



\### 2.2 신규 구현



\*\*프론트엔드 (HireDateEditPop):\*\*

\- 현재 연차 상태 표시 영역 (영향 분석 하단에 배치)

&#x20; - 법정 휴가: 부여 / 사용 / 잔여

&#x20; - 법정 휴가 외(약정): 부여 / 사용 / 잔여

&#x20; - 전체: 부여 / 사용 / 잔여

\- 수정할 연차 일수 입력 필드

&#x20; - 현재 부여량을 보여주고, 수정 후 부여량 입력

&#x20; - 차액 자동 계산 표시 (예: "현재 17일 → 수정 15일, -2일 회수 예정")

\- 회수 발생 시 회수 사유 필수 입력 필드 노출

\- 변경 사유 통합 입력 필드 (입사일 변경 + 연차 조정 사유)



\*\*백엔드:\*\*

\- 수동 일수 조정 처리 로직

\- 추가 부여 시 소급 발생일 계산 로직 (자세한 내용은 §5 참조)

\- 회수 처리 로직 (CANCELLED 상태 전환)

\- 검증 로직 (회수량 검증)

\### 3.2 검증 규칙



\*\*입력 검증:\*\*

```

\- 변경할 입사일: 필수

\- 수정할 연차 일수: 선택 (입력 안 하면 현재값 유지)

\- 변경 사유: 필수

\- 회수 사유: 회수 발생 시(수정값 < 현재값) 필수

```



\*\*비즈니스 검증:\*\*

```

검증식:

&#x20; 현재 부여량 - 수정할 부여량 > 잔여량 → 저장 불가

&#x20; 

의미: 사용한 연차는 회수 불가

&#x20; - 사용한 연차 = 현재 부여량 - 잔여량

&#x20; - 회수 가능한 최대량 = 잔여량

&#x20; - 회수 시도량 = 현재 부여량 - 수정할 부여량

&#x20; - 회수 시도량이 잔여량 초과 시 사용한 연차까지 회수해야 함 → 차단



\[잔여량 계산 시 포함 항목]

\- ACTIVE 상태 연차

\- 휴가 신청 승인 대기 상태 (USED 직전)

\- 휴가 신청 승인 완료 + 사용 예정 상태

\- ↑ 모두 "사용한 것"으로 카운트되지 않지만 회수 불가 대상



\[저장 차단 시 메시지]

"회수 가능한 연차는 N일입니다. (잔여 N일)

&#x20;이미 사용했거나 사용 예정인 연차는 회수할 수 없습니다."

```

\## 5. 추가 부여 처리 (차액 > 0)



\### 5.1 발생일 결정 - 소급 발생일 + 오늘 날짜 폴백



```

\[1단계: 새 입사일 기준 미부여 발생 일정 계산]

\- 새 입사일 기준 발생했어야 할 발생일 리스트 산출

\- 기존에 부여된 발생일과 비교

\- 미부여된 발생일 식별 (오늘 이전 날짜만)

\- 빠른 발생일 순으로 정렬



\[2단계: 추가 일수만큼 소급 부여]

\- 미부여 발생일 리스트에서 빠른 순서대로 부여

\- 각 발생일에 대해:

&#x20; - GRANT\_DATE: 해당 미부여 발생일

&#x20; - EXPIRE\_DATE: 해당 발생일 기준 정상 소멸일

&#x20; - LEAVE\_LAW\_TYPE: 시스템 자동 판단 (§5.2 참조)

&#x20; - GRANT\_REASON: 'INSADAY\_CHANGE\_BACKFILL'



\[3단계: 미부여 발생일 소진 후 잔여 일수가 있으면]

\- 오늘 날짜로 추가 부여 (A안 폴백)

\- GRANT\_DATE: 오늘

\- EXPIRE\_DATE: 오늘 + 1년 (또는 회사 정책에 따른 소멸일)

\- LEAVE\_LAW\_TYPE: 시스템 자동 판단

\- GRANT\_REASON: 'MANUAL\_OVERAGE' (초과 약정 부여)

```



\### 5.2 LEAVE\_LAW\_TYPE 자동 판단 로직



```

판단 시점: 추가 부여의 GRANT\_DATE 기준



\[판단 로직]

새 입사일 기준 GRANT\_DATE 시점의 산정 근속이:

\- 1년 미만 → STATUTORY\_MONTHLY

\- 1년 이상 \~ 3년 미만 → STATUTORY\_ANNUAL

\- 3년 이상 → STATUTORY\_BONUS (가산연차)

\- 회사 약정 휴가 영역이면 → AGREED



\[예시]

새 입사일 2025-05-11, 추가 부여 발생일 2025-06-11

→ 산정 근속 1개월 → STATUTORY\_MONTHLY



새 입사일 2024-05-11, 추가 부여 발생일 2025-05-11

→ 산정 근속 1년 → STATUTORY\_ANNUAL

```



\### 5.3 처리 예시



\*\*예시 1: 케이스 2 (월차 발생 중 입사일 정정)\*\*

```

입사일: 2025-07-11 → 2025-05-11 (2개월 앞당김)

오늘: 2025-09-26

현재 부여: 월차 2일 (2025-08-11, 2025-09-11)

관리자 입력: 부여 2일 → 4일 (+2일)



처리:

1\. 새 입사일 기준 미부여 발생일 계산

&#x20;  - 발생했어야 할 일정: 2025-06-11, 2025-07-11, 2025-08-11, 2025-09-11

&#x20;  - 기존 부여: 2025-08-11, 2025-09-11

&#x20;  - 미부여: 2025-06-11, 2025-07-11

2\. 추가 2일 부여

&#x20;  - 2025-06-11: 1일 (STATUTORY\_MONTHLY, INSADAY\_CHANGE\_BACKFILL)

&#x20;  - 2025-07-11: 1일 (STATUTORY\_MONTHLY, INSADAY\_CHANGE\_BACKFILL)

3\. 각 부여의 소멸일: 새 입사일 기준 만 1년 시점 = 2026-05-10

```



\*\*예시 2: 케이스 3 (만 N년 도래 변경)\*\*

```

입사일: 2023-08-15 → 2023-03-15 (5개월 앞당김)

오늘: 2026-05-26

현재 부여: 본 연차 15일 (2025-08-15 발생, 2025-08-14 소멸 예정)

관리자 판단: 새 기준 만 3년 도래(2026-03-15)이 이미 지남 → 가산연차 적용

관리자 입력: 부여 15일 → 16일 (+1일)



처리:

1\. 새 입사일 기준 미부여 발생일 계산

&#x20;  - 2024-03-15 발생 (15일), 2025-03-15 발생 (15일), 2026-03-15 발생 (16일, 가산)

&#x20;  - 기존 부여와 매칭 안 됨 (기존은 8월 기준)

2\. 차액 +1일에 대해 미부여 발생일 사용

&#x20;  - 가장 빠른 미부여: 2024-03-15 발생분

&#x20;  - 이미 소멸일 지남 → 다음 미부여로

&#x20;  - 2026-03-15에 1일 추가 부여 (STATUTORY\_BONUS, INSADAY\_CHANGE\_BACKFILL)

&#x20;  - 소멸일: 2027-03-14

```

\## 6. 회수 처리 (차액 < 0)



\### 6.1 회수 우선순위



```

1순위: 소멸일 가까운 순 (먼저 소멸할 부여를 먼저 회수)

2순위: 부여일 최근 순 (같은 소멸일이면 최근 부여를 먼저 회수)

3순위: GRANT\_ID 큰 순 (동률 시 최신 데이터 우선)

```



\### 6.2 회수 처리 방식



```

\[처리 흐름]

1\. 회수 대상 부여 이력 조회

&#x20;  - STATUS = ACTIVE

&#x20;  - USER\_ID = 대상 사용자

&#x20;  - 회수 우선순위로 정렬

2\. 차액(음수)의 절대값만큼 회수

&#x20;  - 부여 이력 단위로 처리

&#x20;  - 한 부여 이력에서 부분 회수 가능

3\. 회수된 부여 이력 처리

&#x20;  - 전체 회수: STATUS = CANCELLED

&#x20;  - 부분 회수: GRANT\_DAYS 차감 (또는 별도 회수 이력 생성, 결정 필요)

4\. 회수 이력 기록

```



\### 6.3 부분 회수 처리 방식 결정 필요



```

선택지 A: 부여 이력의 GRANT\_DAYS 직접 차감

\- 단순함

\- 원본 일수 추적 어려움



선택지 B: 별도 회수 이력 테이블 사용

\- TB\_LEAVE\_WITHDRAW\_HIST 신설

\- 원본 부여는 그대로, 회수만 별도 기록

\- 추적 명확



선택지 C: 부여 이력 분할

\- 5일 부여 → 3일 회수 시

\- 5일 부여를 CANCELLED 처리

\- 2일짜리 새 부여 이력 생성 (사유: 부분 회수 후 잔여)



\[권장: B - 별도 회수 이력]

\- 원본 보존

\- 회수 사유와 시점 명확히 기록

\- 분쟁 시 입증 자료 명확

```



\### 6.4 회수 예시



```

케이스: 부여 17일 → 15일 수정 (-2일 회수)



현재 부여 이력:

\- ID 1: 5일, 소멸 2026-12-31

\- ID 2: 7일, 소멸 2027-03-15

\- ID 3: 5일, 소멸 2027-05-04



회수 처리:

1\. 소멸일 가까운 순 정렬: ID 1 → ID 2 → ID 3

2\. ID 1에서 2일 회수

&#x20;  - 원본 5일 중 2일 회수

&#x20;  - 부분 회수 이력 생성 (회수 사유, 시점, 작업자)

&#x20;  - 또는 ID 1을 CANCELLED 처리 후 3일짜리 신규 부여

3\. 잔여 부여: ID 1 (3일) + ID 2 (7일) + ID 3 (5일) = 15일 ✓

```

\## 7. Attd\_09 화면 동작 변경



\### 7.1 정책 기준 부여 버튼 동작



```

\[변경 후 동작]

\- 대상: 부여된 연차가 전혀 없는 사용자만 (신규 입사자, 일괄 부여 대상)

\- 기존 부여가 있는 사용자: "변경 없음" 처리 (현재 미리보기와 동일)



\[처리 로직]

1\. 선택된 사용자별로 현재 부여 이력 확인

2\. 부여 이력이 있는 사용자: 변경 없음 (skip)

3\. 부여 이력이 없는 사용자: 연차부여 정책 + 입사일 + 경력 인정 기준으로 산정 부여

4\. 미리보기에 "변경 없음" / "신규 부여" 명확히 구분 표시

```

\## 9. 테스트 시나리오



\### 9.1 정상 케이스



```

TC-001: 입사일만 변경 (연차 조정 안 함)

TC-002: 입사일 변경 + 연차 부여량 증가 (+2일)

TC-003: 입사일 변경 + 연차 부여량 감소 (-2일)

TC-004: 입사일 변경 없이 연차만 조정

TC-005: 신규 입사자 (부여 이력 없음) + Attd\_09 정책 기준 부여

```



\### 9.2 검증 케이스



```

TC-101: 회수 시도량 = 잔여량 (저장 가능)

TC-102: 회수 시도량 > 잔여량 (저장 차단, 에러 메시지)

TC-103: 회수 발생 시 회수 사유 미입력 (저장 차단)

TC-104: 변경 사유 미입력 (저장 차단)

```



\### 9.3 추가 부여 발생일 케이스



```

TC-201: 미부여 발생일 충분 (소급만으로 처리)

TC-202: 미부여 발생일 < 추가 일수 (오늘 날짜 폴백 발생)

TC-203: 미부여 발생일 없음 (모두 오늘 날짜 부여)

TC-204: 새 입사일 기준 만 1년 도래 후 추가 부여 (STATUTORY\_ANNUAL로 분류)

```



\### 9.4 회수 케이스



```

TC-301: 부여 이력 1건에서 전체 회수 (CANCELLED)

TC-302: 부여 이력 1건에서 부분 회수

TC-303: 여러 부여 이력에 걸쳐 회수 (소멸일 순)

TC-304: 동일 소멸일 부여 이력 회수 (부여일 최근 순)

```



\### 9.5 Attd\_09 케이스



```

TC-401: 부여 이력 없는 사용자 → 신규 부여 동작

TC-402: 부여 이력 있는 사용자 → 변경 없음 처리

TC-403: 혼합 (일부 부여 있음, 일부 없음) → 부여 없는 사용자만 처리

```
