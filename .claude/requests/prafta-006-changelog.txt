1. 요청 요약
================================================================================
Attd_05.vue 화면에서 테이블 셀에 근무타입(SCH_CD)을 지정할 때, 다음 날짜는
입력을 막고 사용자에게 고지 — 백엔드+프론트 모두 수정.
(1) 해당 SCH_CD 최초 생성일 이전 날짜.
(2) 스케줄 데이터의 USE_YN이 'N'인 기간(USE_YN은 Y↔N 토글 가능 → 시점별 판정).
참고 테이블: TB_SCH_MGMT(현재본), TB_SCH_MGMT_HIST(이력본).

5. Phase 2(인가) 이월 — siteCd 사업장 권한 검증

security 발견 [High] — saveUserWorkPlans가 요청 바디의 siteCd/userCd를 신뢰해
TB_USER_WORK_PLAN에 기록 → 인증된 사용자가 바디의 siteCd를 위조하면 같은 회사 내
타 사업장 사용자의 근무계획을 생성/수정 가능. [Medium] 다건 요청 시 첫 모델의
siteCd로만 검증.

[처리 방침 — 이월]
- 이 결함은 prafta-008 이전부터 존재한 사전 인가 갭이다(saveUserWorkPlans 자체가
  기존부터 바디 siteCd로 INSERT). prafta-008-002가 그 위에 검증을 얹으며 같은
  siteCd를 쓴 것.
- 단순히 토큰 siteCd로 강제하면 멀티 사업장 관리자(정책 §8.3 Site Switcher)가 깨진다.
  올바른 해법은 TB_USER_SITE_AUTH 기반으로 "요청 siteCd가 사용자에게 부여된 접근
  가능 사업장인지" 검증하는 것 — 정책 §8(3축 권한: 화면권한×사업장권한×조직스코프)
  기반 설계가 필요.
- prafta-006.md 요청 범위(생성일·USE_YN 차단)와 무관하며, 사용자가 앞서 결정한
  "인가는 별도 작업으로 분리"(prafta-004-changelog.txt 섹션 10/12) 방침에 부합.
- → Phase 2 인가 작업(§8 3축 권한)에 포함 권장.

[정보성 — Low] LoggingAspect의 @AfterReturning이 모든 컨트롤러 응답을 INFO 로그로
출력 → getUserWorkPlan 응답의 mblNo(복호화 평문) 등 PII가 로그에 노출. 사전 공통
