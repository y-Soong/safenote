3. 사전부터 깨져 있던 백엔드 빌드 에러 (본 작업 무관)
================================================================================

현재 본 작업과 별개로 백엔드 gradle compileJava는 다음 영역에서 실패합니다.
이 에러들은 `git stash` 후 HEAD에서도 동일하게 발생하며, 본 작업 이전부터
존재합니다 (사용자가 File*/JWT 리팩터링을 진행하다 호출처 일부를 미반영
상태로 커밋한 결과로 추정됩니다).

■ 미반영 호출처
  - prafta-backend/.../app/risk/risk01/controller/AppRisk01Controller.java:62
      Map<String, Object> tokenInfo = jwtUtil.getAllClaimsAsMap(authorization);
      → getAllClaimsAsMap의 반환형이 TokenInfo로 리팩터된 이후 미반영.
  - prafta-backend/.../app/risk/risk01/service/impl/AppRisk01ServiceImpl.java:80, 89, 91, 95
      FileInfoCommand.builder() / toBuilder() / selectFileMgmtCd(FileInfoCommand) /
      FileService.saveFile(FileInfoCommand, MultipartFile)
      → FileInfoCommand에 builder/toBuilder가 더 이상 존재하지 않음.
      → FileInfoQuery로 리팩터링된 흐름과 일치하지 않음.
  - prafta-backend/.../app/chkLst/chkLst01/service/impl/AppChkLst01ServiceImpl.java:98 외
      FileInfoModel.getAnswerDesc() / getItemCd() / getFileName() / getInspectValue()
      → FileInfoModel에 해당 게터가 더 이상 존재하지 않음.
      → 동일 파일에서 FileInfoCommand.builder() 등 위와 동일한 미반영 호출.

■ 처리 결정
  - 본 작업 범위(다중 탭 라우팅 + JWT PII 정리 + 비크리티컬 5건)와 무관.
  - 사용자가 진행 중인 별도 리팩터링의 미완 상태로 보임.
  - 임의 수정 시 사용자의 설계 의도를 어길 위험이 크므로 손대지 않음.
  - 사용자 복귀 후 별도 작업으로 분리하여 처리하기를 권장.

■ 본 작업의 코드 일관성 검증 결과 (사전 에러 외)
  - JwtUtil/TokenInfo/AuthServiceImpl/LoginServiceImpl 변경분에 대해
    호출처 grep 결과 0건의 추가 컴파일 에러가 발생하지 않음.
  - 프론트엔드 vite build 성공 (built in ~16s).

[security 단계에서 직접 수정한 이슈] — 5건
1. prafta-004-001 (Critical) — LoginResponse record에서 userPw 필드 제거 + from() 매핑 1줄 제거
   변경 파일: prafta-backend/.../common/cmm/login/dto/response/LoginResponse.java
   원복: git checkout HEAD -- prafta-backend/src/main/java/com/prafta/common/cmm/login/dto/response/LoginResponse.java

2. prafta-004-004 (Medium) — application.properties의 jwt.expiration을 3600000(1시간)으로 변경.
   '// 14일' 인라인 주석은 .properties 규약 위반(값에 포함됨)이었음 — 별도 라인의 # 주석으로 분리.
   변경 파일: prafta-backend/src/main/resources/application.properties

3. prafta-004-005 (Medium) — LoginServiceImpl.Login의 ActiveTokenCommand "7" → "2" (48시간).
   변경 파일: prafta-backend/.../common/cmm/login/service/impl/LoginServiceImpl.java

4. prafta-004-008 (Low) — App.vue fallback의 검증 조건을 (gv_userCd && gv_userNm)에서
   (gv_cmpnyCd && gv_userCd && gv_userNm && gv_authCd && gv_authLevel)로 강화.
   변경 파일: prafta-web-frontend/prafta-web-frontend/src/App.vue

5. prafta-004-010 (Low) — LoginServiceImpl의 dead code sha256() 메서드 제거 + 사용하지 않게 된
   MessageDigest / NoSuchAlgorithmException / StandardCharsets import 정리.
   변경 파일: prafta-backend/.../common/cmm/login/service/impl/LoginServiceImpl.java

[보류된 이슈] — 4건 (회귀 위험 또는 광범위 audit 필요)
- prafta-004-002 (High) — LoginController GET → POST 전환 + LoginView axios.get → post 동반 변경.
  로그인 흐름 핵심 변경으로 회귀 위험. 사용자 복귀 후 별도 작업으로 권장.
- prafta-004-003 (High) — MyInfoPop의 user-info-lists API 호출이 본인 검증을 클라이언트 입력에
  의존. 백엔드 SQL 분기 또는 본인 전용 API 신설 필요. 사용자 복귀 후 별도 작업으로 권장.
- prafta-004-006 (Medium) — Refresh Token rotation 미구현. AuthServiceImpl에서 RT 회전을
  도입하면 multi-tab race condition도 함께 검토 필요. 사용자 복귀 후 별도 작업으로 권장.
- prafta-004-007 (Medium) — axios.js의 userInfo 자동 첨부 패턴 단계적 제거.
  각 controller가 토큰의 gv_userCd를 신뢰하는지 audit 선행 필요. 사용자 복귀 후 별도 작업으로 권장.
- prafta-004-009 (Low) — refresh timeout 5초로 단축 (UX 권고). 보안 무관, 보류.

[정보성 보고 — 본 작업 무관 사전 상태]
- @NoAuth가 다수 controller에 클래스 레벨로 적용됨. AuthAspect의 pointcut이 클래스 레벨
  @NoAuth를 의도대로 처리하는지 별도 검증 필요. 본 작업 영역 밖.
- TB_AUTH_TOKEN.IP_ADDR / USER_AGENT 컬럼이 INSERT 시 누락되어 항상 NULL.
  정책 §11.3 감사로그 도입 시 별도 작업 필요. ipify 제거 PRAFTA-012와는 무관.

작업일: 2026-05-16

[권한 정책 확인 — common/08-permissions.md]
prafta 권한은 3축 AND 모델: ①화면 권한(Role: 마스터관리자/HR/산업안전관리자, 메뉴별
CRUD) ②사업장 권한(사용자×사업장 매핑) ③조직 스코프(소속 사업장은 자기부서+하위,
관리권한은 담당 정/부만; 타 사업장은 화면권한으로 판단). 코드의
AuthRoleUtils.isManager()(master/hr 2종)는 이 모델의 불완전한 단순화임.

[인증 vs 인가 분리 — 사용자 결정]
006-005는 두 성격이 섞여 있어, 사용자가 "인증 구멍만 지금 수정"을 선택:
- [Phase 1 — 진행] 인증(authentication): 유효 로그인 토큰 필수화. 3축 모델 불필요.
- [Phase 2 — 별도 작업으로 분리] 인가(authorization): 권한 정밀검증·조직 스코프.
  §8 3축 모델 기반 설계 필요. 005-5 전체, 005-2/005-1의 isManager 권한체크가 해당.

12. prafta-006 security·qa 재검증 결과 + 조치
================================================================================
검토일: 2026-05-16

[security 재검토] Critical 1·High 1·Medium 2·Low 1
[qa 재검증] 조건부 PASS (요구사항 충족 8/8, 005-3 비로그인화면 회귀 0건)

[핵심 분석 — 클래스 레벨 @NoAuth는 무효]
AuthAspect의 pointcut은 `!@annotation(...NoAuth)`를 쓴다. Spring AOP의 @annotation()
PCD는 **메서드 레벨** 어노테이션만 매칭하므로, 컨트롤러 **클래스 레벨 @NoAuth는 효력이
없다**. 따라서:
- User01Controller의 클래스 @NoAuth는 무력한 오해 유발 dead code였고, AuthAspect는
  이미 /user01 전 엔드포인트에 JWT를 강제하고 있었음 → SEC-1은 실제 인증 우회가 아님.
- 005-2의 5개 컨트롤러 클래스 @NoAuth 제거도 동작 변화 없는 무해한 정리였음.
- 005-3 baseinfo 수정은 pointcut의 `!execution(...baseinfo.controller..)` **패키지
  제외절**(실효성 있음)을 제거한 것이므로 유효하고 올바른 수정.

[직접 적용한 조치 — 3건]
1. SEC-1 — User01Controller.java: 무효·오해유발 클래스 @NoAuth + import 제거.
2. QA Q-1 (update-my-passwd) — POST /user01/update-my-passwd 인증+본인강제 완전 수정.
   MyPasswdParam.from(request) → from(request, tokenInfo). 대상 cmpnyCd/userCd를
   request 무시하고 토큰값으로 강제(본인 비번 변경이므로 userCd도 강제). 컨트롤러에
   @RequestHeader Authorization required=true 추가. (이 엔드포인트는 audit이 짚었으나
   planner가 "미존재"로 오판해 005-1에서 누락됐던 것 — 인증/본인강제는 Phase 1 범주라
   본 차수에서 해소.)
3. SEC-3 — LoginView.vue: fnSubmitLogin의 console.log(평문 ID/비밀번호) 제거 +
   catch의 console.log(err) 제거. (006-001 의도와 모순되던 잔존 코드.)
