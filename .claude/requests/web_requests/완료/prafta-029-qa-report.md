## 4. 핵심 발견 / 플래그

### (a) b(백필)=0 → 세 처리방식 수치 동일 — 정책 정합 ✅
- 72셀 전부 b=0, 따라서 BACKFILL/APPLY_NEW/RESET_ALL의 부여 **일수**가 동일.
- 근거: ① 모든 과거 발생분의 12개월 유효기간(AXIS6)이 TODAY 이전에 소멸 → `computeBackfillPeriods`/`addFiscalBackfillPeriods`가 `availTo < today` 제외(§8.5.8 소멸분 되살리지 않음). 본 입사일들은 모두 최근이라 소급 대상이 당해 1건뿐이고 그건 당기 c가 가져감. ② 처리방식 차이는 **순증 일수**가 아니라 **취소/재발급 메커니즘**에서만 발생: RESET_ALL은 기존 STATUTORY_* 를 CANCELED 후 `_R{HIST_ID}` 키로 재발급. 신규 사용자(기부여 0)라 취소 0건 → KEEP과 동값이 **설계대로**.
- 확인 필요: 기부여 보유 실데이터에서 RESET_ALL의 cancelCount·재발급 멱등키 동작은 본 테스트로 관측 불가.

### (b) P2(MONTHLY_ONLY) = P4(NEXT_YEAR_BULK) 전 셀 동일 — ⚠️ 미구현 갭 (Medium)
- `resolveFiscalEntitlement`: `crossed>=1`→만연차, `crossed==0 && PRORATE`→비례, **그 외(MONTHLY_ONLY/NEXT_YEAR_BULK)→본연차 미부여 동일 폴백**. 클래스 주석(L42·L519~520)도 "PRORATE는 prafta-023로 분리, NEXT_YEAR_BULK로 폴백", "MONTHLY_ONLY와 NEXT_YEAR_BULK는 022에서 동일 처리"라 명시 — **의도된 미구현(스텁)**.
- 판정: 정책서 §8.5.2/§8.5.3의 "차년도 일괄" 의도에 대한 미구현 갭. 단 정책서가 NEXT_YEAR_BULK의 구체 수치 동작을 명문화하지 않음 → "정책 미명세 + 코드 미구현". 첫 회계 시작 통과 후(crossed≥1)에는 어차피 만연차 15라 차이가 안 드러나고, 첫 부분기간의 차년도 일괄분은 다음 회계시작(2027-01-01) 시점이라 본 테스트로 관측 불가.
- 결론: 수치 일치(✅)이나 **NEXT_YEAR_BULK 전용 동작 미구현(⚠️ Medium)** — 후속 정책 명세화 + 구현 결정 필요.

### (c) past2(2025-02-22) 1년미만 그룹의 1년초과 전환 — 정상 ✅
- 입사일 2025-02-22 + TODAY = 근속 15개월 → `creditedMonths>=12`/`crossed>=1` 성립 → 본연차 15. `resolveEntitlement`는 분류 라벨이 아니라 실제 근속으로 판정(§8.5.4/§8.5.2). 요청서 "1년미만/초과"는 base 기준 분류일 뿐.

### (d) 월차 a값 유효기간 절단 (past2 11→8) — 정상 ✅
- m=1·2·3(2025-03/04/05-22 발생)의 유효기간(availTo 2026-03/04/05-22)이 TODAY 이전 → 소멸, 8건 잔존. `computeMonthlyPeriods`의 `availTo < today` 제외(§8.5.8). 법정 월차도 AXIS6 12개월 경과 시 소멸.

### (e) HIRE_DATE(P1) vs FISCAL(P2~4) 1년미만 그룹 차이 — 정상 ✅
- HIRE_DATE는 입사 anniversary 도래 후 본연차(base 2025-07-21은 2026-07-21 미도래→0), FISCAL은 회계 시작 1회 통과 시 즉시 만연차 15. AXIS1 정의 차이(§8.5.2)에서 비롯한 정상 분기.

### (f) 그 외 점검
- 멱등키/이중부여: `alreadyGranted` dual-read(정식키+`_HIRE` 레거시) + 달력연도 전환가드로 차단(§8.5.8) — 로직상 무결, 기부여 보유자 멱등성은 수동 검증 영역.
- 트랜잭션: `hireDateGrant` `@Transactional`, preview는 read-only 확인 ✅.
- 권한: `ensureManager`(§8.5.7), 입사일 변경도 `isManager` 가드 ✅.
- 성능: 직원 루프 내 다중 count 쿼리 존재하나 대상 인원 상한 500(`MAX_GRANT_USER_COUNT`) 가드 — 대량 부여 시 쿼리 수 주의(정보성).
- 입사일 미래 가드: `resolveEntitlement`의 `hire.isAfter(today)` 빈 entitlement 처리 존재 확인.

## 5. 최종 판정

### 6.3 처리방식 비교 결론

1. **APPLY_NEW ≡ BACKFILL (이 케이스 전부 동일).** 유효기간 12개월이라 "유효기간 내 누락 과거분"이 0이어서 BACKFILL의 소급이 발동하지 않는다. 둘의 차이는 *유효기간 내 미부여 과거분이 있을 때만* 발생.
2. **RESET_ALL만 기존 활성 STATUTORY를 취소(CANCELED)하고 변경 입사일 기준으로 재발급한다.** 순활성잔액이 **늘 수도(31→16 정리)**, **줄 수도(27→23)** 있다 — 변경 입사일 기준 재계산값으로 수렴.
3. **APPLY_NEW/BACKFILL은 기존 부여를 보존(§8.5.8 사후 차감 금지)**하므로, 변경 입사일과 **라벨이 달라지면 기존 부여가 잔존(stale·중복 누적)**한다:
   - **HIRE_DATE**: 당기 라벨이 입사 기념일 연도라 입사일이 바뀌면 라벨도 이동 → 과거변경 시 중복(31). **RESET_ALL 권장.**
   - **FISCAL**: 라벨이 회계연도(고정)라 입사일이 바뀌어도 라벨 안정 → APPLY_NEW이 중복을 안 만든다(0 신규).
   - **월차**: YYYYMM 키라 입사일이 바뀌면 새 월(키)이 생겨 APPLY_NEW에서 **11개월 상한을 넘겨 누적**될 수 있다(그룹A 27). RESET_ALL이 정리.
4. **운영 가이드**: 입사일을 **과거로** 옮기면(특히 HIRE_DATE 정책) APPLY_NEW/BACKFILL은 기존 부여가 잔존해 과다해질 수 있으므로 **RESET_ALL**이 안전. 미래로 옮기거나 FISCAL 정책이면 세 방식의 순잔액이 같다(RESET_ALL은 행 교체만).

## 7. 후속 수정 적용 (2026-05-25) — 고용노동부 표준 모델 교정 ✅ 완료

> ⚠️ **§2·§3의 회계연도(P2/P3/P4) 본연차 값은 아래 수정으로 갱신되었다.** 검증 과정에서 발견한 "회계연도 기준 첫해 본연차 조기 부여"를 고용노동부 표준 모델로 교정했다(planner→developer→qa→security 전부 통과, 빌드/테스트 OK).

### 7.1 무엇이 잘못이었나
- 엔진(`resolveFiscalEntitlement`)이 **회계연도 시작(1/1)을 1회만 넘기면(crossed≥1) 근속 1년 미만이어도 만 15일을 부여**했다. 입사 2025-07-21 직원이 2026-01-01(근속 5개월)에 15일을 받음 → §8.5.4(1년 미만=월차만)·§60② 위반.

### 7.2 교정된 표준 모델 (§8.5.3.1 신설)
crossed = 입사 후 도래한 회계연도 시작 횟수.

| AXIS3 | crossed==0 | crossed==1 | crossed>=2 |
