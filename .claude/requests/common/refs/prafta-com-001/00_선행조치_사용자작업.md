A. 의사결정 (코드 작성 불가, 사람이 정해야 함)

A-1. PUSH 인프라(FCM) 결정 — **가장 중요**

현재 DB에는 `tb\\\_noti\\\_outbox` (발송 대기/이력 outbox)와 `tb\\\_user\\\_device` (디바이스 점유) 테이블이 이미 있습니다.
하지만 **실제 푸시를 단말로 쏘는 전송 계층(FCM 등)이 붙어 있는지**가 불명확합니다. 아래를 확인/결정하세요.

* \[ ] **FCM 프로젝트가 이미 존재하는가?**

  * 있으면: FCM 서버 키(또는 서비스 계정 JSON) 위치 확인
  * 없으면: Firebase 콘솔에서 프로젝트 생성 → 서비스 계정 키 발급 필요
* \[ ] **디바이스 토큰(FCM token)을 저장하는 컬럼이 `tb\\\_user\\\_device`에 있는가?**

  * 없으면 → 작업지시서에 "디바이스 토큰 컬럼 추가" 항목을 포함시켜야 함 (현재 DDL에는 FCM 토큰 컬럼이 안 보임 → **확인 필요**)
* \[ ] **outbox를 실제 전송으로 옮기는 워커(스케줄러/배치)가 이미 도는가?**

  * `tb\\\_noti\\\_outbox.SEND\\\_STATUS`가 PENDING → SENT로 누가 바꿔주는지
  * 없으면: 이번 작업은 "outbox에 INSERT까지만" 하고, 실제 전송 워커는 별도 작업으로 분리하는 게 맞음

> \\\*\\\*판단 가이드:\\\*\\\* PUSH 전송 워커가 아직 없다면, 이번 작업의 PUSH 부분은
> \\\*\\\*"tb\\\_noti\\\_outbox에 레코드 INSERT (PENDING 상태)"까지만\\\*\\\* 구현하고,
> 실제 FCM 전송은 별도 작업으로 미루는 것을 권장합니다. (MVP ROI 관점)
> 작업지시서는 이 가정(=outbox INSERT까지)으로 작성되어 있습니다. FCM 전송 워커가
> 이미 있다면 작업지시서의 "전송 범위" 항목을 수정하세요.

A-2. 노무수령거부 통지 발송 시점 결정

노무수령거부 통지를 **언제** 근로자에게 보낼지 정해야 합니다.

* \[ ] (안1) 연차촉진 2차 촉진 이후, 미사용 연차 사용지정일이 **도래하기 전날/당일 아침**에 일괄 통지
* \[ ] (안2) 사용지정일 당일, 근로자가 **출근을 찍는 순간** 통지
* \[ ] (안3) 둘 다 (사전 통지 + 출근 시 재통지)

> 법적으로는 "사전 도달"이 중요하므로 \\\*\\\*안3(사전 통지 필수 + 출근 시 재통지)\\\*\\\*를 권장.
> 다만 MVP에서는 안1(사전 일괄 통지)만으로도 충분. 결정 후 작업지시서 §3에 반영.

A-3. "노무수령거부 대상일"을 무엇으로 식별할지 결정

시스템이 "오늘이 이 근로자의 노무수령거부 대상일"임을 어떻게 아는가?

* \[ ] 연차촉진에서 지정한 **사용지정일** 데이터가 어딘가에 저장되는가?

  * 메모리상 연차촉진(제61조)은 설계되어 있으나, **사용지정일을 저장하는 테이블/컬럼이 확정되었는지** 확인 필요
  * 없으면 → 이 작업의 **선행 의존성**. 사용지정일 저장 구조부터 만들어야 함.

> \\\*\\\*이것이 가장 큰 선행 리스크입니다.\\\*\\\* 노무수령거부는 "사용지정일"이 데이터로 존재해야
> 그날 출근을 감지할 수 있습니다. 사용지정일 저장 구조가 없으면 이 작업 자체가 성립하지 않습니다.
> → A-3을 먼저 확정하지 못하면, 작업지시서를 "사용지정일은 별도 입력/이미 존재한다고 가정"으로 한정해야 함.

A-4. 출근 감지 트리거 위치 결정

근로자가 출근을 찍을 때(`tb\\\_user\\\_attd\\\_mgmt` INSERT 시점) 노무수령거부 대상일인지 검사하는 로직을 어디에 넣을지.

* \[ ] 출근 처리 서비스(체크인) 내부에 hook 추가 → 동기 검사
* \[ ] 별도 배치가 주기적으로 스캔 → 비동기 감지

> 실시간 PUSH가 목적이므로 \\\*\\\*동기 hook(체크인 서비스 내 검사)\\\*\\\* 권장. 작업지시서는 이 가정으로 작성됨.

B. 코드/시드 준비 (DB 작업)

B-1. SYS 공통코드 시드 등록 확인

작업지시서에서 사용할 코드들이 `tb\\\_syst\\\_val\\\_m` / `tb\\\_syst\\\_val\\\_d`에 등록되어 있어야 합니다.
아래는 **신규 등록이 필요한 코드 그룹**입니다. (실제 코드값은 기존 채번 규칙에 맞춰 조정)

* \[ ] **SYS045 (알림 유형)** 에 노무수령거부 관련 타입 추가

  * `LEAVE\\\_REFUSAL\\\_NOTICE` : 노무수령거부 통지(근로자 대상)
  * `LEAVE\\\_REFUSAL\\\_CHECKIN\\\_ALERT` : 노무수령거부일 출근 감지(관리자 대상)
  * (기존 SYS045에 `LEAVE\\\_GRANT\\\_RECALLED`만 있으므로 위 2개 추가)
* \[ ] **(신규) 노무수령거부 이력 상태 코드** — 신규 SYS 그룹 1개 생성 (예: SYS0xx)

  * `NOTICED` : 통지 발송됨
  * `CHECKIN\\\_DETECTED` : 대상일 출근 감지됨
  * `ADMIN\\\_ALERTED` : 관리자 알림 발송됨
  * (MVP는 여기까지. 관리자 조치/최종확정 상태는 v1.x로 미룸)

> 코드값(varchar) 번호는 YJ가 기존 SYS 코드 번호 규칙에 맞춰 부여해야 함. Claude Code에 맡기지 말 것.

B-2. tb\_user\_device FCM 토큰 컬럼 확인

* \[ ] `tb\\\_user\\\_device`에 FCM/디바이스 푸시 토큰 컬럼이 있는지 직접 확인
* \[ ] 없으면 컬럼 추가 DDL을 YJ가 결정 (보안상 토큰도 평문 저장 정책 검토)
